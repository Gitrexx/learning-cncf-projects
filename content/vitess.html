Vitess

TiKV scales a transactional key-value store by rebuilding storage from scratch around Raft-replicated Regions. Vitess takes the opposite bet: don't replace MySQL — surround it. Vitess is a database clustering system that puts a query-routing and topology-management layer in front of a fleet of ordinary MySQL servers, so an application still speaks plain MySQL wire protocol and SQL, but its data can be transparently split across hundreds of shards on hundreds of machines. It was born inside YouTube in 2010 to solve one very concrete problem: YouTube's core MySQL database was falling over under the site's growth, and rewriting every application query to know about shards was not an option.

Where this fits Vitess is a database clustering and sharding system for MySQL. It doesn't touch MySQL's storage engine or replication protocol — it wraps standard mysqld processes with a proxy layer (VTGate) that parses SQL, decides which shard(s) a query needs, and routes it there, plus a sidecar (VTTablet) on every MySQL instance that manages its health, connections, and replication topology. A separate Topology Service (backed by etcd, ZooKeeper, or Consul — Vitess itself doesn't reinvent this, it just needs *a* consistent metadata store) tracks which shards exist and where they live. Vitess graduated CNCF in November 2019, the 8th project to do so, and now runs in production at Slack, Square/Block, GitHub, HubSpot, and (as a managed service) PlanetScale — on top of the workload it was built for at YouTube.

The problem: MySQL scales up, not out

A single MySQL primary can only take so much write traffic before it runs out of CPU, memory, or disk I/O — and unlike reads, writes can't be offloaded to replicas, because replicas apply the same binlog and stay behind the same single writer. The traditional escape hatches all have sharp edges: buy a bigger box (finite, expensive, and eventually impossible); shard manually in the application (every query, every migration, every ORM call now has to know which of N databases a row lives in, and resharding later means rewriting all of it); or move to a different database entirely (rewriting the app and losing MySQL's tooling, replication model, and operational maturity). Vitess's pitch is to keep plain MySQL as the storage engine and put the sharding logic in a layer the application never has to see — it connects over the normal MySQL protocol and, as far as it's concerned, is talking to one very large database.

The moving parts

  • VTGate — a stateless proxy that applications connect to instead of MySQL directly. It parses every query, consults the VSchema (below) to work out which shard(s) it must touch, rewrites and routes the query, and — for queries that must run on more than one shard — merges the results back into one response. Being stateless, you run a pool of VTGates behind a normal load balancer and scale it horizontally like any stateless service.
  • VTTablet — runs alongside every mysqld instance (one per MySQL primary or replica). It enforces query timeouts and row-count limits, pools and multiplexes connections, rewrites unsafe queries, exposes health checks VTGate uses to route only to healthy, caught-up replicas, and drives replication topology changes (like promoting a new primary).
  • Topology Service — the source of truth for cluster metadata: which keyspaces and shards exist, which VTTablet is the primary for each shard, routing rules. Backed by a consistent store (etcd is the common default) — conceptually the same job etcd does for Kubernetes, just for Vitess's own topology.
  • VTOrc — watches replication health and automates primary failover when a primary becomes unreachable, updating the topology so VTGate routes writes to the new primary.
  • vtctld / VTAdmin — the control-plane API and web UI for cluster operations: creating keyspaces, running backups, and driving the resharding and migration workflows described below.

Keyspaces, shards, and the VSchema

A keyspace is Vitess's name for a logical database — what an application thinks it's querying. A keyspace can be unsharded (one shard, exactly like a normal MySQL database — useful for small reference tables) or sharded across many physical shards, each shard being a normal MySQL primary plus its replicas holding one slice of the keyspace's rows. What decides which shard a given row lives on is a Vindex (vitess index) declared per table in the keyspace's VSchema — a JSON document, not something baked into the SQL schema itself: 

{
  "sharded": true,
  "vindexes": {
    "hash": { "type": "hash" }
  },
  "tables": {
    "customer": {
      "column_vindexes": [
        { "column": "customer_id", "name": "hash" }
      ]
    }
  }
}

The hash vindex type takes a column's value, hashes it, and maps the hash into a keyspace ID space (conceptually 0–255); shards each own a contiguous range of that space, conventionally named by their hex boundaries — -40, 40-80, 80-c0, c0-. Hashing spreads rows evenly regardless of the source values' distribution. A lookup vindex is the other common type: an external mapping table (itself stored in Vitess) from some other column — say email — to a keyspace ID, useful when you need to route on a column that isn't the primary sharding key.

How VTGate routes a query

What a query costs depends entirely on whether it can use a vindex:

  • Equality on the primary vindex column (WHERE customer_id = 42) — VTGate computes the keyspace ID directly and sends the query to exactly one shard. This is the fast path and the whole point of choosing a good sharding key.
  • IN-list on the vindex column — VTGate fans the query out to just the shards those specific values map to, and merges the per-shard results.
  • No usable vindex predicate (filtering on a non-indexed column, or an unfiltered scan) — VTGate has no way to narrow it down, so it scatters the query to every shard in parallel and merges (and, for ORDER BY/LIMIT, sorts) the combined results itself. Correct, but it touches the whole cluster for every such query — a sign the schema or query pattern needs a vindex.
  • Cross-shard joins — Vitess's query planner can push a join's inner query down to the shard(s) that hold the outer rows and stitch results together, though joins across unrelated shards are inherently more expensive than a join MySQL could do locally on one box.

Resharding and migration without downtime: VReplication

Both major online workflows in Vitess — Reshard (changing the shard count/boundaries of a keyspace) and MoveTables (moving tables between keyspaces, e.g. migrating an unsharded legacy database into a sharded one) — are built on the same primitive: VReplication. It first copies existing rows from source to target shards in bulk, then switches to streaming ongoing changes from the source's binlog (much like MySQL replication, but Vitess-managed and filtered/re-keyed for the target's shard boundaries) to catch the target up to the moving source. Once the target is continuously caught up, a brief traffic cutover — VTGate starts routing to the new shards, the old ones stop accepting writes — completes the migration. Because the source keeps serving traffic throughout the copy-and-catch-up phase, the whole operation is online: no maintenance window, no frozen writes beyond the final short cutover.

Keeping transactions simple: co-locate what needs to be atomic

Vitess does support a distributed two-phase commit for transactions that must atomically touch multiple shards, but it's the exception path, not the everyday one — cross-shard 2PC adds real latency and complexity. The idiomatic Vitess schema design instead picks a sharding key (often a tenant ID, user ID, or similar) so that rows which need to be transactionally consistent with each other — an order and its line items, say — always hash to the same shard, keeping ordinary transactions local to one MySQL primary where they're just... normal MySQL transactions.

Where you'd reach for it

  • A MySQL workload that's outgrown one primary — write throughput, connection count, or dataset size has hit a ceiling a bigger box won't fix, and you want horizontal scale without rewriting the application off SQL.
  • You want to keep MySQL's ecosystem — existing ORMs, backup tooling, and operational knowledge mostly keep working, because the wire protocol and SQL surface stay MySQL-compatible.
  • Managing many MySQL clusters at scale — even teams that don't need sharding adopt Vitess for VTOrc's automated failover, built-in connection pooling, and a uniform operational model (including an official Kubernetes Operator that manages keyspaces, shards, and tablets as CRDs) across a large fleet.
Often confused with Vitess vs. TiKV: TiKV is a new storage engine built around Raft from the ground up, with automatic Region splitting and Percolator-style distributed transactions native to the store. Vitess doesn't replace MySQL's storage or transaction engine at all — it's an orchestration and routing layer in front of unmodified MySQL processes, with resharding as an explicit, operator-driven workflow rather than an automatic background process. Vitess vs. manual application-level sharding: manual sharding means every query and migration in the app has to know the shard map; Vitess centralizes that knowledge in VTGate and the VSchema, so the application keeps writing ordinary SQL. Vitess vs. a plain SQL proxy (e.g. ProxySQL): a proxy load-balances and can rewrite queries, but has no concept of a keyspace, a vindex, or a shard map — it doesn't know how to route one query to the *right* shard or run an online resharding workflow.

Why it graduated

Vitess was created at YouTube in 2010 to keep its core MySQL database alive under Google-scale growth, was open-sourced in 2012, joined CNCF as one of its earliest hosted projects (2018), and graduated in November 2019 — the 8th CNCF project to reach Graduated status, after Kubernetes, Prometheus, Envoy, CoreDNS, containerd, Fluentd, and Jaeger. The graduation case rested on exactly the kind of evidence CNCF looks for: sustained large-scale production use (YouTube's MySQL fleet, plus adopters like Slack, Square, GitHub, and HubSpot), a healthy multi-vendor contributor base despite its single-company origin, and clean integration with the rest of the cloud-native stack — a Kubernetes Operator for deployment, and Prometheus metrics throughout.
