Kyverno

The previous deep-dive was OPA: a general-purpose policy engine that pulls "should this be allowed" logic out of your services into Rego, a language built for the job. Kyverno solves the exact same Kubernetes admission-control problem — decide whether a Pod, a Deployment, an Ingress should be allowed to exist, mutated on the way in, or trigger creation of something else — but makes a different bet entirely: no new language at all. A Kyverno policy is a Kubernetes resource, written in the same YAML you already write for every Deployment and Service, describing what to check against using the shape of the resource itself.

Where this fits Same slot in the stack as OPA/Gatekeeper — a validating and mutating admission webhook that the API server calls before persisting an object. Where OPA is "bring your own enforcement point, write policy in a purpose-built language," Kyverno is "install one controller, write policy as Kubernetes YAML you already know how to read." That trade — less general, much lower adoption friction for a platform team that's fluent in Kubernetes manifests but doesn't want to learn Datalog-family logic programming — is the entire reason both projects coexist as CNCF graduated projects solving the same problem.

Why not just use OPA? The YAML bet

Rego is precise and genuinely general-purpose — the same engine enforces policy on Terraform plans, Envoy requests, and CI approvals, not just Kubernetes objects. That generality has a cost: someone on the platform team has to learn a declarative logic language most engineers have never touched, debug partial-set unification when a rule doesn't fire the way they expected, and wire up Gatekeeper's ConstraintTemplate/Constraint CRDs on top before it even talks to Kubernetes.

Kyverno's founders (originally at Nirmata, donated to CNCF in 2020) bet that most platform teams only need the Kubernetes case, and that they'd rather express "this field must match this pattern" as a YAML overlay that looks like the resource it's checking, than as a logic query over a JSON document. A Kyverno ClusterPolicy is itself a CRD, so kubectl apply -f policy.yaml, kubectl get clusterpolicy, and a GitOps pipeline all work exactly like they do for any other cluster object — nothing OPA-specific to learn to operate it day to day.

Architecture: policies are CRDs, four controllers do the work

Kyverno runs as a set of Deployments in its own namespace (kyverno), split since the 3.0 line into four independently-scalable controllers, each watching the policy CRDs and doing one job:

ControllerJob
admission-controllerServes the actual ValidatingWebhookConfiguration/MutatingWebhookConfiguration HTTP endpoints the API server calls synchronously on every matching request — the real-time enforcement path, and the only one on the critical path of kubectl apply.
background-controllerPeriodically scans resources already living in the cluster against validate/verifyImages rules — catches drift and anything created before a policy existed.
reports-controllerAggregates per-request and per-scan results into PolicyReport/ClusterPolicyReport objects — the queryable compliance record.
cleanup-controllerRuns scheduled CleanupPolicy rules that delete matching resources on a cron-like interval (e.g. expired Jobs, stale CertificateSigningRequests).

One operational detail worth knowing: Kyverno manages its own webhook registration dynamically. It doesn't register one webhook for every resource kind up front — it inspects the match blocks across all installed policies and narrows the webhook's rules to only the kinds actually referenced, so a cluster with policies covering only Pods and Namespaces isn't paying an admission round-trip for every ConfigMap write.

One CRD, four rule types

A ClusterPolicy (cluster-scoped) or Policy (namespaced) holds a list of rules. Every rule starts with a match block (kinds, namespaces, label selectors, even the requesting user/service account via subjects) and an optional exclude, then does exactly one of four things:

  • validate — accept or reject the request against a pattern (or anyPattern for an OR of patterns, or a raw deny.conditions expression for anything a pattern can't express).
  • mutate — rewrite the object in place before it's persisted, via patchStrategicMerge (an overlay with special anchors) or patchesJson6902 (RFC 6902 JSON Patch, for precision edits).
  • generate — create (and optionally keep in sync) a different resource in response to the triggering one, e.g. a default NetworkPolicy the moment a Namespace is created.
  • verifyImages — check container image signatures and attestations (via cosign) before allowing the image to run — Kyverno's native answer to "did this image really come from our CI pipeline," the same supply-chain question the in-toto and TUF deep-dives later in this section approach from different angles.

validate: pattern matching, not a boolean query

apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-labels-and-limits
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: require-team-label
      match:
        any:
        - resources:
            kinds: ["Pod"]
      validate:
        message: "label 'team' is required"
        pattern:
          metadata:
            labels:
              team: "?*"
    - name: require-resource-limits
      match:
        any:
        - resources:
            kinds: ["Pod"]
      validate:
        message: "CPU and memory limits are required on every container"
        pattern:
          spec:
            containers:
              - resources:
                  limits:
                    memory: "?*"
                    cpu: "?*"

pattern mirrors the shape of the object it's checking: "?*" means "must exist and be non-empty," "1024" would mean "must equal exactly this," operators like ">1Gi" work on quantities. There's no boolean expression to write — the request passes a rule if the live object's shape matches the pattern, full stop. That's a real trade-off against Rego: pattern matching reads at a glance and needs no new mental model, but it can't express "the sum of all container CPU requests must be under 4 cores" the way an arbitrary Rego expression can (that class of check pushes you toward deny.conditions or, increasingly, a CEL expression — more on that below).

mutate: overlays with add-if-missing anchors

    - name: add-default-limits
      match:
        any:
        - resources:
            kinds: ["Pod"]
      mutate:
        patchStrategicMerge:
          spec:
            containers:
              - (name): "*"
                resources:
                  +(limits):
                    memory: "512Mi"
                    cpu: "500m"
    - name: add-env-label
      match:
        any:
        - resources:
            kinds: ["Pod"]
      mutate:
        patchStrategicMerge:
          metadata:
            +(labels):
              env: "prod"

(name): "*" is a conditional anchor that matches every element of the containers array regardless of name; +(limits) is an add-if-not-present anchor — it injects limits only when the field is missing entirely, leaving a container that already sets its own limits untouched. That "don't clobber what's already there" behavior is the default posture for defaults-injection policies, and it's exactly what makes mutate safe to run broadly instead of only against hand-picked resources.

generate: clone or author a companion resource

    - name: generate-default-networkpolicy
      match:
        any:
        - resources:
            kinds: ["Namespace"]
      generate:
        apiVersion: networking.k8s.io/v1
        kind: NetworkPolicy
        name: default-deny-ingress
        namespace: "{{request.object.metadata.name}}"
        synchronize: true
        data:
          spec:
            podSelector: {}
            policyTypes: ["Ingress"]

The trigger resource (here, a new Namespace) and the generated resource can be completely different kinds. {{request.object.metadata.name}} is a JMESPath variable pulled from the admission request that triggered the rule. data defines the new resource's content inline, the way this example does; a clone source instead copies an existing "golden" resource already in the cluster (e.g. an image-pull Secret a platform team maintains once and fans out to every namespace). synchronize: true means Kyverno keeps watching the source — edit the policy (or the cloned original) and every generated downstream copy updates to match; delete the trigger and the generated resource is deleted too.

Autogen: write the rule once, cover every Pod controller

Writing a validate or mutate rule that matches kind: Pod only protects Pods created directly — but almost nothing in a real cluster creates bare Pods. They come from a Deployment's ReplicaSet, a DaemonSet, a StatefulSet, a Job, a CronJob's JobTemplate. Rather than making you hand-write five near-identical rules with five different spec.template.spec paths, Kyverno auto-generates the equivalent rule for every standard Pod controller kind from the single Pod-scoped rule you wrote, rewriting the JSON path to match each controller's embedded Pod template (spec.jobTemplate.spec.template.spec for CronJob, and so on). The pod-policies.kyverno.io/autogen-controllers annotation lets you narrow or extend which controller kinds get an autogenerated rule, including custom-resource Pod templates like OpenKruise's CloneSet.

Enforce vs audit: background scans and Policy Reports

validationFailureAction: Enforce blocks a non-compliant request outright at admission time; Audit lets it through but records the violation — the same enforce/audit split every admission-control system needs to roll out policy without breaking production on day one. But admission time only covers new requests. With spec.background: true (the default), the background-controller periodically re-evaluates validate and verifyImages rules against every matching resource already living in the cluster — catching drift, resources created before the policy existed, or ones a privileged user pushed straight through kubectl bypassing normal review. Results from both paths — live admission requests and background scans — feed PolicyReport (namespaced) and ClusterPolicyReport objects: a continuously-updated, kubectl get policyreport-queryable compliance record, not just a pass/fail gate at creation time.

The CEL shift: Kyverno's newer policy types

Kubernetes itself gained an in-tree, webhook-free admission mechanism — ValidatingAdmissionPolicy — built on CEL, evaluated inside the API server process itself rather than over the network to an external webhook. Starting with 1.14 (April 2025) Kyverno leaned into that instead of treating it as a competitor: it shipped a new API group, policies.kyverno.io, with CEL-based ValidatingPolicy and ImageValidatingPolicy types, followed in 1.15 (July 2025) by MutatingPolicy, GeneratingPolicy, and DeletingPolicy. These compile down to the same CEL expressions the built-in ValidatingAdmissionPolicy uses — meaning some of them can run in-process in the API server's admission chain instead of round-tripping to Kyverno's webhook — while keeping Kyverno's reporting, background scanning, and exception-handling UX on top. As of this writing the CEL types are v1beta1, with GA targeted for the 1.18 release; the classic YAML-pattern kyverno.io/v1 ClusterPolicy/Policy types (everything demonstrated above) remain fully supported and are still what most existing policies in the wild are written in.

Often confused with OPA/Gatekeeper solves the identical admission-control problem in Rego, is domain-agnostic beyond Kubernetes, and can express arbitrary logic Kyverno's pattern matching can't — at the cost of a new language and an extra CRD layer (Gatekeeper) to reach Kubernetes at all. Kubernetes' built-in ValidatingAdmissionPolicy is a narrower, dependency-free alternative shipped in the API server itself: no controller to install, CEL only, validate-only in its original form, and none of Kyverno's reporting, mutate/generate/verifyImages breadth, or policy exceptions — Kyverno's new CEL-based policy types are best understood as building on top of that primitive rather than replacing it. And Kyverno is not a network policy engine or a Kubernetes-native identity system — generate rules can author a NetworkPolicy as shown above, but Kyverno itself has no opinion about how traffic is actually enforced; that's Cilium's or the CNI's job.

Why it graduated, and where you'll meet it

Kyverno joined CNCF as a sandbox project in 2020 and reached Graduated status in March 2026 — the toolchain's growth from roughly 500 GitHub stars at donation to over 9,000, and adoption at organizations including Bloomberg, Coinbase, Deutsche Telekom, LinkedIn, Spotify, Vodafone, and Wayfair, was the graduation case: a policy engine platform teams could actually get their whole organization to write policy for, not just the security team fluent in a new language. You'll meet Kyverno as the admission controller enforcing Pod Security Standards variants, image-provenance checks ahead of production, default-injection for resource limits and labels, and namespace-scaffolding automation (default NetworkPolicies, Quotas, RBAC) on any cluster where "policy" needed to mean "YAML the whole platform team can read," not "Rego the security team maintains alone."
