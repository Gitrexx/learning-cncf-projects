Open Policy Agent (OPA)

In the Falco deep-dive, "admission control" kept coming up as the layer upstream of runtime detection — the thing that decides whether a Pod is allowed to exist in the first place, before Falco ever gets a chance to watch it misbehave. OPA is the general-purpose engine most admission control (and a lot more besides) is built on: a policy evaluator that takes a JSON document describing "what's about to happen" and a set of declarative rules written in a language called Rego, and returns a decision — also JSON. It has no idea what a Kubernetes Pod is. That's deliberate, and it's the whole point.

Where this fits Every service you've ever written has authorization logic tangled into its code somewhere — an if user.role != "admin" here, a hardcoded list of allowed S3 buckets there. OPA's pitch is to pull that decision out into its own component, express it as data-driven policy, and let any service ask it a question over a simple API. Kubernetes admission control (via Gatekeeper, covered below) is OPA's most famous deployment, but it's the same engine behind Envoy authorization filters, Terraform plan gating, CI/CD approval checks, and API-gateway authorization — anywhere "should this be allowed?" needs to be answered consistently and auditably.

The problem: authorization logic scattered everywhere, in every language

Before a general policy engine, "should this request be allowed" logic lives wherever someone happened to write it: inline in a microservice's request handler, in a Terraform wrapper script, in a Jenkins pipeline step, in a Kubernetes admission webhook written from scratch. Every one of those is a different language, a different deploy cycle, and a different place a security or platform team has to look to answer "what's our policy on privileged containers?" — and every one of them has to be updated, tested, and redeployed separately when the policy changes.

OPA's answer is to decouple policy decision-making from policy enforcement. The service that enforces a decision (a Kubernetes API server, an Envoy proxy, a CI pipeline) stays a thin policy enforcement point: it packages up the relevant facts about the request as JSON, sends that to OPA, and does whatever OPA's answer says. All the actual logic — what counts as compliant, what's forbidden, under what conditions — lives in one place, in one declarative language, versioned and tested like any other code.

Architecture: an in-memory engine over two kinds of documents

Structurally, OPA is a small, dependency-light binary (a single static Go binary) built around one core idea: everything it reasons about is a JSON document, and it keeps two flavors of them in memory to evaluate a query.

DocumentWhat it is
inputThe request-specific JSON handed to OPA at query time — a Kubernetes AdmissionReview object, an HTTP request's method and headers, a Terraform plan. Never stored; it's the question.
base documents (data)Context OPA already has loaded — reference lists (allowed registries, an RBAC role table), pulled in as plain JSON alongside policy, typically via a bundle (below).
virtual documentsThe output of evaluating Rego rules against input and data — the actual answer, e.g. data.k8s.admission.allow.

OPA is deliberately deployment-agnostic about where it runs relative to the thing enforcing its decisions:

  • Sidecar / host daemon — the most common production shape: OPA runs colocated with (or on the same node as) the service that queries it, over localhost HTTP, so a policy decision never leaves the machine and stays low-latency.
  • Library — Go programs can embed OPA's evaluator directly (no network hop at all); other languages can compile a Rego policy to WASM and evaluate it in-process.
  • Central service — a shared OPA (or fleet of them) queried over the network, simpler to operate but a shared dependency and an extra network hop per decision.

Whichever shape, the same REST API underneath: POST /v1/data/<path> with an input body evaluates the virtual document at that path and returns it as JSON.

Rego: policies that generate documents, not step through branches

Rego (inspired by Datalog) reads unfamiliar at first because it isn't procedural — a Rego rule doesn't execute top-to-bottom like a function, it declares what's true. The critical idiom to internalize is the partial set rule: 

package k8s.admission

import rego.v1

default allow := false

allow if {
    count(deny) == 0
}

deny contains msg if {
    some container in input.request.object.spec.containers
    not startswith(container.image, "registry.corp.io/")
    msg := sprintf("container %q uses disallowed registry: %q", [container.name, container.image])
}

deny contains msg if {
    some container in input.request.object.spec.containers
    container.securityContext.privileged == true
    msg := sprintf("container %q must not run privileged", [container.name])
}

deny contains msg if {
    input.request.object.spec.hostNetwork == true
    msg := "hostNetwork is not allowed"
}

Three separate deny contains msg if { ... } blocks all define the same rule, deny — Rego automatically unions every message any of them produce into one set, rather than the last match overwriting the others the way an imperative if/else if/else chain would. And within a single block, some container in input.request.object.spec.containers means "for every container that satisfies the rest of this body" — if three containers all fail the registry check, that one rule body contributes three separate messages to the set, one per container. That's the mental shift: a Rego rule is a generator over every combination that makes the body true, not a single branch that fires once. allow is then just "true when the deny set is empty" — the enforcement point checks one boolean, but the interesting work is entirely in what populated (or didn't populate) deny.

Rego v1 OPA 1.0 (released January 2025) made the if and contains keywords in the example above mandatory for every rule — older Rego let you write deny[msg] { ... } with no keywords at all. If you see that bracket syntax in older blog posts or existing policies, it's pre-1.0 Rego; opa fmt --rego-v1 rewrites it automatically.

Bundles, decision logs, and the management APIs

A single OPA instance evaluating one policy file is the whole story for a demo; running it in production adds three management concerns, all standardized as REST APIs so tooling doesn't have to be OPA-instance-specific:

  • Bundles — a .tar.gz of Rego policy plus JSON data, served from an object store or HTTP endpoint. OPA polls for a new bundle on an interval and hot-swaps it in atomically, so shipping a policy change is "upload a new bundle," not "redeploy every OPA instance."
  • Decision logs — every query OPA answers (in production settings) is recorded with its input, the resulting decision, and a decision_id, streamed to a log sink. This is what makes "why was this request denied last Tuesday" answerable after the fact, and it's the audit trail regulators and security teams actually want.
  • Status & discovery APIs — OPA reports its own health and which bundle revision it's running, and a discovery bundle can even hand OPA the rest of its configuration remotely, so a fleet of OPAs can be centrally managed without touching each instance's local config file.

OPA + Gatekeeper: how Kubernetes admission control actually uses this

Bare OPA has no idea what a Kubernetes ValidatingWebhookConfiguration is — it just answers queries over JSON. Gatekeeper is the project that wires OPA into Kubernetes as a first-class admission controller, and it does that with two custom resources built on OPA's Constraint Framework:

ResourceRole
ConstraintTemplateDefines reusable policy logic (Rego, or increasingly CEL) plus a schema for the parameters that policy accepts — like defining a function signature. Registering one also registers a new CRD kind.
ConstraintAn instance of a ConstraintTemplate's CRD — supplies actual parameters (e.g. the specific list of allowed registries) and which resources/namespaces it applies to. Many Constraints can reuse one ConstraintTemplate.

Gatekeeper's webhook receives every admission request, evaluates it against every applicable Constraint through its embedded OPA, and enforces (or, in audit mode, just records) any violation — the same deny-set-to-decision model above, packaged as Kubernetes-native YAML instead of hand-managed bundles.

Often confused with Kyverno (next deep-dive) solves the same admission-control problem but skips Rego entirely — policies are plain Kubernetes YAML, no new language to learn, at the cost of being Kubernetes-only where OPA is general-purpose. Falco (previous deep-dive) answers a different question at a different time: OPA/Gatekeeper decide whether a resource is allowed to be created; Falco watches what an already-running workload actually does. And OPA itself is not an authentication or identity system — it has no concept of who a user is beyond whatever claims show up in its input document; it's purely the decision layer that something else (your API gateway, your Kubernetes API server) has to feed and act on.

Why it graduated, and where you'll meet it

OPA graduated CNCF in February 2021 — the first policy-focused project to reach that bar — on the strength of being genuinely domain-agnostic: the same engine, the same Rego language, and the same decision-log/bundle tooling work whether the question is "can this Pod be created," "can this Envoy request pass through," "does this Terraform plan violate a guardrail," or "can this CI job deploy to production." You'll meet OPA directly inside Gatekeeper on nearly any Kubernetes cluster with real admission policy, as an Envoy ext_authz filter for API authorization, embedded in Terraform-policy tools like Conftest, and generally anywhere a platform team wants "policy as code" reviewed and versioned the same way application code is.
