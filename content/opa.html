Open Policy Agent (OPA)

Falco answered "is this already-running workload doing something suspicious." OPA answers a different, earlier question: "should this request, resource, or action be allowed at all" — and it answers it for almost anything, not just Kubernetes. A Pod that requests privileged mode, an API call from a user without the right role, a Terraform plan that would open a security group to the world, a CI pipeline stage running against the wrong branch — all of these are the same shape of problem: some piece of structured data (a request) needs to be checked against some rules (a policy) to get a yes/no (a decision). Open Policy Agent is a general-purpose engine that does exactly that, decoupled from every one of those systems, using its own declarative language: Rego.

Where this fits OPA is a decision engine, not a Kubernetes component and not a runtime watcher. It sits wherever a piece of software needs to ask "is this allowed?" and gets back a JSON answer — most visibly, in this landscape, as the brains behind Kubernetes admission control via Gatekeeper. Compared to Falco (runtime behavior, after the fact) and to cert-manager/SPIFFE (identity, not authorization), OPA is squarely about policy as code.

The problem: policy logic duplicated across every system

Before a shared policy engine, "is this allowed" logic tends to get hand-rolled separately in every service that needs it: an if user.role == "admin" block in one microservice's Go code, a different ad hoc check in a Python CI script, a third one baked into Terraform via string matching. Every one of those checks is written in a different language, tested differently (if at all), and reviewed by different people with different context — so "who's allowed to do what" ends up as tribal knowledge scattered through a codebase instead of a single, inspectable source of truth. OPA's premise is to pull that logic out of application code entirely: the service sends OPA a JSON description of what's being asked (the input), OPA evaluates it against Rego policies (optionally combined with reference data the policy needs, like a role list), and returns a JSON decision. The calling service never needs to know the rule that produced the answer — same as a Kubernetes controller never needing to know how the scheduler picked a node, just that it did.

Architecture: a general-purpose decision service

This is the detail that trips people up coming from a Kubernetes-only mental model: OPA has no idea what a Pod is. It's a standalone binary that evaluates Rego against JSON, full stop. How it gets wired into a particular system is someone else's integration layer — for Kubernetes, that layer is Gatekeeper (below). OPA itself can run three ways:

Deployment modeHow it's used
Go libraryEmbedded directly inside a Go program via the rego package — no network hop, no separate process.
Sidecar / host daemonA local OPA process next to the calling service, queried over localhost HTTP — the most common pattern, trading a tiny network hop for language-agnostic integration.
Centralized serviceOne OPA (or cluster of them) serving decisions to many callers over the network — simpler to operate, at the cost of a shared-fate dependency and extra latency per call.

Whichever mode, the interface is the same REST decision API: POST /v1/data/<policy path> with a body of {"input": {...}}, returning {"result": ...} — the evaluated value of the rule at that path. A Kubernetes admission check, an Envoy ext_authz call, and a CI gate all speak this exact same protocol; only the shape of the input document differs.

Policies (and any static reference data) reach a running OPA instance as bundles: OPA polls a bundle server on an interval, downloads a new bundle if the revision changed, and hot-swaps it in — so rolling out a policy change looks like a Git commit and a bundle publish, not a redeploy. Every decision OPA makes can also be streamed out as a structured decision log, which is what turns "we have a policy" into "we can prove what it actually decided, for every request, historically."

Rego: a query language over JSON

Rego (inspired by Datalog) looks unusual at first because it's not describing steps, it's describing conditions that make a rule true. A minimal policy: 

package example

default allow := false

allow if {
  input.method == "GET"
  input.path == ["orders"]
  input.user.role == "viewer"
}

A few things about this that are easy to get wrong coming from a normal programming language:

  • A rule body is an AND. Every statement inside { ... } must hold for the rule to fire — Rego calls this unification: each statement is a query that either succeeds (binds/matches) or fails, and the whole body succeeds only if every statement does.
  • Multiple definitions of the same rule name are an OR. You can write allow if { ... } a second time with a different body, and allow is true if either block's statements all hold. This is the idiomatic way to express "any one of these conditions is sufficient" without ||.
  • default sets the fallback — if no allow if block ever fires, the rule evaluates to whatever default allow declared (almost always false, so policies fail closed).
  • Partial rules build up a set. deny contains msg if { ... } doesn't return one boolean — every block that fires contributes its msg to the deny set, so a single evaluation can report every violation at once, not just the first one found.
A syntax note if you're reading older Rego in the wild OPA 1.0 (December 2024) made the if keyword before a rule body and the contains keyword for partial-set rules mandatory — what's shown above is current Rego v1. Plenty of blog posts, older Gatekeeper constraint templates, and existing production policies still use the pre-1.0 style — allow { ... } without if, and deny[msg] { ... } instead of deny contains msg if { ... }. Semantically identical; you'll meet both forms.

OPA on Kubernetes: Gatekeeper

OPA doesn't hook into the API server on its own — that integration is Gatekeeper, a separate CNCF project (also under the OPA org) built as a ValidatingAdmissionWebhook that embeds the OPA constraint framework. Gatekeeper's policy model is deliberately two separate CRDs, splitting "what a rule checks" from "where it applies":

CRDRole
ConstraintTemplateDefines the Rego logic and a schema for parameters — written once by a platform team, e.g. "require these labels" with a parameterizable label list.
ConstraintAn instance of a ConstraintTemplate: fills in the parameters (which labels) and a scope (which kinds/namespaces it applies to) — written by whoever owns that specific rule's rollout.

When a resource is created or updated, the API server sends Gatekeeper an AdmissionReview; Gatekeeper evaluates it against every matching Constraint (each one delegating to its ConstraintTemplate's Rego, run inside an embedded OPA), and the request is rejected if any Constraint's violation set is non-empty — exactly the "collect every deny message" pattern from the Rego section above, now wired to a real API server. Gatekeeper also runs a separate audit loop that periodically re-evaluates already-existing resources against current Constraints — catching drift from a Constraint that was tightened after some objects were already admitted, something a webhook alone (which only sees new admission requests) can never do.

Also notice that allow never directly inspects the request — it only checks count(deny) == 0, so tightening or loosening what counts as a violation is purely a matter of editing deny blocks, and allow's logic never has to change.

Beyond Kubernetes: one engine, many enforcement points

Because OPA's contract is just "JSON in, JSON out," the same Rego skillset and the same engine show up well outside Kubernetes:

  • API gateways & service mesh — Envoy's ext_authz filter can call OPA per-request for fine-grained authorization (this is also how Istio can delegate authorization decisions to OPA).
  • Infrastructure as code — Conftest runs Rego against Terraform plans, Kubernetes YAML, or Dockerfiles in CI, failing a pipeline before a bad change ever reaches a cluster or cloud account.
  • Custom application authorization — microservices querying a local OPA sidecar for "can this user do this action on this resource," replacing hand-rolled RBAC checks with one auditable policy set.
  • Commercial control plane — Styra, founded by OPA's original creators, offers a hosted management layer (bundle distribution, decision log aggregation, a policy authoring UI) on top of open-source OPA — the project itself stays fully open and CNCF-governed.
Often confused with Kyverno (next deep-dive) solves the same Kubernetes admission-control problem as Gatekeeper but writes policies as native Kubernetes YAML instead of Rego — no new language to learn, at the cost of being Kubernetes-only where OPA/Rego is general-purpose. Kubernetes' own ValidatingAdmissionPolicy (built into the API server, CEL-based, stable since v1.30) runs in-process with no separate webhook service or extra network hop at all — a lighter-weight native option for policies simple enough to express in CEL, though Gatekeeper and Kyverno both still cover richer scenarios (external data lookups, mutation, resource generation) that ValidatingAdmissionPolicy doesn't. And don't conflate OPA the engine with Gatekeeper the Kubernetes integration — OPA has no Kubernetes awareness at all; Gatekeeper is what teaches it to speak AdmissionReview.

Why it graduated, and where you'll meet it

OPA entered CNCF Sandbox in March 2018, moved to Incubating in April 2019, and graduated on January 29, 2021 — the first general-purpose policy engine to reach that bar, on the strength of adoption that spans well past its most visible use case. You'll meet OPA most often as the engine underneath Gatekeeper enforcing Kubernetes guardrails (no privileged containers, no images from untrusted registries, mandatory resource limits), but recognizing the pattern "Rego policy + JSON input + allow/deny decision" will let you spot it anywhere a team has pulled authorization or validation logic out of application code and into a shared, testable, version-controlled policy layer — CI gates, API authorization, cloud infrastructure guardrails, all speaking the same decision API.
