Prometheus

Prometheus is the reason "labels" and "PromQL" are now the default vocabulary for talking about metrics in cloud-native systems. It's a metrics collection, storage, and alerting system built around one contrarian idea for its era: instead of every service pushing its numbers somewhere, Prometheus pulls — it walks over to each target on a schedule and scrapes a plain-text HTTP endpoint. That single design choice, paired with a dimensional data model and its own query language, is what makes Prometheus fit Kubernetes so naturally that it became the de facto monitoring layer for the entire ecosystem.

Where this fits Prometheus was the second project ever to reach CNCF Graduated status, in August 2018 — right after Kubernetes itself. It was created at SoundCloud in 2012, inspired by Google's internal Borgmon system. Today it's less "a tool you install" and more "a data model and protocol" — the /metrics text-exposition format and PromQL are implemented or ingested by most observability vendors (Datadog, Grafana Cloud, AWS Managed Prometheus, and more), and the Kubernetes API server, kubelet, etcd, CoreDNS, and Envoy all expose Prometheus-format metrics out of the box.

The problem: push-based monitoring didn't fit a dynamic cluster

Before Prometheus, the common pattern (StatsD, Graphite) was push: each application process actively sends its metrics to a central collector, usually over UDP, on its own schedule. That works fine for a static fleet of long-lived hosts, but it breaks down as infrastructure gets more dynamic. The collector has no way to tell "no data because the service is idle" from "no data because the service crashed, or the network dropped the packets" — UDP pushes are fire-and-forget. And every application needs to know, and keep up to date, the address of wherever the collector currently lives.

Kubernetes made this worse: Pods are ephemeral, rescheduled, IP addresses churn constantly. A pull-based system inverts the relationship — the monitoring system already needs to discover what's running (via the Kubernetes API, exactly like kube-proxy or an Ingress controller would), so it can use that same discovery to know what to scrape. And a failed scrape is itself a first-class, unambiguous signal: up == 0 tells you precisely that a target didn't answer, at a precise timestamp — no guessing about whether "silence" means healthy or dead.

The data model: a metric name plus a set of labels

Every time series in Prometheus is uniquely identified by a metric name plus a set of key/value labels — for example http_requests_total{method="GET", path="/api/orders", status="200"}. Each distinct combination of label values is its own independent time series internally; this is the dimensional data model, and it's what lets PromQL slice, filter, and re-aggregate along any of those dimensions later, instead of committing to one hierarchy up front like Graphite's dotted metric names did.

Prometheus has four metric types, and which one a metric is changes what queries make sense on it:

Architecture: scrape, store, query, alert

The Prometheus server is a single binary with three main jobs. Its retrieval component reads a scrape configuration, resolves target lists via a service discovery integration (for Kubernetes: the kubernetes_sd_config, which watches Pods, Services, and Endpoints via the API server, the same watch mechanism a controller uses), applies relabeling rules to keep or drop/rename targets and labels, then issues an HTTP GET to each target's /metrics endpoint on a fixed interval (commonly 15–30s) and parses the plain-text exposition format. Its storage component is a custom local time-series database (the TSDB, below). Its HTTP server exposes the PromQL query API (used by the built-in expression browser, Grafana, or anything else) and evaluates configured recording and alerting rules on a schedule.

Two companion pieces round out the model. Exporters are small adapter processes that translate a system's native stats into Prometheus format when the system itself doesn't speak it — node_exporter for host/kernel metrics, kube-state-metrics for the state of Kubernetes objects, and hundreds more for databases, queues, and hardware. The Pushgateway is the deliberate escape hatch for the one case pull doesn't fit: short-lived batch jobs that finish before a scrape would ever catch them — they push their final metrics to the Pushgateway once, and Prometheus scrapes that on its normal schedule. Alertmanager is a separate process the server forwards firing alerts to; it owns grouping, deduplication, silencing, inhibition, and routing to Slack/PagerDuty/email — kept deliberately out of the server so alert delivery survives a Prometheus restart.

Storage: an append-only local TSDB, not a general database

Prometheus's TSDB is local to each server and optimized for one access pattern: many small samples, appended in roughly time order, queried mostly by recent range. Incoming samples land first in the head block, an in-memory structure (default 2-hour window) that also gets written to a write-ahead log (WAL) on disk as a crash-recovery journal — if Prometheus restarts, it replays the WAL to rebuild the head instead of losing the last two hours. Once the head's window is exceeded, its data is compacted into an immutable on-disk block: a directory containing compressed sample chunks and an index mapping label combinations to the chunks that hold their samples. Background compaction later merges adjacent small blocks into progressively larger ones (up to ~10% of total retention), which is why old data takes less disk overhead per sample than fresh data. This design is exactly why a single Prometheus server doesn't horizontally scale on its own — it's why systems like Thanos, Cortex, and Mimir exist: they sit on top of this same block format for durable, multi-cluster, long-term storage.

PromQL: selecting, ranging, and aggregating

A bare metric name like http_requests_total is an instant vector — one current value per matching time series. Adding a duration in brackets, http_requests_total[1m], turns it into a range vector — the raw samples from the last minute for each series, which most functions consume as input. The single most important function is rate(counter[range]): the per-second average increase of a counter over that range. Because counters reset to zero on a process restart, rate() specifically watches for a value going down between samples and, on detecting one, assumes the counter restarted from zero and adds the post-reset value back into the increase — so a restart shows up as a brief, correct rate rather than an absurd negative number. Aggregation operators like sum(...) by (job) collapse many series down to fewer, keeping only the listed labels — the standard way to go from "rate per Pod instance" to "rate per service." histogram_quantile() takes cumulative bucket counts (the le — "less than or equal" — label on a histogram's _bucket series) and linearly interpolates within the bucket that contains the target rank to estimate a percentile like p90 latency.

Alerting rules and Alertmanager

Recording rules precompute and save a frequently-needed or expensive PromQL expression under a new metric name on a schedule, so dashboards query the cheap precomputed series instead of recalculating it every time. Alerting rules are the same idea aimed at a boolean condition (a query that returns any series at all means the alert is active); when one has been true continuously for its configured for duration, Prometheus marks it firing and pushes it to Alertmanager. Alertmanager then groups related alerts into one notification (e.g. one Slack message for "23 Pods down" instead of 23 pages), applies inhibition (suppress "high latency" once "service down" is already firing for the same service — the second is just a symptom of the first), honors any active silences (a maintenance window someone declared), and finally routes the result to the right receiver by label match.

Why it graduated, and where you'll meet it

Prometheus graduated on the strength of being independently reinvented at nearly every large engineering org before it existed as shared software — the pull model, dimensional labels, and a purpose-built query language solved a problem everyone running dynamic infrastructure actually had. You'll meet it as the metrics backbone underneath most Kubernetes clusters (frequently paired with Grafana for dashboards), as the API that Horizontal Pod Autoscalers and KEDA can scale on via the Prometheus Adapter, and as the ingestion target that most CNCF projects (Envoy, Istio, Cilium, CoreDNS, etcd) expose natively. It's still actively evolving: Prometheus 3.0 (November 2024) stabilized native histograms, added a new default web UI, support for UTF-8 metric and label names, and — notably — the ability to natively ingest OTLP (OpenTelemetry's wire protocol), plus a more efficient Remote Write 2.0 protocol for shipping data to long-term storage backends.

Often confused with Grafana is a visualization layer that queries Prometheus (among many other sources) — it has no scraper and no TSDB of its own, and doesn't compete with Prometheus so much as sit on top of it. OpenTelemetry standardizes how applications are instrumented and how telemetry is transported (via the OTel Collector); it's complementary, not competing — an OTel Collector can export metrics into Prometheus format, and Prometheus 3.0 can now ingest OTLP directly. Thanos, Cortex, and Mimir are separate systems built on top of Prometheus's data model and block storage format to add horizontal scale, multi-cluster global querying, and long-term retention — they extend Prometheus, they don't replace it. StatsD and Graphite are the older, push-based predecessors Prometheus was designed as a reaction against.
