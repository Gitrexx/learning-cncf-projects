Flux

Argo proved the pull-based GitOps model — an in-cluster controller reconciling toward Git instead of a CI job pushing changes with standing cluster credentials — as a single, centralized platform with its own UI. Flux is CNCF's other graduated GitOps toolkit, and it takes the opposite architectural bet: instead of one application-shaped controller, Flux is the GitOps Toolkit — a set of small, single-purpose controllers, each built around one Kubernetes CRD, that compose through a shared "source produces artifact, other controllers consume it" contract. There's no bundled UI; Flux is a set of APIs meant to be composed, scripted, and built on top of.

Where this fits Same delivery-layer slot as Argo CD: Flux doesn't build images (your CI does that) and it doesn't run the cluster (Kubernetes does). It's the layer that continuously pulls already-built manifests and charts from Git (or an OCI registry) into a running cluster — the thing that makes "Git is the source of truth" literally true, all the time, not just at deploy time.

The GitOps Toolkit: one job per controller

Where Argo CD's application controller does source-fetching, diffing, and applying all in one process, Flux splits that into independently deployable controllers connected by CRDs. Each is a small Kubernetes operator you can run, upgrade, and even omit on its own:

ControllerCore CRD(s)Job
source-controllerGitRepository, OCIRepository, HelmRepository, HelmChart, BucketFetches from Git/OCI/Helm/S3-compatible sources and publishes a versioned Artifact
kustomize-controllerKustomizationBuilds an Artifact with Kustomize and applies it to the cluster, continuously
helm-controllerHelmReleaseInstalls/upgrades Helm charts sourced from an Artifact, the declarative way
notification-controllerAlert, Provider, ReceiverForwards Flux events out (Slack, webhooks) and accepts events in (instant re-reconcile on push)
image-reflector / image-automationImageRepository, ImagePolicy, ImageUpdateAutomationScans registries for new tags and commits the update back into Git

The core contract: sources produce Artifacts

Every reconciliation in Flux starts with source-controller. Point a GitRepository at a repo/branch (or an OCIRepository at a registry, or a HelmRepository at a chart repo), and on every reconcile interval it fetches the latest content, computes a content-addressed revision — for Git this looks like main@sha1:8f3c2a1… — and, only if that revision changed, repackages it as a tarball Artifact served over an internal HTTP endpoint inside the cluster. Nothing downstream ever talks to GitHub directly; everything downstream — the kustomize-controller, the helm-controller, even a custom controller you write — consumes that same Artifact HTTP endpoint. That single indirection is what lets Flux support Git, OCI registries, S3 buckets, and Helm repos through one uniform interface, and it's why Flux can reconcile straight from a signed OCI artifact with no Git repo involved at all.

Kustomization: continuous apply, continuous drift correction

A Kustomization resource ties a sourceRef (which GitRepository/OCIRepository to build from) to a path inside that Artifact, and reconciles on an interval (commonly 1m): 

apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: checkout
spec:
  interval: 1m
  path: ./deploy/production
  prune: true
  sourceRef:
    kind: GitRepository
    name: checkout-repo
  dependsOn:
    - name: infra-base
  healthChecks:
    - kind: Deployment
      name: checkout
      namespace: default

Every interval, kustomize-controller re-runs kustomize build against the latest Artifact, computes a diff against live cluster state, and applies it with server-side apply. prune: true means resources removed from Git get deleted from the cluster too, not just left behind. dependsOn makes one Kustomization wait for another to report healthy before it reconciles — the ordering mechanism that plays the same role as Argo CD's sync waves, but expressed as an explicit graph between whole Kustomizations rather than a numeric annotation on individual resources. healthChecks gates Ready status on named resources actually rolling out successfully.

The differentiator: drift correction, not just drift detection Because the reconcile loop reruns on every interval regardless of whether Git changed, Flux doesn't just apply once and wait for the next commit — it keeps re-diffing live state against the last-fetched Artifact and re-applies whenever they disagree. Someone runs kubectl edit on a Flux-managed Deployment and changes the replica count by hand? Within one interval, kustomize-controller reverts it back to what Git says, no commit required. This is Flux's default behavior, whereas GitOps engines built around an explicit "sync" action have historically needed self-heal turned on separately to get the same guarantee.

HelmRelease: the same model, for charts

helm-controller mirrors the Kustomization pattern for Helm: a HelmRelease references a chart (resolved through a HelmChart/ HelmRepository Artifact, exactly like Kustomization's sourceRef), carries inline values, and reconciles continuously — including drift correction on Helm-managed resources, and automatic rollback if a new release fails its readiness checks. Because it's a first-class CRD rather than a shell-out to the helm binary, chart installs are declarative, observable via kubectl get helmrelease, and composable with dependsOn alongside plain Kustomizations — a database HelmRelease can gate an application Kustomization that needs it up first.

Multi-tenancy: impersonation, not implicit trust

A cluster with many teams' Kustomizations reconciling shouldn't mean every team's Git commits can touch every other team's resources with the same blanket permissions. Each Kustomization/HelmRelease can set a serviceAccountName, and the controller impersonates that ServiceAccount — scoped by ordinary Kubernetes RBAC — for every apply it performs on that object's behalf. A platform team can hand tenant teams a namespace and a tightly-scoped ServiceAccount, point their Kustomization at it, and know a compromised or careless commit in that tenant's repo can't reach outside its RBAC boundary — no separate multi-tenancy feature required, just Kubernetes' own permission model applied per reconciler.

Closing the loop: notifications and image automation

notification-controller runs in both directions. Outbound, an Alert + Provider pair forwards Flux reconciliation events — a failed apply, a completed sync — to Slack, Microsoft Teams, generic webhooks, or as OpenTelemetry spans for tracing a rollout across the whole toolkit. Inbound, a Receiver exposes a webhook endpoint that a Git host or registry can hit on push, triggering an immediate reconciliation instead of waiting out the poll interval — the event-driven complement to Flux's default interval-based polling.

image-reflector-controller and image-automation-controller push GitOps a step further by closing the loop back into Git itself: an ImageRepository scans a registry for new tags, an ImagePolicy picks the one that matches a rule (semver range, newest build, regex), and an ImageUpdateAutomation patches the matching tag directly into your manifests and commits that change to Git — so even "just bump the image tag" stays GitOps: the commit exists, is reviewable, and is what source-controller then picks up on its next poll.

Often confused with Argo CD solves the same pull-based reconciliation problem but as one centralized, UI-first application platform with an explicit sync action per Application; Flux is a modular set of composable controllers, continuously self-healing by default, with no bundled UI (a community Flux Operator and dashboards like Weave GitOps fill that gap when teams want one). Where Argo has Argo Rollouts for progressive delivery, Flux's ecosystem sibling is Flagger — a separate CNCF-adjacent project that drives canary/blue-green rollouts by watching metrics and manipulating a service mesh or ingress, triggered by the same HelmRelease/Kustomization revisions Flux reconciles.

Why it graduated, and where you'll meet it

Flux graduated in November 2023 on the strength of the same core GitOps guarantee as Argo — Git as the single source of truth, continuously enforced — proven through a different architectural lens: small, independently composable controllers over one centralized application platform. You'll meet Flux wherever a platform team wants to build its own opinionated internal developer platform on top of GitOps primitives rather than adopt a monolithic UI, wherever multi-tenant clusters need RBAC-scoped reconciliation out of the box, and increasingly wherever teams want to ship OCI artifacts straight into a cluster without a Git repo in the loop at all.
