in-toto

SPIFFE and SPIRE (the last two deep-dives) answer "is this running workload really who it claims to be, right now?" in-toto asks a different question about the same software, earlier in its life: did this artifact actually go through the process I think it went through — the right steps, in the right order, each one done by someone authorized to do it — before it ever became a running workload at all?

Where this fits in-toto is a framework and toolset for instrumenting a software supply chain — clone, build, test, package, sign, deploy — so that every step leaves behind a signed, verifiable record of what it did and what files it touched. A separate layout, authored once by whoever owns the pipeline, says who is allowed to perform each step and how the steps must chain together. Anyone downstream — a CI gate, a package registry, an end user — can later run verification against that layout and the accumulated records, without re-running the pipeline or trusting any single step in isolation.

The problem: a pipeline is only as trustworthy as its weakest, unverified link

A typical release goes through many hands and many machines: a developer pushes code, a CI runner checks it out, a build step compiles it, a test step runs a suite, a packaging step bundles the artifact, and a deploy step ships it. Each individual tool in that chain might be perfectly secure. The failure mode in real incidents — the event-stream npm package compromise, the Codecov Bash uploader tampering, the SolarWinds build-server injection, the xz backdoor smuggled into a release tarball that never matched its source — is almost never "one tool got hacked and everyone noticed." It's that nothing was checking the seams between steps: a compromised build server can silently substitute a different binary than the one the source actually produced, or an attacker can skip straight to packaging a step that should have required a code review first, and nothing downstream would know, because nothing was recording — and later checking — that the whole sequence actually happened as intended.

in-toto's approach: make every step attest to what it consumed and produced, tie those attestations to a specific authorized identity, and give whoever owns the pipeline a way to define, in advance, exactly what a legitimate run is supposed to look like — then let anyone verify an actual run against that definition after the fact.

The layout: the pipeline's contract, signed before anything runs

A layout is written once, by whoever owns the project — think of it as playing the same role the offline root key plays in TUF (a later deep-dive): it's the one thing every other check is anchored to. A layout specifies, for each expected step:

  • Functionaries — the public keys of whoever is authorized to perform this step. A step can require agreement from more than one functionary; the layout sets a threshold (e.g. "2 of these 3 keys must sign off") so no single compromised credential can forge a step alone.
  • Artifact rules — constraints tying this step's inputs (materials) and outputs (products) to other steps, e.g. "this step's materials must MATCH the previous step's products" — this is what actually chains the pipeline together and is what catches tampering between steps.
  • Inspections (optional) — commands the verifier itself runs against the final artifacts at verification time, e.g. re-running a linter or diffing an unpacked archive.

The layout itself is signed by the project owner's key and typically has a short expiration, so a stale or leaked layout can't authorize a stale set of functionaries forever.

Link metadata: proof that a step actually happened

Each functionary runs their step through in-toto-run (a thin wrapper around the actual command) instead of running it bare. The wrapper:

  1. Hashes every file matching the step's declared materials pattern before running the command.
  2. Runs the actual command (a build script, a test suite, whatever the step really does).
  3. Hashes every file matching the step's declared products pattern after the command finishes.
  4. Bundles materials, products, the command run, and some environment metadata into a link, and signs it with the functionary's private key.

A link is deliberately not a claim about intent or correctness — it doesn't say "this build succeeded" or "this code is safe." It only says, cryptographically: this specific key hashed these exact input bytes, ran this exact command, and produced these exact output bytes. That narrow, mechanical claim is precisely what lets independent links from independent steps be checked against each other without any of them having to trust one another directly.

What just got caught, and how Notice that verification never re-executes the build or inspects file contents for "maliciousness" — it only compares independently-signed numbers. When the artifact is swapped, package's own link honestly records the hash of whatever it actually received, which simply no longer matches the product hash build's link recorded — an artifact rule violation. When an unauthorized key signs a step, the signature check fails independently of whether the hashes agree at all. Two orthogonal checks, catching two orthogonal attacks.

From links to attestations: the in-toto Attestation Framework

The original link format was purpose-built for exactly one job: proving a supply-chain step happened. As the ecosystem grew, people wanted to attach other kinds of signed claims to an artifact too — an SBOM, a vulnerability scan result, a SLSA provenance record — using the same trust machinery. The in-toto Attestation Framework (specified as ITE-6, in-toto Enhancement #6) generalizes the link into a layered, extensible envelope:

LayerRole
Envelope The outermost signed wrapper (a DSSE envelope) — carries the signature(s) and the payload type, independent of what's inside.
Statement The payload: binds one or more subjects (an artifact, identified by digest) to a predicate, tagged with a predicateType URI.
Predicate The actual claim, whose shape depends entirely on predicateType — a link predicate (the original model, now just one option), a SLSA Provenance predicate, an SPDX or CycloneDX SBOM, or a VSA summarizing the result of someone else's verification.

This is why you'll see "in-toto attestation" used as a general term today, well beyond the original step-by-step layout-and-link model — it's the same signed-envelope machinery, generalized so any supply-chain tool can publish structured, verifiable claims in one common format.

Where in-toto sits next to SLSA, Sigstore, and TUF

These four names get used almost interchangeably in supply-chain-security talks, but each answers a different part of the question:

ProjectAnswersIs it software you run?
SLSA (Supply-chain Levels for Software Artifacts) "What properties should a trustworthy build process have?" — a checklist/maturity model (source integrity, isolated build, provenance) with graduated levels. No — a specification and set of requirements, not a tool.
in-toto "How do I encode, sign, and verify a claim that a specific supply-chain step happened correctly?" — the attestation format plus the layout/link toolchain that produces and checks those claims. A SLSA Provenance predicate is typically carried inside an in-toto attestation. Yes — CLI tools (in-toto-run, in-toto-verify) and libraries.
Sigstore "How do I sign things without managing long-lived keys, and how do I make signatures publicly auditable?" — keyless signing (Fulcio) backed by an OIDC identity and a public transparency log (Rekor). Yes — infrastructure often used underneath in-toto to actually sign and publish attestations (e.g. cosign attest).
TUF next deep-dive "How do clients safely fetch and trust software updates from a repository, even if some of the repository's keys are later compromised?" — a role hierarchy and trust delegation model focused specifically on the distribution/update step. Yes — a specification with reference implementations, focused downstream of where in-toto's pipeline ends.

In short: SLSA sets the bar, in-toto is how you prove you cleared it during the build pipeline, Sigstore is often the signing infrastructure underneath in-toto's attestations, and TUF picks up specifically at the "how do I trust what I'm downloading" step that comes after the pipeline in-toto just verified.

Often confused with in-toto is easy to conflate with the things it complements rather than replaces. It doesn't sign things itself the way Sigstore/cosign does — it defines what gets signed and lets you plug in any signer. It doesn't define required build properties the way SLSA does — SLSA tells you what a Level 3 build must guarantee; in-toto is how that guarantee gets recorded and checked. And unlike SPIFFE/SPIRE (previous two deep-dives), which prove the identity of a running workload right now, in-toto proves facts about a process that already finished — the build that produced the artifact you're about to run, long before it becomes a workload with an identity of its own.

Why it graduated, and where you'll meet it

in-toto joined CNCF as a Sandbox project on August 14, 2019, moved to Incubating on March 10, 2022, and reached Graduated status on February 10, 2025 (announced that April) — CNCF specifically credited it with giving organizations "verifiable and auditable" supply chains after a string of high-profile build-pipeline compromises made this problem impossible to ignore. In production you'll meet its attestation format underneath GitHub's artifact attestations and SLSA provenance generators for GitHub Actions, inside Tekton Chains (which automatically wraps Tekton pipeline runs in signed in-toto attestations), in witness (a CLI that wraps arbitrary CI steps the same way in-toto-run does), and as the attestation format package registries like PyPI use for build provenance on published packages. Datadog, Autodesk, and much of the broader Sigstore/SLSA tooling ecosystem build directly on top of it.
