Cloud Native Buildpacks

Every container you've deployed started as an image, and most of those images came from a Dockerfile someone copy-pasted, tweaked, and then forgot about. Multiply that by a few hundred services and you get hundreds of slightly different base images, build steps, and cache strategies, and every OS CVE means rebuilding all of them. Cloud Native Buildpacks (CNB, or just "Buildpacks") replace the Dockerfile with a contract. You hand your source code to a builder. Small, reusable programs called buildpacks detect what the code is ("a Node app with a lockfile"), each contributes its own image layers, and a standard lifecycle assembles a production OCI image with an SBOM attached. Because the layers are structured, the lifecycle can later swap the OS layers underneath thousands of images without rebuilding any of them. That operation is called rebase.

Where this fits The buildpack idea comes from Heroku (2011), where git push heroku main turned source into a running app with no build file, and from Cloud Foundry, which adopted it. In 2018 Heroku and Pivotal joined forces to rebuild the concept on OCI images and a written spec, and Cloud Native Buildpacks entered the CNCF Sandbox in October 2018. It moved to Incubating in November 2020. The TOC voted it Graduated on July 17, 2026, and CNCF announced the graduation on August 11, 2026. You've probably used it without knowing: mvn spring-boot:build-image, Google Cloud Run's "deploy from source," Heroku's current platform generation, and GitLab Auto DevOps all build with buildpacks.

The problem: Dockerfiles don't scale across a fleet

A Dockerfile is a script: an ordered list of instructions, each producing one layer stacked on the previous. That is simple and very flexible, and for one service it's fine. Across an organization, four things go wrong:

  • Every team re-solves the same problem. Which base image, how to install the JDK, how to cache node_modules, run as non-root, set memory flags for the JVM. Good practice spreads by copy-paste and decays the same way.
  • The cache is linear. Layer N is only reused if layers 1…N−1 were. Change something early, like a new runtime version or a patched base image, and everything after it rebuilds.
  • Patching the OS means rebuilding the world. A glibc or OpenSSL CVE in the base image requires a full rebuild, test, and push of every image built FROM it. A platform team can't do that itself. It has to chase every app team.
  • No inventory. What exactly is inside that image? Without an SBOM produced at build time, you're reverse-engineering it with a scanner afterward.

Buildpacks move image construction from "each app writes a script" to "the platform provides a builder, and the app provides only its source." That's the same shift Kubernetes made for deployment: declare what, and let a standard machine decide how.

CNB has a handful of nouns. Get them straight and the rest is mechanical.

The project is mostly a specification with two halves: the Buildpack API and the Platform API, both versioned independently. The CNCF project ships the spec, the lifecycle, the pack CLI, and libraries. The buildpacks themselves mostly come from implementations: Paketo (a Cloud Foundry Foundation project), Heroku, and Google Cloud each publish their own builders.

Anatomy of a buildpack

A buildpack is two executables, written in any language (Go and shell are common), that talk to the lifecycle through files and environment variables.

bin/detect: "is this mine?"

Runs against the source tree. Exit 0 = pass, 100 = fail (any other code is an error). On pass it can write a build plan saying what it provides and requires. The Node engine buildpack provides node; the npm-install buildpack requires node. A group passes only if every requirement is satisfied, which is how buildpacks compose without knowing each other directly. 

# written by node-engine's bin/detect to $CNB_BUILD_PLAN_PATH
[[provides]]
name = "node"

[[requires]]
name = "node"
[requires.metadata]
version = "22.*"          # from package.json "engines", .nvmrc, or BP_NODE_VERSION

bin/build: "contribute layers"

Runs in the build container with the source at /workspace and a private directory $CNB_LAYERS_DIR. Each subdirectory it creates is a layer, and a sibling <layer>.toml declares what that layer is for, using three flags: 

# /layers/paketo-buildpacks_node-engine/node.toml
[types]
launch = true    # ship it in the final image
build  = true    # expose it (PATH, env) to later buildpacks in this build
cache  = true    # keep it in the build cache for the next build

[metadata]
version = "22.11.0"   # free-form; the buildpack compares this next time to decide "reuse or rebuild"
FlagsTypical useIn the final image?
launchJRE, Node runtime, node_modules, a compiled binary's helpersYes, as its own OCI layer
build + cacheJDK, Go toolchain, ~/.m2, Go build cache, npm cacheNo. Restored for the next build only
launch + cacheRuntimes that are also needed during the next buildYes, and kept in cache

The buildpack also writes launch.toml to declare processes (web, worker, …). The lifecycle sets the image's entrypoint to its own launcher, which loads each layer's environment (PATH, JAVA_TOOL_OPTIONS, …) and then execs the chosen process. That's why a buildpack image "just works" with docker run and with a plain Pod spec without a command:. 

[[processes]]
type = "web"
command = ["node", "server.js"]
default = true

The lifecycle: analyze → detect → restore → build → export

The platform runs the lifecycle phases in order (or all at once with creator, which is what pack build does for trusted builders). An optional, still-experimental extend phase lets image extensions apply Dockerfile snippets to the base images, for the rare case where an app needs an OS package.     What to notice
    Edit app code: only the app layer is new. Every buildpack layer keeps its digest and isn't
    re-uploaded. Change dependencies: the dependency layer is rebuilt but the runtime layer is
    reused, because each buildpack decides cache validity for its own layers (by comparing lockfile
    checksums or versions in the layer metadata) instead of inheriting a linear chain. Patched run
    image + rebase: only the run-image layers change, there's no build at all, and the operation is a
    manifest rewrite in the registry. The Dockerfile column shows that a base-image change invalidates every line.
  


  
What each phase actually does

  

    
PhaseBinaryMechanism

    
      
analyzeanalyzerChecks registry access, and reads the previous image's io.buildpacks.lifecycle.metadata label: which layers it had, their digests and their .toml metadata. No image pull needed, only the config.

      
detectdetectorRuns bin/detect for the builder's order groups and resolves the build plan. Writes group.toml (the chosen buildpacks) and plan.toml.

      
restorerestorerRestores layer .toml metadata from the previous image, and the actual contents of cache=true layers from the cache (a volume or a cache image).

      
extend experimentalextenderApplies extension-generated Dockerfiles to the build (or run) base image.

      
buildbuilderRuns each chosen buildpack's bin/build in order. A buildpack that sees matching metadata (same version, same lockfile checksum) can leave a launch layer's contents empty and keep its .toml, meaning "reuse the layer from the previous image."

      
exportexporterBuilds the image: run-image layers + launcher + each launch layer + one app layer (/workspace) + config + SBOM layer. Layers whose digest matches the previous image are referenced, not re-uploaded. It also writes the cache. Timestamps are fixed to 1980 so identical inputs give byte-identical layers (reproducible builds).

Rebase: patching thousands of images without a build

  

    This is the feature that makes platform teams adopt buildpacks. An OCI image is a manifest
    listing layer digests, plus a config. With a Dockerfile, the app layers were produced by commands that ran
    on top of the base, so you can't safely swap the base out from under them. Buildpack layers are
    different. The spec requires app and buildpack layers to sit on top of the run image through a defined
    ABI-compatible
    interface. Their contents don't depend on the run image's bytes.
  

  

    So pack rebase myapp (the rebaser binary) does the following: read the image's manifest,
    drop the old run-image layer digests from the bottom, put the new run image's digests in their place, keep every
    other digest unchanged, update the config and labels, and push the new manifest. No layer is downloaded, nothing
    is executed, and nothing is uploaded except a few KB of JSON. Rebasing an image takes seconds, so a
    platform can roll a base-image CVE fix across a whole fleet in an afternoon. kpack does it automatically whenever
    a new run image appears.
  

  

    The caveat
    Rebase is only safe within an ABI-compatible line (Ubuntu 22.04 → 22.04 patched, not 22.04 → 24.04). Changing the
    OS version needs a full rebuild, which is a builder change. If an image extension modified the run image, the
    lifecycle labels it io.buildpacks.rebasable=false and refuses to rebase it.
  


  
The SBOM comes for free

  

    Each buildpack knows exactly what it installed (Node 22.11.0 from this URL with this checksum; these 412 npm
    packages), so it writes <layer>.sbom.cdx.json / .spdx.json / .syft.json
    next to its layers. The exporter collects these into a dedicated SBOM layer in the image. You can pull it with
    pack sbom download myapp and feed it to a scanner like Grype, or attach it with an attestation tool.
    This is "SBOM by construction" rather than "SBOM by scanning," which matters once supply-chain policy (see the
    in-toto and TUF deep-dives) starts asking for one.
  


  
Platforms: how you actually run it

  
pack on a laptop or in CI


pack build ghcr.io/acme/web \
  --builder paketobuildpacks/builder-jammy-base \
  --env BP_NODE_VERSION=22 \
  --publish                     # write straight to the registry, no local daemon image

pack inspect ghcr.io/acme/web   # buildpacks used, processes, run image
pack rebase  ghcr.io/acme/web   # swap in the newest run image
pack sbom download ghcr.io/acme/web -o ./sbom

  

    pack uses a Docker or Podman daemon only to run the lifecycle container. The build itself
    is not a Docker build. Per-app settings live in a project.toml (env vars, include/exclude paths,
    extra buildpacks) instead of a Dockerfile.
  


  
kpack on Kubernetes

  

    kpack (originally from Pivotal/VMware, donated to the Buildpacks community organization in 2023)
    is the Kubernetes-native platform, built as CRDs and controllers. A ClusterStore holds buildpacks, a
    ClusterStack holds the build/run images, a Builder combines them, and an
    Image resource says "keep ghcr.io/acme/web built from this Git repo." Its controller
    creates Build Pods on every new commit, rebuilds when a buildpack version changes, and
    rebases every Image when the stack's run image changes. It's continuous reconciliation of images, in the
    same way a Deployment reconciles Pods. It fits naturally upstream of Argo CD or Flux.
  


apiVersion: kpack.io/v1alpha2
kind: Image
metadata: { name: web, namespace: apps }
spec:
  tag: ghcr.io/acme/web
  serviceAccountName: registry-push
  builder: { kind: ClusterBuilder, name: default }
  source:
    git: { url: https://github.com/acme/web, revision: main }

When to reach for it, and when not

  
    
    
  • Yes: a platform team supporting many services in mainstream languages (Java, Node, Go,
      Python, .NET, Ruby, PHP) that wants consistent, secure-by-default images, SBOMs, and fleet-wide base patching.
    • 
    
  • Yes: an internal developer platform with a "push code, get a running app" experience, the
      Heroku model on Kubernetes.
    • 
    
  • Think twice: images that need unusual OS packages, custom native toolchains, or very
      specific layering. You'll spend time fighting the builder or writing your own buildpack/extension, and a
      Dockerfile may be honestly simpler.
    • 
    
  • Trade-off to accept: you give up control of the build in exchange for standardization. The
      builder is now a product someone has to own, version, and update.
    • 
  


  
Why it graduated

  

    The project's value is a stable, vendor-neutral spec that competing vendors (Heroku/Salesforce,
    VMware/Broadcom through Paketo, Google) all build on, with a lifecycle they share instead of forking. At
    graduation it had broad production use through those platforms and Spring Boot, plus end users running it
    directly with pack and kpack. It also completed a third-party security audit (Quarkslab, via OSTIF), holds an
    OpenSSF Best Practices badge, and runs a multi-vendor governance model. The stated next focus areas are OCI
    artifact handling, SBOMs and supply-chain metadata, and WebAssembly targets.
