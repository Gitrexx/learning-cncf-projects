CloudEvents

Knative Eventing's deep-dive left a forward reference dangling: every message flowing through a Broker and Trigger was described as "a CloudEvent," with a promise to come back to what that actually means. This is that spec. CloudEvents isn't a server, a controller, or anything you kubectl apply — it's a small, precise agreement about what metadata an event needs to carry so that producers, routers, and consumers who have never heard of each other can still agree on what an event is, regardless of which language, cloud, or broker moves it.

Where this fits CloudEvents is a specification, not software — the same category as SPIFFE from earlier in this landscape. It defines a small set of context attributes (metadata like id, source, type) and how to serialize and carry them over real transports (HTTP, Kafka, AMQP, MQTT, NATS, and more). It says nothing about how events get routed, retried, or stored — that's left to whatever sits on top, whether that's Knative Eventing's Broker/Trigger, Dapr's pub/sub building block, or a cloud vendor's event bus.

The problem: every system's "event" looked slightly different

Long before CloudEvents, every platform that emitted events invented its own envelope. One system called the event ID eventId, another id, another buried it inside a vendor-specific header. One put the event kind in a type field, another in eventType, another inferred it from the URL path. None of this was wrong on its own — but it meant a routing layer, a logging pipeline, or a client SDK that wanted to work across sources had to hand-write a translation for every producer it might ever see. Tooling couldn't be built once and reused, because there was no shared shape to build it against.

CloudEvents, incubated at CNCF starting in 2018 with early backing from Microsoft, Google, IBM, Red Hat, and others who all separately ran into this, fixes exactly the metadata — nothing else. It doesn't touch delivery semantics, ordering, or what the event payload looks like inside. It just guarantees that if something calls itself a CloudEvent, a handful of fields will always be named the same thing, mean the same thing, and be findable the same way — whether the event arrived over HTTP, Kafka, or an SDK call, and whether it came from AWS, Azure, GCP, or a Knative Source running on your own cluster.

The context attributes: the part every CloudEvent has in common

Every CloudEvent carries a small set of context attributes — metadata about the event, kept separate from its payload (data). Four are required, four are optional, and producers can add their own on top as extension attributes.

AttributeRequired?Meaning
id Required Identifies this event within the producer's scope. id + source together — not id alone — must be unique per distinct event, which is what lets a consumer deduplicate redelivered events.
source Required A URI-reference identifying the context the event occurred in — the "who" of the event, e.g. /orders/checkout-service or https://github.com/cncf/cloudevents.
type Required What kind of occurrence this is. Convention is reverse-DNS namespacing, e.g. com.github.pull_request.opened — this is the field routing/filtering logic keys on (Knative's Trigger filters match on exactly this).
specversion Required Which version of the CloudEvents spec this event conforms to. Currently always the string "1.0".
time Optional When the occurrence happened, as an RFC 3339 timestamp.
subject Optional The specific subject of the event within the producer's context — e.g. if source is a storage bucket, subject might be the one object key that changed. Lets a consumer filter without parsing data.
datacontenttype Optional The media type of data, per RFC 2046 (e.g. application/json) — same idea as an HTTP Content-Type, describing a payload CloudEvents itself never standardizes.
dataschema Optional A URI pointing at the schema data conforms to, so a consumer can validate or deserialize it without guessing.
Extension attributes Producers can attach any additional attribute beyond this base set — a traceparent for W3C distributed-tracing correlation, a partitionkey for a queue that needs one, or anything domain-specific. The naming rule that keeps every attribute — base or extension — mappable onto any transport's native metadata (an HTTP header, a Kafka record header) is strict: lower-case ASCII letters and digits only, no dashes or underscores, kept terse (≤ 20 characters is the convention). That single constraint is why an attribute name never needs escaping no matter which protocol binding carries it.

Event formats and content modes: how the envelope actually travels

Two separate ideas combine to get a CloudEvent onto the wire. An event format defines how to serialize the whole envelope — attributes plus data — into bytes; JSON is the default and most widely implemented format, with Avro and Protobuf formats also defined for schema-heavy or binary-native pipelines. A content mode defines how that envelope rides over a specific transport's own metadata mechanism:

Content modeHow it works
Binary Every context attribute maps onto the transport's native metadata — for HTTP, each attribute becomes a header literally named ce-<attribute> (so ce-id, ce-source, ce-type...), while data goes into the body untouched, with the ordinary Content-Type header carrying datacontenttype.
Structured The entire envelope — attributes and data together — is serialized using one event format and placed as a single blob in the body/value, with Content-Type set to that format's own media type, e.g. application/cloudevents+json.
Batched An array of full structured-mode events in one message, for transports/receivers that can usefully accept more than one event per call.

A receiver tells binary from structured mode purely by inspecting Content-Type: if it starts with application/cloudevents, treat the body as a full structured-mode envelope; otherwise, treat it as binary mode and read attributes back out of the ce-* headers. Every compliant HTTP implementation is required to support both modes. The exact same binary/structured split repeats — using each transport's own native metadata slot instead of HTTP headers — in the separate protocol binding specs for Kafka (record headers), AMQP, MQTT, NATS, and others, which is what lets one SDK call read a CloudEvent the same way regardless of which of those actually carried it.

Often confused with CloudEvents vs. Knative Eventing / Dapr pub/sub: CloudEvents is the envelope format; Knative Eventing's Broker/Trigger and Dapr's pub/sub building block (previous deep-dives) are two separate implementations that route messages shaped like CloudEvents — the same spec-vs-implementation split as SPIFFE vs. SPIRE earlier in this landscape. CloudEvents vs. a message broker (Kafka, NATS, RabbitMQ): orthogonal, not competing — CloudEvents defines what rides inside a message; the broker still owns delivery, ordering, and persistence. A broker's messages can be CloudEvents-shaped or not. CloudEvents vs. a webhook payload: most webhook payloads are bespoke JSON with no shared envelope; a CloudEvents-conformant producer is a webhook payload that any generic CloudEvents tooling can also parse, without a custom integration per source.

Why it graduated, and where you'll meet it

CloudEvents entered CNCF as a Sandbox project in 2018, moved to Incubating in October 2019, hit spec version 1.0 not long after, and reached Graduated status on January 25, 2024. What graduated is unusual for this landscape: not one reference server, but a stable spec plus a family of officially maintained SDKs (Go, Java, JavaScript/TypeScript, Python, C#, Rust, PHP, Ruby, PowerShell) and a conformance test suite, adopted independently by competing vendors — a strong signal for a format, since it means no single company controls how events are shaped. You'll meet it in two places: baked into CNCF eventing projects (Knative Eventing natively, Dapr's pub/sub building block by default), and adopted directly by public clouds as their event format of choice — AWS EventBridge, Azure Event Grid, and Google Cloud Eventarc all support CloudEvents as a first-class representation, which is what makes it realistic to write one event-handling library that works whether the event originated on your cluster or in someone else's cloud.
