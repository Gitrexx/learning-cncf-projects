Argo

Classic continuous delivery pushes: a CI pipeline builds an artifact, then runs kubectl apply or helm upgrade against your cluster using credentials the pipeline holds. That means every CI job is a standing door into production, and if someone hand-edits a live resource, nothing notices or fixes it. Argo is CNCF's answer to running Kubernetes delivery the other way around — an in-cluster controller pulls desired state from Git and continuously reconciles the cluster to match it. Argo isn't one tool; it's a family of independent controllers — Argo CD (GitOps delivery), Argo Workflows (Kubernetes-native pipelines), Argo Rollouts (progressive delivery), and Argo Events (event-driven triggers) — that graduated together as a single CNCF project in December 2022 and are commonly chained into one end-to-end delivery pipeline.

Where this fits Argo sits at the delivery layer: it doesn't build your container images (that's your CI system) and it doesn't run your cluster (that's Kubernetes). It's the layer that gets already-built artifacts and already-written manifests into a running cluster, safely and repeatably — the same conceptual slot as a Jenkins/GitHub Actions deploy job, but pull-based and Kubernetes-native instead of push-based and imperative.

Argo CD: the reconciliation loop

Argo CD runs as four components in its own namespace. The repo server clones the Git repo and renders raw Kubernetes manifests — from plain YAML, Helm charts, Kustomize overlays, or Jsonnet — without ever touching the live cluster. The application controller is the actual reconciliation engine: it diffs those rendered manifests against live cluster state (watched via the Kubernetes API) and drives sync operations. The API server is the stateless gRPC/REST front door for the CLI, UI, and webhooks, and Redis caches rendered manifests and cluster state so the controller isn't re-cloning Git and re-templating on every reconcile tick.

An Application resource ties a Git source (repo, path, revision) to a cluster destination (context + namespace). Every reconcile, the controller renders the source at its pinned revision, diffs it against live state, and reports two orthogonal status fields — this distinction trips up almost everyone the first time they see it:

  • Sync status (Synced / OutOfSync) — does live state match what's in Git, right now?
  • Health status (Healthy / Progressing / Degraded) — is the workload actually working, independent of whether it matches Git?

An app can be Synced and Degraded — correctly deployed, but crash-looping — or OutOfSync and Healthy — someone hand-edited a live resource and it's still running fine, just drifted. Health assessment is built in for common types (Deployments, StatefulSets, Ingresses) but Argo CD has no generic notion of "healthy" for an arbitrary CRD; you supply a Lua health check for anything custom.

Sync waves and hooks: ordering the apply

A raw kubectl apply -f of everything at once breaks when order matters — a Deployment referencing a ConfigMap that doesn't exist yet, or an app that needs a database migration run first. Argo CD resources can carry a argocd.argoproj.io/sync-wave annotation (an integer, default 0): the controller applies the lowest wave first, waits for those resources to report healthy, then proceeds to the next wave. Orthogonally, PreSync, Sync, and PostSync hooks attach one-off Jobs to lifecycle phases — a PreSync migration Job that must succeed before the main apply proceeds, for instance. ApplicationSet: syncing a fleet, not one app

One Application per cluster or environment doesn't scale past a handful of targets. The ApplicationSet controller generates many Application resources from a single spec, using generators: List (a static list), Cluster (one app per cluster registered with Argo CD — the standard multi-cluster fan-out), Git (one app per repo subfolder or per matching file), and Matrix (the cartesian product of two generators, e.g. every cluster × every environment overlay). One ApplicationSet YAML replaces dozens of hand-maintained Application manifests.

Argo Workflows: pipelines as Kubernetes pods

A Workflow is a set of named templates. A container template is the atomic unit — one Pod running one container. Composition templates chain them: Steps runs a sequential (or parallel-within-a-step) list, while DAG lets you declare each task's dependencies explicitly and the controller computes the parallelism and fan-out for you. Because each step really is its own Pod, steps can run wildly different container images side by side — a GPU training image next to a lightweight data-validation image — which is why Argo Workflows is the substrate under Kubeflow Pipelines: Kubeflow compiles its Python pipeline definitions down to Argo Workflow DAGs and lets the Workflows controller do the actual execution.

Data moves between steps as artifacts (staged through S3/GCS/Azure Blob between Pod runs) or small parameters. WorkflowTemplate and ClusterWorkflowTemplate make common templates reusable via templateRef instead of copy-pasting YAML, and CronWorkflow schedules Workflow creation the way a CronJob schedules Pods.

Argo Rollouts: progressive delivery

The Rollout CRD is a near drop-in replacement for Deployment — same pod template, same selector semantics — but it swaps the built-in rolling-update strategy for progressive-delivery strategies. Canary defines a sequence of steps (setWeight: 20, pause, setWeight: 50, …) that gradually shift traffic from the stable version to the new one. Blue-Green stands up a full "preview" ReplicaSet alongside the active one and cuts traffic over — manually or automatically — once it's validated.

What makes this progressive rather than just "rolling update with extra steps" is automated analysis: an AnalysisTemplate queries a metrics provider (Prometheus, Datadog, and others) at each step, and a failing threshold automatically aborts the rollout and shifts traffic back to stable — no human watching a dashboard required. Actual traffic shifting is delegated to whatever's already in the cluster — a service mesh (Istio, Linkerd), an ingress controller, or the Gateway API — via a pluggable traffic-router interface.

Argo Events: triggering the pipeline

Three CRDs cover event-driven automation: an EventSource listens for something external (a webhook, an S3 upload, a Kafka topic, a cron schedule) and normalizes it into a common event format; an EventBus — backed by NATS JetStream — carries those events; and a Sensor subscribes to events, evaluates trigger conditions (including boolean combinations of multiple events), and fires a trigger — most commonly creating an Argo Workflow, but it can equally invoke a Lambda, an HTTP call, or any Kubernetes resource.

How the family chains into one pipeline

None of the four controllers depend on each other at runtime, but they compose into a common shape: Argo Events normalizes a git push into a trigger → Argo Workflows runs the CI pipeline (build, test, push image, write the new tag to a manifest repo) → Argo CD detects that Git commit and syncs the manifest into the cluster, where it's a Rollout rather than a plain Deployment → Argo Rollouts takes over the actual canary rollout of that change, using live metrics to auto-promote or auto-abort. A newer sibling project, Kargo (from the original Argo CD/Rollouts team), fills the gap none of the four solve on their own: multi-stage promotion — dev → staging → prod — by orchestrating the Git commits that Argo CD then syncs.

Often confused with Flux is the other major CNCF-graduated GitOps toolkit and solves the same pull-based reconciliation problem as Argo CD, but as a modular set of small controllers (source, kustomize, helm, notification) with no built-in UI, versus Argo CD's centralized, UI-first application platform — covered in its own upcoming deep-dive. Tekton and Jenkins X overlap with Argo Workflows as Kubernetes-native pipeline engines, though Tekton is more CI-focused while Workflows leans general-purpose DAG execution (hence its ML/data-pipeline adoption). Flagger, from the Flux ecosystem, plays the same role as Argo Rollouts for progressive delivery.

Why it graduated, and where you'll meet it

Argo graduated on the strength of proving GitOps at production scale: pull-based reconciliation means CI systems never hold cluster-admin credentials, drift is continuously self-corrected instead of applied once and forgotten, and every change is auditable through Git history alone. You'll meet Argo CD as the dashboard platform teams point at to answer "what's actually running, and does it match Git"; Argo Workflows as the engine under CI systems and ML pipeline tools like Kubeflow; and Argo Rollouts wherever a team wants automated, metric-driven canary releases instead of a fixed-timer rolling update.
