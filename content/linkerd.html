Linkerd

Istio's pitch is breadth: one mesh, every traffic-management and security knob you could want. Linkerd starts from the opposite premise — that most of that surface area is complexity most teams never touch, and every feature you don't use is still a resource cost, an upgrade hazard, and an attack surface you're carrying anyway. Linkerd is the mesh built around doing the two things almost everyone actually wants — automatic mTLS and reliable per-route metrics — as well and as cheaply as possible, and treating everything else as optional.

Where this fits Linkerd's original version (built at Twitter's spinoff Buoyant, on the JVM using Twitter's Finagle RPC library) was the very first project the CNCF ever accepted, back in January 2017 — before "service mesh" was even a common term, and before Istio's first public release. That JVM-based Linkerd 1.x was heavy: slow startup, large memory footprint per sidecar. In 2018, Buoyant scrapped it and rewrote the project from scratch as Linkerd2, merging in a sister project called Conduit and switching the data plane to a purpose-built Rust proxy. That rewrite is the Linkerd you meet today, and on July 28, 2021 it became the first service mesh of any kind to reach CNCF graduation.

The problem: does a mesh have to be this heavy?

The Envoy and Istio deep-dives established the cost side of the sidecar model: an extra container per Pod, extra memory and CPU, extra hops for every request. Istio's answer was ambient mode — keep Envoy's full feature set, but only pay for it where you actually need L7. Linkerd's answer predates ambient mode and takes a different angle entirely: replace the general-purpose proxy with a much smaller one that was never trying to do everything Envoy does in the first place, and ship only the mesh features the vast majority of users reach for — mTLS and observability by default, traffic policy as an opt-in layer on top.

Control plane: three small, single-purpose services

Where istiod consolidated Istio's control plane into one do-everything binary, Linkerd keeps three narrowly-scoped components, each running as its own Deployment in the linkerd namespace:

  • destination — the service discovery brain. Proxies query it over gRPC to resolve a logical name into concrete endpoints, and it enriches each endpoint with the metadata a proxy needs to act on: the mTLS identity expected on the other end, zone/locality, and which authorization policy applies.
  • identity — a lightweight certificate authority. It issues short-lived TLS certificates to every meshed proxy, derived from the workload's Kubernetes ServiceAccount, and rotates them automatically.
  • proxy-injector — a mutating admission webhook, exactly like Istio's, that adds the proxy (and an init step to redirect traffic into it) to every Pod in a labeled namespace at creation time.

Notably, none of this requires a metrics backend to function. Golden-metrics collection lives in a separate, optional add-on (linkerd-viz, its own small Prometheus plus a dashboard) — the core control plane's only job is discovery, identity, and injection.

Data plane: linkerd2-proxy, a micro-proxy on purpose

Every meshed Pod gets a sidecar running linkerd2-proxy, written in Rust specifically for this one job — it is not a trimmed-down Envoy, and it was never meant to be a general-purpose proxy. It understands exactly what a mesh sidecar needs: transparent TCP proxying, HTTP/1.1, HTTP/2, and gRPC framing, and the mTLS handshake — and nothing else. That narrow scope is what keeps it small: typically single-digit megabytes of memory and negligible idle CPU per Pod, versus Envoy's much larger and more general codebase. Traffic still reaches it the same way it reaches an Envoy sidecar — iptables rules installed by an init container (or, on newer clusters, a CNI plugin) transparently redirect the Pod's traffic through the proxy with no application changes.

Automatic mTLS: no CRD required

This is Linkerd's signature difference from Istio. Istio ships mTLS as a policy you turn on — a PeerAuthentication resource with a STRICT/PERMISSIVE mode. Linkerd just does it: the moment two meshed proxies talk to each other, they opportunistically upgrade the connection to mutual TLS automatically, using certificates the identity service already issued at injection time. There's no CRD to write and no mode to pick — it's a property of being in the mesh at all. That default-on posture is a big part of why Linkerd shows up so often in security-conscious environments (finance, government, regulated industries) that want encryption-in-transit without an explicit policy for every namespace.

Golden metrics, retries, and the move to Gateway API

Because every request already flows through linkerd2-proxy, the proxy is a free vantage point for the three golden metrics any operator wants for every route: success rate, requests per second, and latency distribution (p50/p95/p99). linkerd-viz scrapes these automatically for every meshed workload — no app instrumentation required. Traffic policy sits on top as an opt-in layer: ServiceProfile was Linkerd's original way to declare per-route retries, timeouts, and a retry budget. Newer Linkerd releases are shifting that configuration onto the standard Kubernetes Gateway API (HTTPRoute) instead of Linkerd-specific CRDs, and the older SMI TrafficSplit API for weighted canary routing is deprecated in favor of weighted HTTPRoute backends — the same portable-API direction Istio is heading with its GatewayClass support.

Retries are deliberately conservative by default: Linkerd only retries a request it knows is safe to repeat, and only within the configured budget — otherwise a struggling downstream would get hit with a multiplying flood of retried traffic on top of the load that's already hurting it.

Why it graduated, and where you'll run into it

Linkerd graduated on the strength of being the mesh category's pioneer (first CNCF project, period) that also proved it could reinvent itself — the ground-up Linkerd2 rewrite is a rare example of a CNCF project throwing away its original implementation and coming back leaner instead of iterating on something structurally too heavy. In production you'll meet it where operators want mesh security and observability without a large operational learning curve or resource budget: security-sensitive platforms that want mTLS on by default, smaller platform teams that don't want to own Istio's configuration surface, and clusters where sidecar footprint (memory, CPU, startup time) is a real constraint at scale.

Often confused with Istio is the other major mesh, but the two aren't drop-in alternatives with the same feature list — Istio trades footprint for breadth (fine-grained traffic shaping, its own ambient dataplane options, deep Envoy extensibility), while Linkerd trades breadth for a smaller, simpler, security-default posture. Linkerd is not built on Envoy at all — that's the most common mix-up — it uses its own linkerd2-proxy, which is why its resource footprint looks so different. And Linkerd's mTLS is automatic and always-on for meshed traffic, whereas Istio's is a policy you configure via PeerAuthentication — same outcome, opposite defaults.
