SPIFFE

Every deep-dive so far in this section answered "is this allowed" (Falco, OPA, Kyverno) or "does this certificate stay valid" (cert-manager). SPIFFE — the Secure Production Identity Framework For Everyone — answers a question underneath all of those: how does a workload prove who it is in the first place, without embedding a shared secret (an API key, a password, a static token) that can leak, get checked into a repo, or outlive the workload it was minted for?

Where this fits SPIFFE is a standard, not software you install — think of it the way you'd think of the OCI image spec or OpenTelemetry's data model: a set of RFC-style specification documents that define what a workload identity looks like and how it's verified, so that different identity providers, service meshes, and platforms can all speak the same language. cert-manager (previous deep-dive) issues X.509 certs generically for any purpose; SPIFFE narrows the question to specifically workload identity and defines the shape that identity must take. The next deep-dive, SPIRE, is the production system that actually implements SPIFFE and hands workloads real identity documents — this one is about the shape of the problem and the format of the answer.

The problem: proving identity without a shared secret

Picture a payments service calling an inventory service inside a cluster. Before either side does anything sensitive, inventory needs to know: is this really payments calling, and not something impersonating it? The traditional answers all leave something to be desired:

  • API keys / static tokens — a secret both sides must provision, store, and rotate by hand. If it leaks, it's valid until someone notices and revokes it — which could be months.
  • IP allow-lists — in Kubernetes, Pod IPs are recycled constantly as Pods are rescheduled; an IP identifies a network location, not a workload's identity, and says nothing about whether the process behind it is really what it claims to be.
  • Bespoke per-platform identity — cloud provider A's instance-metadata identity, cloud provider B's service-account tokens, a VM's SSH host key — none of them speak to each other, so a workload that spans clouds, VMs, and containers ends up with three unrelated identity systems and no way to reason about trust between them uniformly.

SPIFFE's answer: give every workload a cryptographically verifiable identity document, issued automatically by something that already knows the workload is legitimate (a platform like Kubernetes, which already knows which Pod is running which service account), short-lived so a leaked credential expires fast, and expressed in a uniform format so any two SPIFFE-aware systems can verify each other regardless of what platform either one runs on.

The SPIFFE ID: a URI, not a name

The core primitive is the SPIFFE ID — a URI of the fixed form: 

spiffe://<trust domain>/<workload path>

The trust domain (e.g. example.org or prod.us-east.example.internal) identifies which identity provider — which root of trust — issued and vouches for this ID. Two workloads in the same trust domain can verify each other by checking the ID against one shared trust bundle; workloads in different trust domains need an explicit federation relationship before they'll trust each other at all — trust is scoped and explicit by design, never ambient.

The workload path after the trust domain is entirely up to whoever operates that trust domain — SPIFFE deliberately does not standardize it, because different platforms need different amounts of detail baked into the identity itself (a namespace and service account name on Kubernetes; a region and role name in a VM fleet). What SPIFFE does standardize is the URI shape around it, so any SPIFFE-aware verifier can always find the trust domain and treat the rest as an opaque, comparable identifier.

Why a URI and not, say, a UUID A URI keeps the trust domain human-legible and lets standard URI parsing extract it — any verifier can split on the first / after the authority and know exactly which trust bundle to check against, without needing an out-of-band lookup table mapping opaque IDs to issuers.

The SVID: an identity document, in two flavors

A SPIFFE ID is just a name — it isn't, by itself, verifiable proof of anything. The proof is the SVID (SPIFFE Verifiable Identity Document): a signed credential that binds a SPIFFE ID to a workload and lets any relying party verify it against the trust domain's public key material. SPIFFE defines two interoperable SVID formats:

FormatCarries the SPIFFE ID asTypical use
X.509-SVID a URI SAN in a standard X.509 certificate mutual TLS between workloads — the SPIFFE ID rides inside the same handshake that establishes an encrypted channel, so authentication and transport security happen in one step. This is the SVID Istio, Linkerd, and Envoy's SDS-based mTLS all consume.
JWT-SVID the sub claim of a signed JSON Web Token identity that needs to travel through layers that don't terminate TLS themselves — an API gateway forwarding a token, a message queue, a context where you want to assert identity in a request/message rather than at the connection level.

Both formats carry the same SPIFFE ID and are backed by the same trust domain — they're two encodings of one identity, chosen based on where in the stack you need to present it. Both are deliberately short-lived (X.509-SVIDs commonly rotate hourly; JWT-SVIDs are typically minutes) so that even a leaked SVID has a short shelf life, in the same spirit as cert-manager's push toward short-lived certificates in the previous deep-dive — except here the identity, not just the transport, is what's rotating.

Trust bundles and trust domains: who you believe, and about what

A trust bundle is the set of root public keys for a trust domain — hand a workload the trust bundle for prod.example.org, and it can verify any SVID claiming to be from that trust domain, without contacting anything else at verification time. Two workloads can only mutually authenticate if each holds the other's trust domain's bundle: same trust domain, automatic (they share one bundle by construction); different trust domains, only after an explicit federation relationship is configured to exchange bundles. Kubernetes namespaces give you soft, RBAC-enforced isolation within one API server; SPIFFE trust domains give you a hard cryptographic boundary that can span multiple clusters, clouds, or even organizations — a trust domain is a bigger, more deliberate unit of trust than a namespace, and typically one trust domain covers many namespaces across many clusters, not the other way around.

What SPIFFE deliberately doesn't define

A recurring theme in this section: a graduated CNCF project usually solves one layer of a problem precisely and leaves the rest to something else. SPIFFE is unusually narrow on purpose — it defines the ID format, the two SVID document formats, a workload API for fetching SVIDs, and a federation protocol for exchanging trust bundles. It does not define:

  • How to decide whether a workload deserves a given SPIFFE ID — that's attestation, entirely left to an implementation — covered in depth in the SPIRE deep-dive next.
  • How SVIDs are actually issued, stored, or rotated — again, an implementation concern. SPIRE is the reference implementation; other systems (Istio's own CA, some service mesh vendors) also issue SPIFFE-shaped SVIDs.
  • Authorization — SPIFFE proves who a workload is, not what it's allowed to do. Pairing a verified SPIFFE ID with an authorization decision is OPA/Kyverno's kind of job (or a mesh's authorization policy), layered on top.
Often confused with mTLS is a transport-security mechanism; SPIFFE is an identity format that happens to have an X.509 encoding that plugs into mTLS — Istio and Linkerd both use X.509-SVIDs under the hood for their sidecar mTLS, but SPIFFE itself says nothing about TLS handshakes. OAuth2/OIDC tokens also assert identity as signed JSON, but they're built for end-user and application-to-API authentication with human-facing flows (redirects, consent screens, long-lived refresh tokens); SPIFFE is purpose-built for workload-to-workload identity with no human in the loop and identities that rotate continuously. And as noted above, SPIFFE is a specification — for the thing that actually issues SVIDs day to day in production, see the next deep-dive, SPIRE.

Why it graduated, and where you'll meet it

SPIFFE (together with SPIRE) joined CNCF as a Sandbox project in March 2018, moved to Incubating in September 2020, and reached Graduated status in January 2022 — one of the earlier graduations, reflecting how foundational identity is to everything built on top of it. You'll meet SPIFFE IDs directly in Istio and Linkerd's mTLS certificates (both encode a SPIFFE-shaped identity in the SAN), in Envoy's SDS-based workload identity, in HashiCorp Vault and various secrets managers that accept a SPIFFE-verified identity as an authentication method, and increasingly as the identity layer platform teams reach for whenever they need workload identity that works uniformly across Kubernetes, VMs, and multiple clouds at once.
