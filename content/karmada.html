Karmada

You know how to run one Kubernetes cluster. Almost nobody runs one: there's a cluster per region, per cloud, per environment, per regulatory boundary, plus the on-prem ones and the edge ones. Each of them is its own API server, so "deploy this app to three regions, weighted by capacity, and move it if a region dies" becomes a pile of scripts and a CD tool looping over kubeconfigs. Karmada (short for Kubernetes Armada) is a control plane for your control planes. You point kubectl at it, apply a completely ordinary Deployment, and a separate policy object decides which member clusters get it, how many replicas each gets, and what to change per cluster. Karmada then keeps those clusters in line, the way a Deployment controller keeps Pods in line.

Where this fits Karmada was started at Huawei and open-sourced in 2021 with partners including Alibaba Cloud and several large Chinese enterprises. It grew directly out of experience with Kubernetes Federation (KubeFed). It joined the CNCF Sandbox in September 2021 and moved to Incubating in December 2023. CNCF voted it to Graduated on September 3, 2026 and announced it at KubeCon + CloudNativeCon China. At graduation it had 1,200+ contributors from about 290 organizations. Named production users include Bloomberg, Trip.com, Alibaba Cloud, Huawei Cloud, Wellhub, and vivo, many of them running large multi-cloud and AI-training fleets behind one Karmada control plane.

The problem: N clusters, N sources of truth

Teams run many clusters for good reasons: blast radius (a bad upgrade takes out one cluster, not the company), latency and data residency (an EU cluster for EU users and EU data), capacity and price (burst to whichever cloud has GPUs today), and scale limits (a single cluster tops out at a few thousand nodes). Kubernetes itself has no concept of "another cluster." The usual workarounds each solve part of it:

  • GitOps fan-out (an Argo CD ApplicationSet, or Flux in every cluster) gets the same manifests everywhere. It doesn't schedule. It won't split 30 replicas by free capacity, and it won't move them when a cluster fails.
  • Hand-maintained per-cluster overlays (Kustomize, Helm values per cluster) drift, and every new cluster means editing N folders.
  • KubeFed (Federation v2), the original SIG-Multicluster attempt, made you rewrite every resource as a wrapper type: FederatedDeployment containing a template, a placement, and overrides. Existing tooling, Helm charts, and CRDs didn't understand the wrappers, adoption stalled, and the project was archived in 2023.

Karmada keeps KubeFed's good idea (template + placement + overrides) and drops the bad one. The template stays a native, unmodified Kubernetes resource. Placement and overrides become separate policy objects that select resources, much as a NetworkPolicy selects Pods. Your existing Helm chart works against Karmada unchanged.

Architecture: a Kubernetes API with nothing behind it

The Karmada control plane usually runs as Pods inside an ordinary "host" cluster, but it is a separate API endpoint with its own etcd. Its API server is the real kube-apiserver binary, so it accepts Deployments, Services, ConfigMaps, and any CRD. It has no nodes and no kubelets, though. A Deployment you create there is stored and never runs. Karmada calls it a resource template. Karmada's own components turn templates into workloads in the member clusters:

Push vs. Pull membership

A member joins in one of two modes. Push (karmadactl join): Karmada holds credentials for the member's API server and its execution controller applies manifests directly. Nothing runs in the member, but the control plane must be able to reach it. Pull (karmadactl register): a karmada-agent in the member dials out to Karmada, pulls its work, and reports status. Use Pull for clusters behind NAT or firewalls, at the edge, or where you don't want a central component holding admin credentials for every cluster. The two modes can be mixed freely.

Everything after that (overrides, rendering, applying, status) is mechanical. To find out where something landed and why, look at the binding: kubectl get rb -n <ns> -o yaml.

PropagationPolicy: where, and how many

A PropagationPolicy (namespaced) or ClusterPropagationPolicy (cluster-wide, and the only kind that can select cluster-scoped resources such as ClusterRoles) has two halves: resourceSelectors (which templates; by apiVersion/kind/name/labels) and placement (where they go). The main placement fields:

  • clusterAffinity: eligible clusters by name, label, or field (provider, region, zone). clusterAffinities is an ordered list of fallback groups: use the first group that can fit the workload, and fall over to the next if it can't.
  • clusterTolerations: like Pod tolerations. Clusters carry taints (for example cluster.karmada.io/not-ready:NoExecute), and the policy says which ones it tolerates.
  • spreadConstraints: "spread across at least 2 regions and at most 3 clusters" (spreadByField: region, minGroups, maxGroups).
  • replicaScheduling, the most important one. It decides what happens to spec.replicas:
    • Duplicated: every selected cluster gets the full replica count. Typical for active-active setups where each region must stand alone.
    • Divided + Weighted, static: split the replicas by staticWeightList (for example us:2, eu:1). Remainders go to the higher-weight clusters.
    • Divided + Weighted, dynamic (dynamicWeight: AvailableReplicas): the weight is each cluster's current free capacity for this Pod shape, as reported by the scheduler-estimator, so emptier clusters get more.
    • Divided + Aggregated: pack the replicas into as few clusters as possible, largest free capacity first. Good for chatty workloads where cross-cluster traffic is expensive.
apiVersion: policy.karmada.io/v1alpha1
kind: PropagationPolicy
metadata: { name: web, namespace: shop }
spec:
  resourceSelectors:
  - { apiVersion: apps/v1, kind: Deployment, name: web }
  propagateDeps: true            # also ship the ConfigMaps/Secrets it mounts
  placement:
    clusterAffinity:
      clusterNames: [member-us, member-eu, member-ap]
    replicaScheduling:
      replicaSchedulingType: Divided
      replicaDivisionPreference: Weighted
      weightPreference:
        staticWeightList:
        - { targetCluster: { clusterNames: [member-us] }, weight: 2 }
        - { targetCluster: { clusterNames: [member-eu, member-ap] }, weight: 1 }

OverridePolicy: the same app, slightly different everywhere

Real clusters differ. Each region pulls from its own registry mirror, the EU needs a different storage class, the on-prem cluster needs a proxy env var. An OverridePolicy selects the same templates and lists overrideRules, each scoped to a set of targetClusters and carrying overriders. The overrides are applied when the binding controller renders each cluster's Work. The template in the Karmada API stays clean and identical for everyone. 

apiVersion: policy.karmada.io/v1alpha1
kind: OverridePolicy
metadata: { name: regional-registry, namespace: shop }
spec:
  resourceSelectors:
  - { apiVersion: apps/v1, kind: Deployment, name: web }
  overrideRules:
  - targetCluster: { clusterNames: [member-eu] }
    overriders:
      imageOverrider:
      - { component: Registry, operator: replace, value: europe-docker.pkg.dev/acme }

    What to notice
    With Duplicated, failover does nothing to the survivors. Each already runs the full count, and
    the failed cluster's copy is just gone. With Divided, the lost replicas are re-divided
    among the survivors under the same rule, and the template's total stays at spec.replicas. That is
    the multi-cluster version of a ReplicaSet replacing Pods from a dead node. If capacity runs out, the remainder
    can't be placed and the binding reports it as unschedulable. Real Karmada also does graceful eviction:
    the new replicas become healthy on the survivors before the old Work is purged.
  


  
Failover, in detail

  

    The cluster-status controller probes each member's /healthz (Push) or watches the agent's lease
    (Pull), and sets the Cluster's Ready condition. A not-ready cluster can then be
    tainted NoExecute. Recent releases make which conditions taint which clusters explicit and
    configurable (via ClusterTaintPolicy) instead of hard-coded, because automatic eviction across a
    whole region is a big decision. Workloads whose policy doesn't tolerate the taint are evicted: the scheduler
    re-runs for their bindings and excludes the tainted cluster, and the binding records a graceful eviction
    task so the old placement is only cleaned up once the replacements are healthy (or a timeout passes).
    Separately, application failover (spec.failover.application in the policy) moves
    a workload that is unhealthy in a healthy cluster, using the health that the resource interpreter
    reports, after a tolerationSeconds grace period.
  


  
Beyond Deployments

  
    
    
  • Resource Interpreter Framework. Karmada needs to know how to read and write replicas,
      aggregate status, judge health, and find dependencies for each kind. It ships answers for built-in kinds.
      For your CRDs (a Kubeflow PyTorchJob, a Flink job, an Argo Rollout) you supply them as Lua scripts in a
      ResourceInterpreterCustomization or as a webhook. That's how Karmada schedules arbitrary
      operators' resources, not just core types.
    • 
    
  • Status aggregation. The template's .status in Karmada is the merged status
      from all members (for example the summed readyReplicas), so kubectl rollout status
      against Karmada means something.
    • 
    
  • FederatedHPA / CronFederatedHPA. An HPA that scales the template's total
      replicas from metrics gathered across members (via karmada-metrics-adapter). The scheduler then re-divides
      the new total. Scale up in one place and it spreads across clusters.
    • 
    
  • Multi-cluster networking. MultiClusterService and the SIG-Multicluster
      ServiceExport/ServiceImport API expose a service across clusters. Pod-to-pod
      connectivity itself comes from a CNI-level mesh (Cilium ClusterMesh, Submariner) or a service mesh.
    • 
    
  • Multi-cluster AI/batch. Priority and preemption in policies, multi-component scheduling
      (a training job's launcher and workers kept together), and integration with Volcano and Kueue-style queueing.
      This is a big part of why Karmada's adoption rose with GPU scarcity.
    • 
  


  
Where you'd reach for it

  
    
    
  • Multi-region active-active: one manifest, Duplicated or Divided across regions, with
      automatic failover when a region's cluster goes dark.
    • 
    
  • Multi-cloud capacity: Divided by dynamic weight, so replicas flow to wherever there is
      room (and GPUs) right now.
    • 
    
  • Platform teams with dozens to hundreds of clusters: a single API for app teams, where the
      app team writes a Deployment and the platform's policies decide placement.
    • 
    
  • Hybrid and edge: Pull-mode agents for clusters the center can't reach directly.
    • 
  


  

    Often confused with
    Karmada vs. Argo CD / Flux: GitOps tools deliver manifests from Git. Karmada
    schedules and fails over workloads across clusters. They compose well: Argo CD syncs Git into the
    Karmada API server as if it were one cluster, and Karmada fans the workloads out.
    Karmada vs. Cluster API: Cluster API creates and upgrades the clusters (their
    machines and control planes). Karmada orchestrates workloads across clusters that already exist.
    Karmada vs. Open Cluster Management / Clusternet / Rancher Fleet: neighbors in the same space
    (hub-and-spoke cluster management with ManifestWork-style objects). Karmada's distinguishing bet is the native
    Kubernetes API for templates plus a real replica scheduler. Karmada vs. KubeFed: same goal.
    KubeFed's wrapper types are the mistake Karmada was designed to avoid.
  


  
Why it graduated

  

    The graduation case had the usual pillars. Production use at scale: Trip.com, Bloomberg, vivo,
    Alibaba Cloud, Huawei Cloud, and many others run fleets from dozens to hundreds of clusters through it.
    Broad contribution: from 500+ contributors at incubation to 1,200+ across about 290
    organizations. Governance and security maturity: a third-party security audit, a formal
    steering committee, and stable v1alpha1 policy APIs that operators have relied on for years. Underneath is a
    shift in how people run Kubernetes. "One big cluster" lost to "many clusters," and multi-cluster scheduling went
    from a niche to a platform requirement, with AI training capacity spread across clouds as the latest push.
