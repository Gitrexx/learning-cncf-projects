TiKV

etcd proved that a small, strongly-consistent Raft-backed key-value store is exactly what a control plane needs — but etcd deliberately stays small: a few MB of cluster state, one Raft group, not built to hold your application's data. TiKV asks a different question: what if you took that same "Raft-replicated key-value store" idea and built it to scale *horizontally* to terabytes of data, with real distributed transactions across keys that might live on completely different machines? TiKV is a distributed, transactional key-value database — originally built as the storage engine underneath TiDB, now a general-purpose store used on its own by systems that need horizontally-scalable ACID transactions.

Where this fits TiKV is a distributed transactional key-value database built in Rust at PingCAP, inspired by Google's Spanner (globally-distributed transactions) and Percolator (transactions layered on a distributed store), but without depending on a distributed filesystem the way Bigtable does on GFS. Data is automatically sharded into Regions, each replicated via its own independent Raft group — the same consensus algorithm etcd uses, but run as thousands of small, parallel groups instead of one. A separate Placement Driver (PD) cluster (itself Raft-replicated, and etcd-flavored in spirit) tracks where every Region lives and continuously rebalances the cluster. TiKV graduated CNCF in September 2020 — the 12th project to do so.

The problem: etcd-style consistency doesn't scale past one Raft group

Raft gives you strong consistency, but every write has to go through one leader and get acknowledged by a quorum of followers before it's committed — that's inherently a serial bottleneck for that group. etcd embraces this limit: it caps how much data it holds (multi-GB clusters are explicitly discouraged) and never needs more than one group, because control-plane state is small. A general-purpose database can't make that trade — you might have terabytes of data and need write throughput far beyond what one Raft group's leader can push through. TiKV's answer is to stop treating "the keyspace" as one thing: it's sliced into many contiguous key ranges called Regions, each around 96 MiB by default, each with its own 3-way-replicated Raft group and its own leader. A cluster with a billion keys might have tens of thousands of Regions spread across every node, each independently accepting writes through its own leader — so total write throughput scales with the number of Regions (and nodes), not with the throughput ceiling of a single Raft group.

Three roles: TiKV nodes, Placement Driver, and the client

  • TiKV nodes (stores) — each runs a local RocksDB instance holding the raw bytes for every Region replica it hosts, plus the raftstore layer that runs one Raft state machine per Region replica, batches Raft messages between nodes, and applies committed log entries into RocksDB.
  • Placement Driver (PD) — a small Raft-replicated cluster (structurally similar to an etcd cluster) that is the brain, not the data path: it hands out globally-unique, strictly-increasing timestamps (the Timestamp Oracle, TSO), stores the Region → node mapping, and constantly decides how to schedule the cluster: split a Region that's grown too large, merge two that shrank, move a replica off an overloaded node, or transfer a Region's Raft leadership to spread hot load evenly.
  • Client — talks gRPC directly to whichever TiKV node currently holds the Region's Raft leader (looking that up from PD, and caching it), so reads and writes go straight to the right node with no proxy hop in the common case.

MVCC: every key carries a timestamp

TiKV gives every logical key a whole family of physical versions rather than overwriting in place. Internally a key is stored as (user_key, timestamp) → value, ordered so all versions of a key sit next to each other, newest first. A read at timestamp T just seeks to the first version whose timestamp is ≤ T — this is what lets TiKV give a transaction a single consistent snapshot of the whole keyspace as of one timestamp, even while other transactions are concurrently writing new versions elsewhere, and it's also what makes the distributed transaction protocol below possible: a transaction can write "tentative" versions during its first phase without ever blocking or corrupting a reader's snapshot of the last committed version.

Distributed transactions: an optimized Percolator

Committing a transaction that touches keys scattered across many Regions (and therefore many different Raft groups, possibly on different nodes) needs its own coordination — Raft alone only guarantees consistency within one Region. TiKV adopts Google's Percolator model, a two-phase-commit scheme, using three logical column families:

Column familyHolds
LockWhether a key currently has an in-flight transaction's lock on it, and where to find that transaction's primary key
DefaultThe actual versioned values
WriteA record of when a key's write was committed, pointing at the version in Default

One key involved in the transaction is picked as the primary; every other key is a secondary and stores a pointer back to the primary. Commit runs in two phases:

  1. Prewrite — for every key, write its tentative value and place a lock recording the primary's location; a prewrite fails the whole transaction if it finds a conflicting lock or a newer committed version already there (first-committer-wins). TiKV parallelizes this across batches of keys rather than requiring the primary to go first.
  2. Commit — once every key prewrites successfully, the client commits the primary key first (this single write is the transaction's real commit point), then asynchronously commits the secondaries and clears their locks.

The trick that makes this safe without a lingering coordinator: if a reader runs into a lock left by an unfinished transaction, it doesn't just wait — it looks up that lock's primary key. If the primary is already committed, the transaction is known to have succeeded, so the reader (or anyone) can roll the secondary forward on the spot; if the primary was never committed, the whole transaction is rolled back the same way. No process needs to stay alive coordinating a transaction to completion — any client that stumbles onto a stale lock can resolve it.

Where you'd reach for it

  • As TiDB's storage layer — the overwhelmingly common path: you get a MySQL-compatible distributed SQL database, and TiKV is the part doing sharding, replication, and transactions underneath.
  • Directly, as a KV store — via the Rust/Go/Java/Python clients, when you want horizontally scalable storage with real multi-key ACID transactions and don't need SQL — e.g. as the backing store for another system (this is exactly how TiKV itself is used inside some other CNCF-ecosystem tools).
  • Large, growing datasets that must stay strongly consistent — where a single-leader store (like etcd) would run out of headroom, but you still can't tolerate eventual consistency.
Often confused with TiKV vs. etcd: etcd is one small Raft group meant for control-plane metadata (MBs, not TBs) with no transaction API beyond simple compare-and-swap; TiKV is many parallel Raft groups (Regions) meant to hold your actual application data at scale, with full multi-key ACID transactions on top. TiKV even uses PD, which is architecturally etcd-like, as its own coordination layer. TiKV vs. TiDB: TiDB is the SQL layer (parser, optimizer, distributed SQL execution) — it has no storage of its own and stores every row as TiKV key-value pairs; TiKV has no SQL concept at all, only keys, values, and transactions. TiKV vs. CockroachDB: architecturally close cousins (both Spanner/Percolator-inspired, both Raft-sharded), but CockroachDB bundles the SQL layer and the KV layer into one process/project, while TiKV is deliberately usable as a standalone KV store independent of any SQL engine.

Why it graduated

TiKV joined CNCF as a Sandbox project in August 2018, reached Incubating in 2019, and graduated in September 2020 as the 12th CNCF project to do so. CNCF's graduation review pointed to production adoption that had roughly doubled since joining (to about 1,000 companies) across finance, gaming, and e-commerce, an open, vendor-neutral governance model, and a design that plugged cleanly into the rest of the cloud-native stack — gRPC for its wire protocol, Prometheus for metrics, and a Kubernetes Operator for deployment — while solving a problem (horizontally-scalable, strongly-consistent transactional storage) that etcd deliberately doesn't try to solve.
