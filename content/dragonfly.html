Dragonfly

Harbor and plain Distribution registries answer "is this image allowed, and where does the canonical copy live" — but they say nothing about what happens when a Kubernetes autoscaling event, a rolling restart, or an AI training job spins up a thousand nodes at once and every single one of them tries to pull the same multi-gigabyte image or model checkpoint from that one registry in the same thirty seconds. Dragonfly is a peer-to-peer file and image distribution system: instead of every node hammering the origin, one or a few nodes fetch it once and the rest get it from each other, turning a network storm into a self-organizing swarm.

Where this fits Dragonfly was open-sourced by Alibaba in November 2017 to solve exactly this problem at Alibaba's own scale — hundreds of thousands of container pulls a day during deploys. It joined CNCF as a Sandbox project in October 2018, reached Incubating in April 2020, shipped the rearchitected Dragonfly 2.0 in 2021, and graduated on January 14, 2026 — the 36th CNCF Graduated project — backed by production use at Alibaba, Ant Group, Datadog, DiDi, and Kuaishou, and a contributor base that grew from 45 people at 5 companies to 271 people across 130+ companies since joining CNCF. It doesn't replace a registry like Harbor; it sits in front of one, accelerating the "many nodes, one origin, right now" moment that a registry alone can't solve.

The problem: a registry is one place, a fleet is thousands

A registry — even a well-run one like Harbor, backed by object storage — has finite egress bandwidth and a finite number of concurrent connections it can serve well. That's fine for steady-state traffic, but two increasingly common cloud-native events break it: a fan-out event, where an autoscaler, a canary rollout, or a cluster-wide restart asks hundreds or thousands of nodes to pull the same image inside seconds of each other; and large artifacts, where the object being pulled isn't a 100 MB web app image but a 20–100 GB AI model checkpoint that hundreds of GPU nodes need simultaneously before a training or inference job can start. In both cases every node re-downloading the same bytes from the same origin is wasted work — the bytes are already sitting on the node next to it — and the registry's bandwidth becomes the bottleneck that determines how long the whole rollout takes.

Core architecture: four roles, split control and data plane

Dragonfly v2 separates deciding who talks to whom from actually moving bytes. Four components do the work:

  • Manager — the control-plane brain: cluster configuration, which Scheduler and Seed Peer clusters belong together, RBAC, and a console UI. In Dragonfly's 2026 lightweight deployment mode it can be dropped entirely, leaving the Scheduler as the sole coordinator for smaller installs.
  • Scheduler — for every download request, picks the best parent peer(s) to download from, using a network-topology-aware algorithm, and decides when a piece isn't available anywhere yet and someone has to fetch it from the source ("back-to-source"). The Scheduler never moves file bytes itself — it only makes routing decisions over gRPC.
  • Seed Peer — a root peer with extra capacity, purpose-built to fetch from the origin registry/object-store on the Scheduler's instruction and then act as the first, most reliable source the swarm can pull from. Preheating a rollout means telling Seed Peers to fetch an image before any workload pod needs it, so the swarm is already primed when the real fan-out hits.
  • Peer (dfdaemon) — runs on every node as a daemon. It's both a downloader and an uploader: it fetches pieces (for itself or on behalf of the node) and immediately becomes a source other peers can pull those same pieces from. Clients reach it either as an HTTP/HTTPS proxy (configured as a registry mirror so containerd pulls need no changes) or directly over gRPC via the dfget client.

How a pull actually flows

A file (an image layer, a model shard) is split into pieces — small, independently verifiable chunks — and identified by a task ID derived from its content digest, the same idea as OCI content-addressing. When a node's containerd pulls an image through its configured mirror, dfdaemon intercepts the request and asks the Scheduler for a plan. If some peer in the swarm already has pieces of that task, the Scheduler routes the request to the closest one (same host > same rack > same zone) instead of the origin. If nobody has it yet, the Scheduler triggers a Seed Peer (or the requesting peer itself) to fetch from the source exactly once. The critical detail is that a peer doesn't wait to have the whole file before it starts sharing — as soon as it holds a piece, it can serve that piece to another peer, which is what lets the swarm grow piece-by-piece and node-by-node instead of one full download at a time. Bytes then move directly peer-to-peer over HTTP or Dragonfly's newer Vortex protocol — the Scheduler is never in that data path, only in the routing decision.

Preheating and AI model distribution Because the Scheduler can trigger a Seed Peer proactively, an operator (or a CI/CD pipeline) can preheat an image or model into the swarm ahead of a scheduled rollout, so the fan-out never has a cold-start moment. Since 2026 Dragonfly also speaks the native Hugging Face and ModelScope download protocols directly, so GPU clusters pulling the same model weights get the same P2P fan-out treatment images already had — the piece-splitting and topology-aware routing don't care whether the bytes are a container layer or a .safetensors shard.

What to notice In the traditional panel the origin's connection count stays pegged at your chosen limit round after round — every single node's bytes came from the origin. In the Dragonfly panel the origin is only ever touched in round 1, by the one seed peer; every other node's image came from a neighbor. Because a peer that just finished can immediately serve two more, the "nodes with image" count in the swarm roughly doubles each round instead of growing by a fixed amount — that exponential curve is why the swarm finishes in a handful of rounds even at 96 nodes, while the origin-bound approach still needs one round per batch of "origin slots" nodes.

Where you'd reach for it

  • Large fleets with synchronized pulls — big Kubernetes clusters where a deploy, a cluster-wide restart, or an autoscaling spike asks hundreds or thousands of nodes to pull the same image at once.
  • Expensive or constrained bandwidth — cross-region or cross-cloud links, or an edge/branch site with a limited backhaul, where re-pulling the same bytes over that link per-node is wasteful or slow.
  • Large AI/ML artifacts — model checkpoints and weight shards that many GPU nodes need before a training or inference job can start, where minutes of idle GPU time per node adds up fast.
  • Multi-cluster or edge fleets — nodes that would otherwise all reach back to one central registry over a long path benefit from an in-region swarm that only touches the origin once.
Often confused with Dragonfly vs. "Dragonfly" the in-memory database: DragonflyDB, a Redis/Memcached-compatible in-memory data store, is an entirely unrelated project that just happens to share the name — no relation to CNCF's Dragonfly beyond that. Dragonfly vs. BitTorrent: the epidemic, piece-sharing idea is the same lineage, but Dragonfly is purpose-built for cloud-native operations — a Kubernetes-aware Scheduler with topology-based routing, per-organization Manager/RBAC, registry-mirror integration, and preheating — rather than a public tracker-and-swarm protocol. Dragonfly vs. Harbor: Harbor decides whether an image may exist and stores the canonical copy; Dragonfly doesn't store or govern anything — it accelerates how a large fan-out of nodes actually pulls what's already in a registry like Harbor, and the two are commonly deployed together rather than as alternatives.

Why it graduated

Dragonfly's graduation case rested on the same pillars CNCF looks for at this maturity tier: years of production use at meaningful scale (Alibaba-scale image and, more recently, AI model distribution), adoption beyond its founding company (Ant Group, Datadog, DiDi, Kuaishou among the named production users), and healthy open governance — contributors grew roughly 6x (45 → 271 people) and spread across more than 130 companies since joining CNCF, with commit activity up over 3,000%. It graduated on January 14, 2026 as the 36th CNCF Graduated project, rounding out the registry-and-distribution area alongside Harbor: one project governing what may be pulled, the other making the pull itself scale.
