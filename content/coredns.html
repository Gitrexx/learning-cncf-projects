CoreDNS

Every time a Pod resolves my-service.default.svc.cluster.local to a ClusterIP, CoreDNS answered it. It's the DNS server that ships inside every conformant Kubernetes cluster — almost invisible until it breaks, at which point every Service lookup in the cluster starts failing at once. What makes it interesting isn't just that it's "the cluster's DNS": it's built as a single binary made entirely of small, chainable plugins, an architecture borrowed from the Caddy web server (same original author), and that architecture has a genuinely surprising rule about how those plugins actually run — which is the whole point of the widget below.

Where this fits CoreDNS reached CNCF Graduated status on January 24, 2019 — the first project to graduate that year, and still one of only a handful of graduated projects that almost nobody talks to directly, yet every single workload depends on. It became Kubernetes's default cluster DNS add-on with the 1.13 release (December 2018), replacing kube-dns. Look in the kube-system namespace of any cluster and you'll find it: a coredns Deployment, fronted by a Service still conventionally named kube-dns for backward compatibility, configured by a ConfigMap called coredns holding its Corefile.

The problem: kube-dns's fragile three-container pipeline

Before CoreDNS, cluster DNS was served by kube-dns, which needed three cooperating containers in a single Pod to do one job: kubedns (a SkyDNS-derived process that watched the Kubernetes API and served DNS records from that state), a bundled dnsmasq for caching and stub-domain support, and a sidecar container just to expose health checks and metrics that kubedns and dnsmasq didn't provide on their own. Three processes means three things that can disagree, and dnsmasq in particular carried a history of CVEs serious enough to force security-patch Kubernetes releases on its own. It also had a fairly rigid configuration surface: extending it (say, to handle a custom stub domain cleanly) meant patching or wrapping the binary, not editing a config file.

CoreDNS's model: a single binary, entirely made of plugins

CoreDNS collapses that into one process. Everything — serving Kubernetes-aware records, caching, forwarding to an upstream resolver, exposing metrics, health endpoints, rewriting queries — is a plugin, and a plugin chain works exactly like HTTP middleware: each plugin implements a ServeDNS method that gets a chance to look at the incoming query and can do one of three things — answer it directly and stop the chain, decline it and hand it unmodified to the next plugin, or wrap it (call the next plugin first, then inspect or modify the response on the way back before returning it further up). You only compile in the plugins you actually need, which keeps the binary and its attack surface small — a security-conscious improvement directly informed by kube-dns's dnsmasq history.

How a name resolves inside the cluster

Kubernetes gives every Service a predictable DNS name: <service>.<namespace>.svc.cluster.local resolves to an A record for that Service's ClusterIP. For a headless Service (spec.clusterIP: None) there's no single virtual IP to hand back, so CoreDNS instead returns one A record per ready backing Pod — this is exactly the mechanism StatefulSets rely on to give each replica a stable, individually addressable name. Pods can also get their own record, <pod-ip-with-dashes>.<namespace>.pod.cluster.local, and a Service's named ports get SRV records (_<port-name>._<protocol>.<service>...) so a client can discover the port number, not just the address. Every Pod's /etc/resolv.conf is configured with a search path of svc.cluster.local, cluster.local, then the node's own domains — which is why a bare curl my-service from inside a Pod in the same namespace works at all: the resolver tries the search suffixes in order until one resolves.

The Corefile — and the part that surprises people

CoreDNS is configured with a Corefile: one or more server blocks (a zone plus a port) containing a list of enabled plugin directives. This is the default kubeadm ships: 

.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
       max_concurrent 1000
    }
    cache 30
    loop
    reload
    loadbalance
}

It's natural to read that top-to-bottom as "the order things happen in." That's not how it works. The Corefile only controls which plugins are enabled and how they're configured — the actual call order is fixed by the CoreDNS binary itself, compiled in from an internal plugin.cfg file, completely independent of the order you wrote the directives in. Rearranging the Corefile's lines changes nothing about execution order; only disabling a directive (removing it) or reconfiguring one does anything.

Written in the Corefile

  1. errors
  2. health
  3. ready
  4. kubernetes
  5. prometheus
  6. forward
  7. cache
  8. loop
  9. reload
  10. loadbalance

Actually executed (per plugin.cfg)

  1. reload
  2. ready
  3. health
  4. prometheus
  5. errors
  6. loadbalance
  7. cache
  8. kubernetes
  9. loop
  10. forward
The consequence that matters Notice where cache really sits: upstream of both kubernetes and forward, not tucked away near the bottom like the Corefile suggests. That means a query that already has a live cache entry never reaches the kubernetes plugin's API lookup or the forward plugin's upstream round-trip at all — it's answered straight out of the cache, every time, until the entry's TTL (30s here) expires. Why it graduated, and where you'll meet it

CoreDNS graduated on the strength of quietly replacing a fragile, security-troubled component with a smaller, safer, and far more extensible one, at a moment where "extensible via plugins, not forks" was becoming the expected shape for cloud-native infrastructure. You'll meet it as the default DNS layer of essentially every Kubernetes cluster you touch, usually without thinking about it — until DNS latency or NXDOMAIN errors show up in an incident, at which point understanding its Corefile and real plugin order stops being trivia and starts being the fastest path to a fix. It's also used well outside Kubernetes, as a general-purpose authoritative or recursive DNS server (via plugins like file, etcd, or the cloud-provider ones) wherever its plugin model is a better fit than a traditional DNS server.

Often confused with kube-dns is CoreDNS's retired predecessor, not an alternate name for the same thing — different codebase, different (three-container) architecture, no longer maintained. external-dns runs in the opposite direction: it watches Kubernetes Ingresses and Services and writes matching records into an external provider (Route 53, Cloud DNS, etc.) so the outside world can find your cluster — it never answers a DNS query itself and has nothing to do with svc.cluster.local. NodeLocal DNSCache is an optional DaemonSet that runs an additional CoreDNS instance (just the cache plugin, mostly) on every node to sit in front of the cluster's real CoreDNS Deployment and avoid conntrack/UDP contention at very large scale — it's an add-on layer, not a replacement for the CoreDNS you've just learned about.
