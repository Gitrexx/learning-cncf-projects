SPIRE

The SPIFFE deep-dive covered the shape of a workload identity — the SPIFFE ID, the X.509-SVID and JWT-SVID formats — and pointedly left two questions unanswered: how does anything decide a workload deserves a given identity, and who actually signs and hands out the credential? SPIRE (the SPIFFE Runtime Environment) is the production system that answers both: it's the reference implementation that turns the SPIFFE spec into a running service issuing real, rotating identity documents to real workloads.

Where this fits If SPIFFE is the spec for what an identity document looks like, SPIRE is the software that decides who gets one and issues it. It does this through attestation: first attesting the node a workload runs on, then attesting the workload itself, before ever handing out a credential. No shared secret is bootstrapped by a human at any point — the platform SPIRE is embedded in (Kubernetes, AWS, GCP, bare metal) supplies the evidence.

Two servers, two attestation problems

SPIRE has exactly two components, and each solves a different half of the trust problem:

ComponentRuns whereJob
SPIRE Server Centrally, one (logical) instance per trust domain Holds the trust domain's signing authority (a root or intermediate CA), stores registration entries (the policy describing which identities exist and who qualifies), and attests nodes before trusting the agent running on them.
SPIRE Agent One per node (host, VM, or Kubernetes node) Proves its own node's identity to the server (node attestation), then locally attests workloads on that node and serves them SVIDs over the Workload API.

Splitting the two matters: a compromised node should only be able to obtain identities for workloads legitimately scheduled on that node, never mint identities for anything else in the trust domain. Node attestation draws that boundary before workload attestation ever runs.

Node attestation: the agent earns its own identity first

An agent can't vouch for workloads until the server trusts the agent itself. On startup, the agent gathers platform-specific evidence via a Node Attestor plugin and presents it to the server, which validates it with the matching server-side plugin — the check happens against the platform's own APIs, not against anything the agent can fabricate:

  • Kubernetes (k8s_psat) — the agent presents a projected service account token (PSAT) for its own Pod; the server validates it against the Kubernetes API server's TokenReview API.
  • Cloud instance identity (aws_iid, gcp_iit, azure_msi) — the agent presents a cloud-signed instance identity document; the server checks its signature against the cloud provider's public key and cross-checks the instance is actually running.
  • Join token — a one-time, out-of-band secret pre-registered with the server; the fallback for platforms with no ambient evidence to attest against (e.g. bare VMs).

Once verified, the server derives selectors for the node (e.g. which cluster, which node UID) and checks them against registration entries scoped to that agent, then issues the agent its own X.509-SVID — something like spiffe://example.org/spire/agent/k8s_psat/mycluster/<node-uid>. Every later exchange between that agent and the server happens over mTLS using this SVID.

Workload attestation: selectors and registration entries

Once the agent is trusted, workloads on its node authenticate to it for free — not with a credential, but because the kernel tells the agent who's calling. A workload connects to the Workload API socket; the agent reads the caller's process ID straight off the socket connection (SO_PEERCRED on Linux) and hands that PID to its configured Workload Attestor plugins — k8s (queries the kubelet for the owning Pod's namespace, service account, labels, and image), docker, or unix (UID/GID/binary path). Each plugin returns selectors: verified facts like k8s:ns:payments or k8s:sa:checkout-api.

Separately, an operator (or, on Kubernetes, the spire-controller-manager reconciling CRDs) has pre-created registration entries on the server — the policy layer that SPIFFE deliberately leaves undefined. Each entry says, in effect: "any workload presenting these selectors, scheduled under this agent, gets this SPIFFE ID." The agent caches the entries relevant to it and, for each Workload API call, checks whether an entry's required selectors are all present among the ones it just discovered for that process. A match mints the SVID; no match means no identity — the workload gets nothing to present, which is the SPIRE equivalent of a default-deny.

Issuance and rotation: no polling, no restarts

The Workload API isn't a request/response call a workload polls — it's a long-lived streaming gRPC call. The agent pushes an SVID down the stream immediately, then proactively pushes a replacement before the old one expires (X.509-SVIDs commonly default to a ~1 hour TTL, rotated well before that) or whenever the underlying registration entry changes. The workload never restarts, never re-authenticates, never even asks — it just always has a current SVID sitting in memory, refreshed underneath it. This is what makes short-lived credentials tolerable operationally: the rotation is invisible to the application.

Trust bundles, federation, and nested SPIRE

The server holds (or chains to) the trust domain's signing key, distributes the public trust bundle to agents over the same Workload API, and keeps it current as keys roll. Two extensions scale this beyond one server:

  • Federation — two SPIRE servers in different trust domains each publish a bundle endpoint and periodically fetch the other's bundle; once configured, workloads in each domain receive the peer's bundle through their local Workload API and can verify SVIDs from the other domain — the concrete mechanism behind the federation toggle in the SPIFFE deep-dive.
  • Nested SPIRE — a downstream SPIRE Server registers with an upstream one like any other workload and receives an intermediate CA instead of a leaf SVID, letting it sign SVIDs for its own local agents without a direct connection back to the root server for every request. Useful for multi-cluster or edge deployments where every cluster gets its own server, but all identities still chain to one trust domain's root of trust.
Often confused with A Kubernetes ServiceAccount token already proves "which ServiceAccount" to the Kubernetes API server — SPIRE's k8s_psat node attestor actually consumes one as evidence, but the SVID it produces is a portable, cross-platform identity usable far beyond the Kubernetes API, including mTLS between services and cross-cluster or cross-cloud verification. Vault's identity/secrets engine also issues short-lived credentials, but from a request Vault must authenticate first; SPIRE issues credentials proactively, streamed continuously, with no request needed once the Workload API connection is open. And remember the layering from the SPIFFE deep-dive: SPIRE decides who a workload is; it says nothing about what that workload is authorized to do — that's still OPA, Kyverno, or a mesh's authorization policy, consuming the SPIFFE ID SPIRE just proved.

Why it graduated, and where you'll meet it

SPIRE moved through CNCF's maturity levels in lockstep with SPIFFE — Sandbox in March 2018, Incubating in September 2020, Graduated in January 2022 — reflecting that the spec alone wasn't enough; the ecosystem needed a trusted, production-hardened implementation before workload identity could be treated as solved infrastructure. You'll run into SPIRE directly as Istio's pluggable CA backend (via its Envoy SDS integration), inside HashiCorp Vault and Teleport integrations that accept a SPIRE-issued SVID as an authentication method, in multi-cluster and multi-cloud platforms that need one uniform identity system spanning Kubernetes, VMs, and bare metal at once, and increasingly as the identity layer under service-to-service auth for AI agent and MCP-style systems that need workload identity beyond just human/API-key auth.
