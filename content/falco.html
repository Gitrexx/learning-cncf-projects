Falco

Everything you've studied so far in this landscape either shapes traffic (Envoy, Istio, Linkerd, Cilium) or delivers desired state (Argo, Flux, KEDA) — none of it watches what a running container is actually doing. Admission control (a topic you'll meet next, with OPA and Kyverno) can stop a Pod from ever being created with the wrong image, the wrong privileges, or a mounted host path — but once that Pod is running, nothing in the stack so far notices if a process inside it spawns a shell, reads /etc/shadow, or opens a reverse network connection to an unfamiliar host. That gap — runtime behavior, not deploy-time configuration — is what Falco closes: a CNCF-graduated engine that watches the Linux kernel's own record of what every process does and evaluates it against declarative rules in real time.

Where this fits Falco is runtime threat detection, sitting downstream of everything that decides what's allowed to exist (Kubernetes RBAC, admission policy) and catching what happens after a workload is already running — an attacker who got in through a vulnerable dependency, a supply-chain compromise, a misconfigured Pod that's now being abused. It doesn't replace a policy engine or a network policy; it's the layer that assumes those might fail and watches for the fallout, live.

The gap: security up to the container boundary, not inside it

Before Falco (created at Sysdig in 2016, donated to CNCF in 2018, graduated February 29, 2024), Kubernetes security tooling mostly stopped at the container boundary: scan the image for known CVEs, enforce that it doesn't run as root, restrict what it can mount. All of that is necessary and all of it is static — checked once, at build or deploy time. None of it tells you that, three hours after deployment, a process inside a "safe" container spawned bash with an interactive terminal, or that a Node.js web server suddenly started executing curl to download a binary into /tmp. Catching that requires watching the one source of truth no attacker can lie to: the sequence of syscalls a process actually issues to the kernel. Falco taps that stream directly.

Architecture: a kernel-level driver feeding a stateful rules engine

A Falco instance runs as a privileged DaemonSet Pod on every node and is built from a small stack of purpose-built libraries plus a pluggable capture layer:

LayerRole
driverCaptures raw syscall events from the kernel. Three interchangeable options exist (below) — Falco doesn't care which one is loaded, they all feed the same event stream upward.
libscap (System CAPture)The low-level capture backbone: talks to whichever driver is loaded, pulls events off the ring buffer, and can also read/write .scap trace files for offline replay.
libsinsp (System INSPection)Enriches raw syscalls with state Falco keeps in memory — which process, container, image, and (via a Kubernetes metadata cache) which Pod/namespace each event belongs to — and evaluates the rules engine against that enriched event.
rules engineLoads YAML rule files, compiles each condition into a filter expression, and checks every enriched event against every loaded rule, emitting an alert on a match.

The driver is the one piece with real deployment tradeoffs, so Falco ships three:

DriverHow it capturesTradeoff
kernel moduleA traditional loadable kernel module (.ko), compiled per-kernel-version.Broadest kernel compatibility, but runs code in kernel space and needs a matching build for the exact running kernel.
ebpf (classic/legacy probe)An eBPF program compiled per-kernel-version, loaded into a kernel eBPF hook.Safer than a kernel module (eBPF's verifier rejects unsafe programs) but still needs a build matching the host kernel, typically via an init container running driverkit.
modern_ebpf (CO-RE)A single pre-compiled CO-RE BPF object, portable across kernel versions with no build step.No driverkit, no kernel headers, no privileged init container — became the default driver as of Falco 0.40 for exactly that reason, requires kernel 5.8+.
Same idea, different layer than Cilium If "eBPF in the kernel" sounds familiar from the Cilium deep-dive: Cilium hooks the networking path (XDP/tc) to make forwarding decisions in-line. Falco hooks the syscall path purely to observe — it doesn't sit in the request path and by default can't block anything itself, it emits alerts. (Falco Talon, covered below, is what turns an alert into an actual response.)

Anatomy of a rule

A Falco rule is a YAML object with four parts, and the example below is a simplified version of a real rule shipped in Falco's default rule set: 

- rule: Terminal shell in container
  desc: A shell was spawned with an attached terminal inside a container.
  condition: >
    spawned_process and container
    and shell_procs and proc.tty != 0
    and not trusted_debug_containers
  output: >
    Shell spawned in container (user=%user.name shell=%proc.name
    parent=%proc.pname cmdline=%proc.cmdline container=%container.id
    image=%container.image.repository)
  priority: WARNING
  tags: [container, shell, mitre_execution]
  • condition — a boolean expression over event fields (proc.name, fd.name, evt.type, container.id, k8s.ns.name, …) using Sysdig's filter syntax. Note spawned_process, container, and shell_procs aren't primitives — they're macros, named, reusable sub-expressions (e.g. shell_procs: proc.name in (bash, sh, zsh, dash, ksh)) that keep rules readable and let a whole rule pack share one definition of "what counts as a shell."
  • output — a template string interpolating fields from the matched event (%proc.name, %container.id, …) into a human-readable alert.
  • priority — a syslog-style severity from EMERGENCY down to DEBUG, used for routing and filtering downstream.
  • tags — free-form labels, increasingly aligned to MITRE ATT&CK technique IDs, so a rule pack can be mapped straight onto a compliance or threat-coverage framework.

Lists (a named array, e.g. of trusted image names) and exceptions (a not <macro> clause referencing one) are the standard way to tune a noisy default rule without editing its core logic — you add an exception macro like trusted_debug_containers that names the images or namespaces that are legitimately allowed to spawn shells, instead of hand-editing the rule's condition every time.

Plugins: beyond syscalls

Syscalls are Falco's original and still primary event source, but not every threat surfaces there — a compromised cloud IAM credential or a suspicious Kubernetes API call (someone exec-ing into a Pod, escalating a ClusterRoleBinding) never shows up as a Linux syscall on a node. Falco's plugin framework generalizes the same rules engine to arbitrary event sources:

  • Source plugins generate a stream of events from something external — AWS CloudTrail, Okta, GitHub audit logs, or (the flagship example) the k8saudit plugin, which consumes the Kubernetes API server's own audit log via webhook or file and turns each audit entry into a Falco event with source k8s_audit.
  • Extractor plugins teach the rules engine how to pull fields (like ka.user.name or ka.target.namespace) out of that source's event payload, so rule conditions and output templates can reference them exactly like proc.name from a syscall.

The practical effect: the same declarative rule format, the same priority/tag/output model, and the same downstream alerting pipeline now cover "someone exec'd into a production Pod through the API server" alongside "a process inside that Pod spawned a reverse shell" — two different event sources, one detection engine.

From alert to action: falcosidekick and Falco Talon

Falco itself only ever emits — an alert goes to stdout, a file, or gRPC by default, and stops there. Two ecosystem projects pick it up from that point:

  • falcosidekick is a fan-out router: it receives Falco's JSON alerts and forwards them to 70+ destinations — Slack, PagerDuty, Elasticsearch, Prometheus, Kafka, cloud event buses — so an alert reaches whatever your team already watches.
  • Falco Talon is a no-code response engine: you map specific rules (by name, tag, or field match) to automated actions — kill the offending Pod, label it for quarantine, apply an isolating NetworkPolicy — so a detection can trigger real, immediate containment instead of just paging a human.

That three-stage shape — kernel-level detection → fan-out → optional automated response — is deliberate: Falco stays narrowly focused on "is this event a real match for a real rule," and lets purpose-built downstream tools own delivery and remediation.

Often confused with OPA/Kyverno (upcoming deep-dives) evaluate policy at admission time — should this Pod be allowed to be created at all — a fundamentally earlier and different question than Falco's "given this Pod is already running, is it doing something suspicious right now." You typically run both: admission policy to keep obviously bad configurations out, Falco to catch what gets through anyway. Tetragon (a Cilium sibling project) overlaps closely — also eBPF-based, also syscall-level — but leans toward in-kernel enforcement (blocking an action before it completes) and ties naturally into Cilium's existing eBPF dataplane, whereas Falco's strength is its mature, declarative rule ecosystem and broad plugin-based event sources. Sysdig is the company that created Falco and remains its largest contributor, but Falco itself has been fully open-source and CNCF-governed since its 2018 donation — Sysdig's commercial platform is a separate product built partly on top of it.

Why it graduated, and where you'll meet it

Falco graduated CNCF on February 29, 2024 — the first (and so far only) project in the "runtime security" category to reach that bar, on the strength of a mature, widely-deployed detection engine, a driver story that finally removed the "which kernel am I on" friction (modern eBPF/CO-RE), and a rule ecosystem with community packs mapped to MITRE ATT&CK for Containers, PCI-DSS, and HIPAA. You'll meet Falco anywhere a team needs to answer "would we even notice if a container got compromised right now" — intrusion detection on Kubernetes nodes, container-escape and cryptomining detection, and increasingly as the audit trail behind a compliance program, since a fired rule with a MITRE tag doubles as evidence a specific control is actually being enforced, not just documented.
