KubeVirt

Most companies running Kubernetes still have a second platform next to it: a VMware (or Hyper-V, or OpenStack) estate full of virtual machines that can't be containerized, at least not yet — a Windows app, a vendor appliance, a legacy monolith with a kernel module, a database a vendor will only support on a VM. KubeVirt deletes that second platform. It's a set of Kubernetes controllers and CRDs that let you declare a VirtualMachine the same way you declare a Deployment, and then runs that VM — a real KVM guest with its own kernel — inside an ordinary Pod, so the scheduler, the CNI, the CSI driver, RBAC, quotas, and kubectl all just work for it.

Where this fits Started at Red Hat in 2016, KubeVirt entered the CNCF Sandbox in September 2019, moved to Incubating in April 2022, and was announced as Graduated on November 10, 2026 at KubeCon + CloudNativeCon North America — ten years after its first commit. It's the engine under Red Hat OpenShift Virtualization, SUSE Harvester, and a long list of other "VMs on Kubernetes" products, with production users including ByteDance, Cloudflare, CoreWeave, and NVIDIA, and roughly 2,000+ contributors from 500+ organizations. The timing is not an accident: Broadcom's acquisition of VMware and the licensing changes that followed sent a wave of enterprises looking for an exit, and "move the VMs onto the Kubernetes platform you already run" became the most popular answer.

The problem: two platforms, two of everything

Running VMs and containers on separate stacks means two schedulers, two networking models, two storage systems, two sets of RBAC and audit, two monitoring pipelines, two on-call rotations, and two licensing bills. Worse, the VM side doesn't speak the Kubernetes API, so none of your GitOps, policy engines, or operators can touch it. Earlier attempts at convergence ran containers inside VMs (fine, but still two control planes) or bolted Kubernetes onto OpenStack. KubeVirt inverts it: Kubernetes is the only control plane, and a VM is just another workload type that it schedules.

The key design bet: don't teach the kubelet about VMs. Instead, put the hypervisor process — QEMU/KVM, managed by libvirt — inside a container in a Pod. Then the VM inherits everything Kubernetes already does for Pods: the scheduler places it, cgroups bound its resources, the CNI gives it a network, a PVC gives it a disk.

The object model

KubeVirt adds CRDs that mirror the patterns you already know:

KubeVirt objectKubernetes analogyWhat it is
VirtualMachine (VM)StatefulSet with replicas 0/1The durable, declarative definition. Has a runStrategy (Always, Halted, Manual, RerunOnFailure…) that decides whether an instance should exist. Survives stop/start.
VirtualMachineInstance (VMI)PodA running VM. Created by the VM controller when the VM should be on; deleted when it's stopped. One VMI ↔ one virt-launcher Pod.

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: legacy-app
spec:
  runStrategy: Always
  dataVolumeTemplates:              # CDI: create + populate the root disk PVC
  - metadata: { name: legacy-app-root }
    spec:
      source: { registry: { url: "docker://quay.io/containerdisks/fedora:latest" } }
      storage: { resources: { requests: { storage: 30Gi } } }
  template:                         # ← this becomes the VMI
    spec:
      domain:
        cpu: { cores: 2 }
        memory: { guest: 4Gi }
        devices:
          disks:      [ { name: root, disk: { bus: virtio } } ]
          interfaces: [ { name: default, masquerade: {} } ]
      networks: [ { name: default, pod: {} } ]
      volumes:  [ { name: root, dataVolume: { name: legacy-app-root } } ]

kubectl apply that, then virtctl console legacy-app to get a serial console, or virtctl vnc for a graphical one. kubectl get vmi shows it running on a node like any Pod.

The component chain

KubeVirt is a classic operator-style system. Following a VM from kubectl apply to a booted guest:

  1. virt-operator installs and upgrades everything else, driven by a single KubeVirt CR (which also holds cluster-wide config such as feature gates and migration defaults).
  2. virt-api serves the CRDs' validating/mutating webhooks and the subresources — console, VNC, pause, start/stop — that virtctl talks to.
  3. virt-controller (cluster-wide, leader-elected) watches VMs and creates VMIs; for each VMI it renders a virt-launcher Pod spec with the right CPU/memory requests, device requests (e.g. devices.kubevirt.io/kvm), volumes, and networks — then hands it to the normal Kubernetes scheduler.
  4. virt-handler (a DaemonSet, one per node) sees that a VMI's Pod landed on its node. It prepares node-level plumbing and talks to the virt-launcher over a local socket, telling it to define and start the domain. It also reports VMI status back and drives the node side of live migration.
  5. virt-launcher (one Pod per VM) runs a small Go supervisor plus libvirt; libvirt spawns the QEMU process that is the VM. If the guest shuts down, QEMU exits, the Pod completes, and the VMI ends.

The insight to take away The VM's resource accounting, placement, eviction, and network identity all belong to the virt-launcher Pod. That's why a VM shows up in your Pod quotas, why a node drain affects it, why Prometheus and your CNI's NetworkPolicies see it, and why you can't "just" move it — moving a running VM means moving a process with gigabytes of live memory to a different Pod on a different node. That's live migration.

Storage and networking

Disks are Kubernetes volumes. A VM disk can be a PVC (the normal case — via a DataVolume so CDI imports or clones the image into it), a containerDisk (an ephemeral disk image shipped in a container image), a cloudInitNoCloud volume for first-boot config, or ConfigMaps/Secrets exposed as disks. Whatever CSI driver backs your PVCs — Ceph via Rook, a SAN driver, Longhorn, Portworx — is your VM storage. Snapshots and clones map onto CSI snapshots.

Networking starts with the Pod network: the virt-launcher Pod gets a normal Pod IP from your CNI, and KubeVirt connects the guest's virtual NIC to it — masquerade (NAT the guest behind the Pod IP; the default, and migration-friendly) or bridge (hand the Pod's IP to the guest directly). Services, Ingress, and NetworkPolicy apply to the VM because they apply to its Pod. VMs that need to sit on an existing VLAN — the common case in a VMware migration, where VMs keep their IPs — get secondary networks via Multus (bridge, SR-IOV, OVN-Kubernetes localnet), declared as NetworkAttachmentDefinitions.

Live migration: moving a running VM

Pods are disposable — evict one and its controller makes another. VMs aren't: people expect a VM to survive a node drain or a kernel patch without rebooting. KubeVirt does this the way every hypervisor does — pre-copy live migration — but orchestrated with Kubernetes objects:

  1. A VirtualMachineInstanceMigration is created — by you (virtctl migrate), or automatically when a node is drained and the VMI's evictionStrategy is LiveMigrate (virt-api's eviction webhook turns the eviction into a migration).
  2. virt-controller creates a second virt-launcher Pod (the target) and lets the scheduler place it on another node.
  3. The source and target virt-handlers set up a migration proxy; libvirt on the source streams memory to QEMU on the target. Round 1 copies all of RAM while the guest keeps running.
  4. Every subsequent round re-sends only the pages the guest dirtied during the previous round. If the guest dirties memory slower than the network can copy it, each round is shorter than the last.
  5. When the remainder is small enough to send within the allowed downtime, the source pauses the guest, sends the last pages plus CPU/device state, and the target resumes it. Pause is typically milliseconds. The source Pod completes; the VMI's status.nodeName now points at the new node.

Requirements fall out of the mechanism: the disk must be reachable from both nodes (a ReadWriteMany PVC, or KubeVirt's newer storage live-migration to copy it), and the network binding must let the guest keep its identity (masquerade is fine; a plain pod-network bridge binding is not migratable). Tuning lives in the KubeVirt CR's migration config and in MigrationPolicy objects that select VMIs by label: bandwidthPerMigration, completionTimeoutPerGiB (how long to keep trying, scaled by VM size), allowAutoConverge, and allowPostCopy.

    What the knobs really trade
    Auto-converge keeps the guest on the source but steals CPU time from it (QEMU starts at a
    20% throttle and raises it each round) — the app slows down, but a failed network mid-migration is harmless.
    Post-copy flips the guest to the target immediately and pulls missing pages on demand when
    it touches them — it always converges, but for that window the VM's state is split across two hosts, so if
    the network or either node fails, the VM is lost. That's why both are off by default and usually enabled
    per workload via a MigrationPolicy.
  


  
Where you'd reach for it

  
    
    
  • VMware exit / consolidation — move existing VMs (often with the
      Forklift/MTV
      tooling) onto the Kubernetes platform you already operate, keeping their IPs via Multus.
    • 
    
  • Mixed applications — a containerized front end that talks to a database or vendor
      appliance that must stay a VM, now in the same namespace, behind the same Services and policies.
    • 
    
  • Non-Linux or kernel-specific workloads — Windows servers, custom kernels, or anything
      needing hardware isolation stronger than a container.
    • 
    
  • Infrastructure-as-a-service on Kubernetes — clouds and GPU providers that sell VMs
      but want one Kubernetes-based control plane underneath (GPU passthrough, vGPU, and DRA-based GPU claims
      are first-class).
    • 
    
  • Labs, CI, and edge — throwaway VMs from containerDisks for testing OS images, or
      hyperconverged edge boxes (Harvester) where one small cluster runs both.
    • 
  


  

    Often confused with
    KubeVirt vs. Kata Containers / gVisor / Firecracker: those run containers inside a
    lightweight VM (or sandbox) for isolation — you still ship an OCI image and the VM is invisible plumbing.
    KubeVirt runs a full, persistent VM with its own disk, firmware, and OS that you manage as a VM.
    KubeVirt vs. Cluster API: Cluster API creates VMs to
    become Kubernetes nodes; KubeVirt VMs are workloads (though Cluster API Provider KubeVirt
    does use KubeVirt VMs as nested cluster nodes). KubeVirt vs. OpenShift Virtualization /
    Harvester: those are products; KubeVirt is the upstream engine inside both.
  


  
Why it graduated

  

    The graduation case rested on the usual three pillars, all at real scale. Production adoption
    far beyond Red Hat — ByteDance, Cloudflare, CoreWeave, NVIDIA, plus every vendor shipping a "VMs on Kubernetes"
    product. Diverse contribution — on the order of 2,000 contributors from 500+ organizations
    including NVIDIA, Microsoft, AMD, Intel, SUSE, and Red Hat. And governance and security
    maturity — a completed third-party security audit, a formal steering committee, and the CNCF Code of
    Conduct. Behind that is the market moment: the post-Broadcom VMware migration wave turned "one platform for VMs
    and containers" from a nice idea into a budget line, and KubeVirt was the open, vendor-neutral way to do it.
