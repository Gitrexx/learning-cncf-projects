OpenTelemetry

By the mid-2010s, "observability" had a fragmentation problem: every vendor and language shipped its own tracing SDK, its own metrics client, its own wire format, and switching backends meant re-instrumenting every service by hand. OpenTelemetry (often shortened to OTel) is the industry's answer — a single, vendor-neutral specification, set of APIs/SDKs, and a standalone Collector process for generating, processing, and exporting the three telemetry signals — traces, metrics, and logs — the same way regardless of which backend eventually stores or displays them.

Where this fits OpenTelemetry formed in 2019 from the merger of two competing CNCF/Google efforts — OpenTracing (a tracing API standard) and OpenCensus (Google's combined tracing+metrics library) — under the thesis that the ecosystem needed one standard, not two. It reached CNCF Graduated status in May 2026, and by contributor and commit volume it's routinely cited as the second-most active CNCF project after Kubernetes itself — a reflection of how much of the observability industry (Datadog, Grafana, Honeycomb, New Relic, Splunk, and the cloud providers) now builds against its API and wire format instead of a proprietary one.

The problem: N languages × M backends × your own instrumentation

Before a shared standard, adding tracing to a service meant picking a vendor's SDK and sprinkling vendor-specific calls through your code. Move to a different tracing backend, or a different APM vendor, and you re-instrument everything — the SDK calls, the context-propagation glue, all of it. Worse, in a microservices system where one request crosses ten services possibly written in five languages by five teams, get any of them using an incompatible tracing library and the trace breaks at that hop — you can no longer follow one request end to end.

OpenTelemetry attacks this by separating three concerns that used to be bundled into one vendor SDK: a stable API your code calls (so instrumented code never needs to change when you change backends), an SDK that implements that API and decides how data is processed and exported, and a portable wire protocol (OTLP) plus a standalone Collector process that can receive, transform, and re-export telemetry without the application knowing or caring where it ultimately lands.

Three signals, one shared foundation

All three signals attach to the same underlying primitives so they can be correlated, not just collected side by side.

SignalUnit of dataWhat it answers
TracesSpan — a named operation with a start/end time, attributes, and a parent-child link to other spansWhat happened, across which services, in what order, and where did the time go?
MetricsData point — a number (counter, gauge, histogram) with attributes, aggregated over timeHow much / how often / how fast, in aggregate, over a window?
LogsLog record — a timestamped body plus attributes, optionally carrying a trace/span IDWhat exactly happened at this one instant, in detail?

Every piece of telemetry is tagged with a shared Resource (which process/service/Pod produced it) and uses standardized semantic conventions for attribute names, so a Go service's http.route means exactly the same thing as a Java service's. The killer feature this enables: a log line can carry the trace_id of the request it happened during, so you can jump straight from "this specific error log" to "the full distributed trace it occurred in" — something three separate, uncorrelated tools could never do.

Context propagation: how one trace survives crossing services

A trace only stays connected across a network hop if the receiving service knows which trace and which parent span it belongs to. OpenTelemetry does this with the W3C Trace Context standard: an outgoing request carries a traceparent header encoding the trace ID, the calling span's ID, and sampling flags; the receiving service's instrumentation reads that header, creates its own span as a child of the one named in the header, and forwards the (updated) header to whatever it calls next. In-process, this same information rides on a language-native Context object that auto-instrumentation threads through async boundaries so you don't have to. A companion mechanism, Baggage, lets you propagate arbitrary key-value pairs (a tenant ID, a feature flag) alongside the trace context to every downstream service, independent of what gets exported as telemetry.

Architecture: instrument once, route data through a Collector

Application code depends only on the API (a stable interface with no implementation) — this is what makes instrumented libraries portable regardless of which backend a given deployment eventually chooses. At startup, the process wires in an SDK (the concrete implementation) configured with processors and exporters, or uses auto-instrumentation (a Java agent, a Python/Node loader, or eBPF-based instrumentation) to generate telemetry for common frameworks with zero code changes. Telemetry typically doesn't go straight to a backend — it's sent over OTLP (OpenTelemetry Protocol, over gRPC or HTTP) to the OpenTelemetry Collector: a standalone, vendor-agnostic process that decouples "what my app emits" from "where it ends up."

A Collector is configured as one or more pipelines, each a chain of three component kinds:

  • Receivers — how data gets in: an OTLP receiver (the default), or receivers that scrape/pull from other systems entirely (a Prometheus-format scrape receiver, a Jaeger receiver for legacy clients), so the Collector can absorb telemetry that never spoke OTLP.
  • Processors — transform data in flight: batch (buffer and flush in bulk instead of one network call per span), attributes (insert, rename, or redact fields — a common place to strip PII or stamp deployment.environment), filter (drop telemetry matching a rule, e.g. noisy health-check spans), and memory_limiter (protect the Collector itself from an ingestion spike).
  • Exporters — how data leaves: to Jaeger, to Prometheus (remote-write or as a scrape target), to a commercial backend's OTLP endpoint, or just to stdout for debugging.

Collectors are deployed in two common shapes: as an agent (a sidecar or per-node DaemonSet, close to the workload, doing light processing) forwarding to a gateway Collector (a central deployment doing heavier processing, sampling, and fan-out to one or more backends) — or as a single Collector doing both jobs in smaller setups.

Why it graduated, and where you'll meet it

OpenTelemetry graduated on the strength of near-universal adoption as the instrumentation layer underneath the rest of observability — it doesn't compete with backends, it feeds them. Every major cloud provider and observability vendor now ships or ingests OTLP natively; language ecosystems ship official OTel SDKs; and Kubernetes-adjacent projects increasingly assume it as the default telemetry path rather than a bolt-on. You'll meet it as the Collector sitting between workloads and Prometheus/Jaeger/a vendor backend, as the auto-instrumentation agent injected by an Operator or admission webhook with zero app changes, and — directly relevant to what's next on this roadmap — as the foundation Jaeger itself now runs on: Jaeger v2 is built as a distribution of the OpenTelemetry Collector, with tracing storage as one of its exporters.

Often confused with Jaeger is a tracing backend — storage plus a UI for viewing traces; it consumes telemetry that OpenTelemetry standardizes how to generate and ship, and its current architecture is literally an OTel Collector under the hood. Prometheus owns metrics storage and PromQL; OpenTelemetry standardizes how metrics are produced and transported upstream of it — Prometheus 3.0 can ingest OTLP directly, and a Collector's Prometheus exporter can expose a scrape endpoint either way. Fluentd is a logging-specific collector with its own routing model, predating OTel's logs signal; OTel's log support is newer but adds the trace/span correlation Fluentd alone doesn't have. OpenTelemetry itself stores nothing and renders no UI — it is instrumentation and transport, not a backend.
