Envoy

Every project so far in this landscape has been about running or packaging containers. Envoy is about a different layer entirely: the network hop between one service and the next. It's a high-performance proxy written in C++ that sits next to (or in front of) an application and handles everything about talking over the network on that application's behalf — routing, load balancing, retries, timeouts, TLS, and observability — without the application knowing any of it is happening. It's the piece of infrastructure most other projects in this landscape's Networking section are actually built on top of.

Where this fits Envoy started at Lyft in 2015-2016 to solve Lyft's own microservices networking mess, joined CNCF as an incubating project in September 2017, and graduated in November 2018 — the third project ever to graduate, right after Kubernetes and Prometheus. It's not a service mesh itself; it's the universal data plane that Istio, Envoy Gateway, Contour, Gloo Edge, and several other CNCF and commercial products are all built around. Learning Envoy is learning the mechanism underneath most of the "service mesh" and "API gateway" conversations you'll run into.

The problem: every language was reinventing the network stack

Before Envoy, a company running microservices in multiple languages faced an awkward choice. Networking concerns that sound simple — retry a failed call, time out a slow one, load-balance across healthy instances, collect latency stats, encrypt the connection — all have to be implemented somewhere. The common answer was a per-language client library: Java shops used Netflix's Hystrix and Ribbon, Go shops wrote their own, and so on. That meant the same logic got built and debugged N times, behaved slightly differently in each language, and was invisible to operators unless every team instrumented it the same way.

Lyft's answer was to pull all of that out of the application entirely and run it as a separate sidecar process next to every service instance. The application talks to localhost; Envoy does the actual dialing, retrying, balancing, and encrypting to the real destination. Because Envoy is a separate out-of-process binary, it works identically no matter what language the application is written in — polyglot for free, and one place to add a feature, fix a bug, or collect a metric for every service in the fleet.

Process model: one process, worker threads, non-blocking I/O

Envoy is a single multi-threaded process. A small main thread handles configuration processing, stats aggregation, and admin duties. The actual traffic is handled by a configurable number of worker threads, each running its own non-blocking event loop (built on libevent) and each capable of independently accepting connections, running filters, and proxying bytes. There's no locking between workers on the hot path — each owns its connections outright — which is what lets Envoy push very high connection counts and low tail latencies out of a single process. Configuration changes and stats are reconciled centrally but applied to each worker's thread-local state, so a config update doesn't stall traffic already in flight.

Hot restart Because upgrading the Envoy binary or reloading certain configuration would otherwise mean dropping every open connection, Envoy supports hot restart: a new child process starts up, takes over listening sockets from the old process via shared memory and passed file descriptors, and the old process drains its existing connections before exiting. In practice most modern deployments instead just replace the Pod (rolling update) and let the mesh's connection draining handle it — but hot restart is why Envoy could be safely upgraded in place even in Lyft's original bare-VM deployments.

The request path: listener → filter chain → route → cluster → endpoint

This is the core mental model, and it's exactly what today's widget below lets you drive by hand. Every request Envoy proxies moves through the same five stages:

  1. Listener — a named network address (an IP and port) where Envoy accepts incoming connections. A single Envoy typically runs several listeners: one for inbound (:443/:8080), one for the app's own outbound calls, one for the admin interface.
  2. Filter chain — an ordered pipeline of pluggable filters each connection runs through. L3/L4 (network) filters see raw bytes/TCP; for HTTP traffic the chain typically hands off to the HTTP Connection Manager, an L7 filter that parses HTTP/1.1, HTTP/2, or HTTP/3 and runs its own nested chain of HTTP filters — auth, rate limiting, CORS, compression, whatever's configured — ending in the special router filter.
  3. Route match — the router filter looks up the request (by path, headers, authority, method — most commonly path prefix or exact match) against an ordered route table and picks the first rule that matches. Route order matters: a catch-all / rule placed first would shadow every more specific rule after it.
  4. Cluster — the matched route names a cluster: a logical group of upstream hosts that are functionally interchangeable (e.g. all healthy replicas of one backend service), along with its load balancing policy (round robin, least request, ring hash, and others), health checking, circuit breaking, and outlier detection settings.
  5. Endpoint — the cluster's load balancer picks one concrete healthy upstream host — an IP:port — and Envoy proxies the request there, applying any configured retries and timeouts along the way.

Dynamic configuration: xDS, the "universal data plane API"

Everything above — listeners, routes, clusters, endpoints — can be hardcoded in a static config file, but that's not how Envoy is used in practice at any real scale. Instead, a separate control plane computes the desired configuration and streams it to every Envoy over a family of gRPC APIs collectively called xDS ("x" Discovery Service — x stands in for whichever resource type):

APIDiscovers
LDS — Listener Discovery Servicewhich listeners and filter chains to run
RDS — Route Discovery Servicethe route table a listener's HTTP Connection Manager should use
CDS — Cluster Discovery Servicewhich upstream clusters exist and their policy
EDS — Endpoint Discovery Servicethe live, healthy member list of each cluster
SDS — Secret Discovery ServiceTLS certificates and keys, rotated without a restart

In practice these are usually all multiplexed over one stream as ADS (Aggregated Discovery Service), so ordering between resource types stays consistent. Envoy calls xDS the "universal data plane API" deliberately: because it's a standard, wire-level protocol rather than an Envoy-internal implementation detail, any control plane can drive any Envoy. That's the whole reason Istio's istiod, Envoy Gateway, Contour, Gloo Edge, and Kuma can all exist as separate projects with different opinions about what configuration to compute, while all of them reuse the exact same Envoy binary as the thing that actually moves bytes. It's also why xDS has grown beyond Envoy itself — other proxies and even "proxyless" gRPC clients now speak xDS directly.

Observability is not bolted on

Because every byte already flows through Envoy, it's a natural place to generate telemetry without any application code changes:

  • Stats — deep, per-cluster, per-listener counters and histograms (request counts, upstream/downstream latency, connection pool state, circuit breaker trips) exposed on the admin interface and scraped by Prometheus.
  • Distributed tracing — Envoy generates and propagates trace headers (compatible with OpenTelemetry, Zipkin, and others) so a request's hop through the mesh shows up as spans, even though the application itself never wrote tracing code.
  • Access logs — structured, configurable per-request logs, useful independent of a full tracing backend.

This is a big part of why "adopt a service mesh" and "get uniform golden-signal metrics for free" tend to be the same conversation — the mesh is just many Envoys, and the metrics come from Envoy, not from instrumenting every service by hand.

Why it graduated, and where you'll run into it

Envoy graduated CNCF in November 2018 on the strength of production adoption well beyond Lyft — it was already running at scale inside companies building their own infrastructure around it. Today you'll meet Envoy in three overlapping shapes:

  • As a sidecar in a service mesh — Istio's data plane is literally an Envoy container injected into every meshed Pod.
  • As an edge/ingress gateway — Envoy Gateway, Contour, and Gloo Edge all use Envoy as the actual proxy behind a Kubernetes-friendly control plane (Envoy Gateway specifically implements the Kubernetes Gateway API).
  • Embedded directly — some platforms and API gateways use the Envoy binary or its filter framework directly rather than through one of the above.
Often confused with Istio is not a competitor to Envoy — it's a control plane for Envoy; Istio's data plane is Envoy. NGINX and HAProxy are older, well-proven proxies, but they were designed around static or file-reloaded configuration and don't have xDS-style dynamic, incremental, streamed config as a first-class citizen — that gap is exactly what made Envoy the default choice for environments where the fleet of upstream endpoints changes constantly (i.e. Kubernetes). Envoy Gateway is not a fork of Envoy or a different proxy — it's a Kubernetes-native control plane, packaged as its own CNCF project, that generates xDS config and runs the standard Envoy binary underneath.
