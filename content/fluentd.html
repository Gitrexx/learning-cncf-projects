Fluentd

A single request might leave a trail across an nginx access log, an application's JSON stdout, a database's slow-query log, and a kernel audit log — each in a different format, on a different host, rotated on a different schedule. Before Fluentd, "collect all the logs somewhere useful" meant a pile of bespoke tail-and-grep scripts, format-specific shippers, and fragile pipelines glued together per data source. Born at Treasure Data in 2011 and CNCF's third graduated project (2019, right after Kubernetes and Prometheus), Fluentd made log collection a single, pluggable, configurable layer: one process that can read from almost anything, reshape records uniformly, and route them to almost anywhere.

Where this fits Fluentd is the unified logging layer: it doesn't generate logs (your application, nginx, and the kernel do that), and it isn't a place logs live long-term (that's Elasticsearch, S3, a data warehouse, or a log-analysis SaaS). It sits in between — collecting, parsing, enriching, buffering, and routing — the same conceptual slot that OpenTelemetry's Collector occupies for traces and metrics, but Fluentd predates OTel by a decade and today is most often deployed as a per-node log shipper in a Kubernetes cluster, typically as a DaemonSet reading each node's container log files.

The plugin pipeline: input → parser → filter → buffer → output

Every Fluentd deployment is a chain of five plugin types, each independently swappable:

  • Input plugins (source directives) get data in — tailing a file, listening on a TCP/HTTP port for the forward protocol, subscribing to syslog, reading from a container runtime's log driver. Over 500 plugins exist across all five categories, covering nearly any source or destination you'd want.
  • Parser plugins turn a raw line into a structured record — regex, JSON, CSV, the standard Apache/nginx combined log format, or a custom grok-style pattern. This is what turns an opaque string into queryable fields.
  • Filter plugins transform records already in flight — adding fields (hostname, environment, Kubernetes pod metadata via kubernetes_metadata), dropping records that match a pattern (grep), masking sensitive fields, or re-parsing a nested string field.
  • Buffer plugins hold records before they're written out — in memory for low latency, or on disk (file buffer) so a crash or a downstream outage doesn't lose data already accepted.
  • Output plugins (match directives) write records out — Elasticsearch, Kafka, S3, BigQuery, another Fluentd/Fluent Bit forwarder, or just stdout for debugging.

Tag-based routing: the config model that ties it together

Every record Fluentd handles carries a tag — a dot-delimited string like app.checkout.access — assigned by whichever source ingested it (often via a tag parameter naming the plugin and file). Routing is then just pattern matching: a <match app.**> block catches every tag starting with app., a more specific <match app.checkout.*> wins for that exact prefix, and <filter app.**> blocks apply transformations to matching records as they pass through — all without touching the record's actual content, the same way Kubernetes Services route by label selector rather than by inspecting pod internals. A minimal config reads almost like a short program: 

<source>
  @type tail
  path /var/log/app/*.log
  tag app.checkout
  <parse>
    @type json
  </parse>
</source>

<filter app.**>
  @type record_transformer
  <record>
    hostname "#{Socket.gethostname}"
  </record>
</filter>

<match app.**>
  @type elasticsearch
  host es.internal
  <buffer>
    @type file
    path /var/log/fluentd-buffer
  </buffer>
</match>

Buffering and delivery guarantees

Fluentd batches records into chunks before an output plugin flushes them, and chunks accumulate in a buffer — either in memory (fast, but lost on a crash) or on disk via the file buffer (survives a restart, at the cost of I/O). If a flush fails — the Elasticsearch cluster is down, a network blip — Fluentd retries with exponential backoff rather than dropping the chunk, which is what gives Fluentd pipelines their at-least-once delivery characteristic: a record can be delivered more than once during a retry, but a transient downstream outage shouldn't silently lose logs. This is the same buffer-and-retry shape you'd recognize from a Kafka producer or an OpenTelemetry Collector's queued exporter — decoupling "accept the record" from "successfully deliver the record" is what makes any of these pipelines resilient to a flaky downstream.

Fluentd vs. Fluent Bit

Fluentd is written in C for its core with plugins in Ruby, which makes it flexible and plugin-rich (500+ plugins) but heavier — tens of MB of memory at rest. Fluent Bit is a separate CNCF graduated project: a from-scratch reimplementation in pure C, with a much smaller plugin set and a memory footprint in the single-digit MBs, purpose-built to run as a DaemonSet on every node without denting the node's resources. The common production pattern pairs them: Fluent Bit at the edge (one per node, forwarding via the Fluentd forward protocol) feeding a smaller number of Fluentd instances doing aggregation — heavier parsing, enrichment, and fan-out to multiple backends — so the expensive plugin ecosystem only runs where resource cost is amortized across many nodes' worth of logs.

Why it graduated, and where you'll meet it

Fluentd graduated on the strength of being the neutral, vendor-agnostic answer to "how do logs get from everywhere to anywhere" at a time when every logging vendor wanted to own the collection agent too. Its plugin architecture meant switching log backends — Elasticsearch to S3 to a SaaS vendor — was a config change, not a re-instrumentation project. You'll meet Fluentd (or its sibling Fluent Bit) as the log-shipping DaemonSet in nearly every Kubernetes logging stack — EFK (Elasticsearch-Fluentd-Kibana) is the direct descendant of the classic ELK stack with Fluentd in Logstash's seat — and as the default log forwarder bundled by most managed Kubernetes log-collection add-ons.

Often confused with Fluent Bit is Fluentd's lightweight sibling project (see above) — not a competitor, and the two are commonly deployed together. Logstash (part of the Elastic Stack) plays a similar collect-transform-route role but is Elastic-owned, JVM-based, and tightly coupled to the Elasticsearch ecosystem, versus Fluentd's vendor-neutral, CNCF-hosted plugin model. The OpenTelemetry Collector can also collect and route logs (via its own receiver/processor/exporter pipeline, covered in the OpenTelemetry deep-dive) and is increasingly overlapping with Fluentd's territory as OTel unifies all three signal types — but Fluentd remains the more battle-tested, plugin-rich choice specifically for logs today.
