Jaeger

A single user click on "Checkout" can fan out into a dozen network calls across a dozen services — an API gateway, an auth check, a catalog lookup, a payment charge, a database query, an event publish. When that request is slow, or fails, which of those dozen hops was the problem? Distributed tracing answers that by following one request as it crosses every service boundary, and Jaeger is the CNCF project that made distributed tracing practical at scale: born at Uber to debug exactly this fan-out problem in their microservices fleet, open-sourced in 2017, and CNCF Graduated in 2019.

Where this fits Jaeger is a tracing backend — it stores traces and gives you a UI and query API to explore them. It doesn't generate telemetry itself; that's the job of instrumentation (today, almost always OpenTelemetry SDKs). In fact, as of Jaeger v2 (the current architecture), Jaeger is no longer a separate codebase from OpenTelemetry at all — it's built as a purpose-configured distribution of the OpenTelemetry Collector, with Jaeger's storage and query layer wired in as Collector components. If you've read the OpenTelemetry deep-dive, you already know most of the pipeline; this page is about what happens to trace data once it lands, and how to actually read a trace.

What a trace actually is

A trace is not a single record — it's a tree of spans, each one representing a single unit of work (an HTTP handler, a database query, a function call). Every span carries the same trace_id (shared by every span in the request), its own span_id, and a parent_span_id pointing at whichever span caused it to start. That parent/child chain — propagated across network hops via the W3C traceparent header, as covered in the OpenTelemetry page — is what lets a tracing backend reassemble "gateway called auth, which returned, then gateway called payment, which called a database" purely from independently-reported spans, with no central coordinator involved while the request is in flight.

Each span also records a start time and duration, a service name and operation name, key-value tags (http.route, db.statement, an HTTP status code), and optionally timestamped logs within the span (a retry, an exception). Stack all of a trace's spans up against a shared time axis, indented by parent/child depth, and you get the classic waterfall view — the primary way anyone reads a trace.

Architecture: from agents-and-collectors to an OTel Collector distribution

Jaeger's original (v1) architecture split the pipeline into dedicated processes: a Jaeger Agent as a per-host sidecar batching spans from local processes, a Jaeger Collector receiving those batches, validating and indexing them, and writing to a storage backend (Cassandra or Elasticsearch for production scale, or an in-memory/Badger store for local use), and a Query service + UI reading that storage back out for the web console.

Jaeger v2 collapses this into the OpenTelemetry Collector's own receiver/processor/exporter model: a jaeger receiver still accepts spans from legacy Jaeger clients, but the default path is the same OTLP ingestion OpenTelemetry SDKs already speak; Jaeger's storage layer ships as an exporter (jaeger_storage, backed by the same Cassandra/Elasticsearch/Badger options); and the Query service and UI run alongside as an extension of the same binary. Practically, this means "run Jaeger" today largely means "run a Collector configured with Jaeger's storage exporter" — one less system to reason about, and direct interoperability with every other OTel-speaking tool in your pipeline.

Sampling: you can't keep everything

At real traffic volumes, recording and storing every span of every request is prohibitively expensive, so tracing systems sample — deciding which traces are worth keeping in full.

  • Head-based sampling decides at the very start of a trace, usually probabilistically (e.g. keep 1% of requests) or via rate limiting, before anyone knows whether the request will be slow or fail. Cheap and simple, but you might sample away exactly the slow, erroring trace you'd want to investigate.
  • Tail-based sampling buffers all of a trace's spans until the trace finishes, then decides — keep it if it errored, keep it if it was unusually slow, sample the rest normally. This needs a buffering layer (typically a Collector tier) that can see a trace's full span set before deciding, which costs more memory but keeps the traces you actually need.
  • Jaeger also supports adaptive sampling, where the Collector adjusts per-service, per-operation sampling probabilities over time to hit a target volume rather than using one fixed rate everywhere.

What to notice Switch to the "Slow checkout" trace and click "Reveal bottleneck." The payment-service span looks like the slow one at a glance — it spans 330 of the trace's 420ms. But its own work is quick; almost all of that time is really its child, the payment-db span, running an unindexed query (db.rows_examined in the tags jumps from a dozen rows in the fast trace to nearly half a million in the slow one). That distinction — a wide bar in the waterfall versus the span whose self time actually accounts for it — is the whole reason engineers reach for a trace instead of a dashboard: an aggregate latency metric tells you the checkout endpoint got slow; the trace tells you exactly which query, on which service, at which parent call, did it.

Why it graduated, and where you'll meet it

Jaeger graduated on the strength of being the reference open-source distributed tracing backend at a time when every organization running microservices on Kubernetes hit the same wall: metrics tell you that something is slow, logs tell you what happened on one host, but only a trace tells you where in a multi-service call chain the time or the failure actually occurred. You'll meet Jaeger as the tracing backend behind an OpenTelemetry Collector's exporter list, as the UI engineers open after a Prometheus alert fires to find the slow hop, and increasingly bundled as the default tracing store in service-mesh observability add-ons (Istio and Linkerd both ship Jaeger integration out of the box).

Often confused with OpenTelemetry generates and transports traces (the API, SDKs, and Collector); Jaeger stores them and gives you a UI to read them — and, per above, Jaeger v2 is literally built on the OTel Collector, so the line between "instrumentation" and "backend" is now mostly about which components you enable. Zipkin is an older, still-maintained tracing backend with a similar span model and its own wire format (predating OTLP) — Jaeger can ingest Zipkin-format spans, but the two are separate projects with separate storage and UIs. Prometheus owns metrics and aggregate time-series, not per-request causality — a Prometheus alert on p99 latency is what tells you to go open Jaeger, not a replacement for it. And a trace is not a log: a log line tells you what happened at one instant on one host; a trace tells you the shape and timing of an entire multi-service call.
