CubeFS

Rook's answer to "who runs the storage layer" was: wrap Ceph, a system where block, file, and object are three client APIs over one shared object store (RADOS). CubeFS starts from a different design question entirely — one JD.com actually had at exabyte scale: can metadata and data be split into two independently-scaling clusters, so that browsing a directory with a million files never waits on a slow disk, and a hot dataset can automatically cool from replicated storage into cheaper erasure-coded storage without the application noticing? CubeFS is a distributed storage system built around exactly that separation, exposed through POSIX, HDFS, and S3 APIs over the same underlying data.

Where this fits CubeFS is a cloud-native distributed file and object storage system, born inside JD.com (China's second-largest e-commerce company) to run its own storage at exabyte scale, open-sourced in 2019. Its defining architectural move is a hard split between a metadata subsystem (who owns which inode, what's in a directory) and a data subsystem (the actual bytes) — each its own cluster of nodes, scaled and tuned independently. Data itself can live in one of two storage engines: multi-replica for hot, latency-sensitive workloads, or Reed-Solomon erasure coding (via a subsystem called Blobstore) for cold data at a fraction of the storage cost.

The problem: metadata and data don't scale the same way

A single POSIX filesystem namespace with billions of files has two very different bottlenecks. Metadata operations — stat, readdir, creating a file, renaming — are small, latency-critical, and need to be strongly consistent: two clients renaming the same file can't both "win." Data operations are the opposite: they're about raw throughput moving potentially huge, sequential byte streams, and they tolerate more relaxed placement. Traditional network filesystems (and, in a different way, even Rook/Ceph's RADOS layer) treat data placement as the one hard problem and let metadata ride along inside the same object model. CubeFS instead treats metadata as a first-class, separately-scaled service — the bet being that at JD.com's scale (hundreds of petabytes, later growing past an exabyte, across 200+ adopting companies today), keeping the entire live metadata working set in memory across a dedicated fleet is what keeps a billion-file namespace fast, while data nodes are free to scale out purely for capacity and throughput.

Three subsystems, three clusters

A CubeFS deployment is three independently-scaled clusters of daemons, all coordinated through Raft:

  • Resource Management (Master) — a small cluster of Master nodes that owns cluster-wide bookkeeping: creating and tracking volumes, allocating new metadata and data partitions, health-checking every MetaNode and DataNode, and rebalancing. Masters replicate their own state via Raft and persist it to RocksDB; only the Raft leader serves writes.
  • Metadata Subsystem (MetaNode) — a fleet of MetaNode processes, each hosting many Meta Partitions: a Meta Partition owns a contiguous range of inode IDs and keeps that range's inode B-tree (file attributes) and dentry B-tree (directory entries, i.e. name → inode mappings) entirely in memory for speed, checkpointed to disk. Each Meta Partition is itself replicated across 3 MetaNodes via Raft (CubeFS calls this Multi-Raft — many small, independent Raft groups running concurrently rather than one big one) — so a namespace with a huge inode count isn't one bottlenecked shard, it's however many partitions the Master has split it into, each with its own leader and its own quorum.
  • Data Subsystem (DataNode / BlobNode) — where bytes actually live, in one of two engines described below.

Two data engines: replicate hot, erasure-code cold

This is CubeFS's other defining idea: data storage isn't one-size-fits-all, and the two engines can be used side by side, even for the same volume as data ages.

EngineUnitRedundancyOptimized for
Replica subsystem (DataNode)Data Partition, replicated across a set of DataNodes2 or 3 full copiesHot data — low latency, high throughput, cheap recovery (just copy)
Erasure-code subsystem (Blobstore / BlobNode)a stripe of fixed-size blocks across BlobNodesReed-Solomon N data + M parity shardsCold data — same durability at a fraction of the raw storage cost, at the price of costlier recovery

A volume can be configured to store data purely as replicas, purely as erasure-coded blobs, or — the common production pattern — start as replicas while data is hot and being actively written/read, then let a background migration process demote cold, rarely-touched data into Blobstore once it stops being hot, reclaiming most of that 3x replication overhead automatically instead of the application ever managing tiers itself.

Multi-protocol: the same bytes, three doors in

Unlike a storage system that's "S3-native" or "POSIX-native" and treats the others as bolt-on gateways, CubeFS was designed so POSIX, HDFS, and S3 clients can address the same underlying volume — a file written via a mounted POSIX client can be listed and read back through the S3-compatible object API, and vice versa. In practice:

  • POSIX — via FUSE (cubefs-client) or a kernel bypass client, mounted like any local filesystem; the path most application code takes with zero changes.
  • HDFS-compatible — implements the Hadoop FileSystem interface, so existing big-data jobs (Spark, Hive, Flink) can point at CubeFS instead of a real HDFS cluster with no code change, while gaining separated compute/storage scaling.
  • S3-compatible — an object gateway speaking the AWS S3 API, so tools built against S3 SDKs work unmodified.

This is a big part of why CubeFS shows up under both "big data" and "AI/ML" workloads: a training pipeline can read a dataset over the POSIX mount for maximum throughput while a separate analytics job queries the exact same data over S3, with no export/copy step between them.

Try it: trace a file write through the cluster

Pick a data engine, then write a file and watch it move through the three subsystems. In replica mode, the file's bytes land as full copies on a handful of DataNodes. In erasure-coded mode, they're striped into data shards plus parity shards spread across BlobNodes — any single shard can be lost and reconstructed from the rest.

What to notice The Master is only ever consulted to locate or allocate partitions — it never sees the file's bytes. Metadata (the inode + the directory entry) is written and Raft-committed on the MetaNode fleet completely independently of where the data itself ends up, which is exactly the separation this whole architecture is built around. And notice erasure coding doesn't reduce durability versus 3x replication — a 4+2 stripe also tolerates 2 losses — it just does it in 1.5x the original size instead of 3x.

Where you'd reach for it

  • Big-data platforms replacing HDFS — get HDFS API compatibility with separated compute/storage scaling and erasure-coded cold tiers, without re-architecting Spark/Hive/Flink jobs.
  • AI/ML training and model storage — high-throughput POSIX access to large datasets and checkpoints, with the same data also reachable over S3 for other tooling.
  • Kubernetes-native shared storage at large scale — a CSI driver exposes CubeFS volumes as ReadWriteMany PVs, useful anywhere many Pods need to share a filesystem across a large, cost-sensitive dataset.
  • Database/middleware storage-compute separation — using CubeFS as the durable backing store so stateless compute nodes can be scaled or replaced independently.
Often confused with CubeFS vs. Rook/Ceph: both are self-hosted, self-healing distributed storage for Kubernetes, but Ceph's RADOS is one object store underneath block/file/object clients, while CubeFS explicitly separates metadata (MetaNode/Raft) from data (DataNode or Blobstore) as different clusters, and leads with HDFS/S3/POSIX multi-protocol access to the same volume rather than three separate client APIs. CubeFS vs. HDFS: CubeFS's HDFS compatibility layer is a drop-in replacement, but under the hood it isn't Java/JVM-based, separates metadata differently (no single active NameNode to fail over), and adds erasure coding and S3/POSIX access HDFS doesn't natively have. CubeFS vs. MinIO: MinIO is S3-object-storage-only; CubeFS's S3 API is one of three doors into the same POSIX-capable filesystem, useful when you need both a real mountable filesystem and object access to the same data.

Why it graduated

CubeFS entered CNCF as a Sandbox project in 2020, reached Incubating in mid-2022, and graduated in January 2025 — CNCF's announcement cited over 200 adopting organizations managing roughly 350 petabytes of data in production, spanning e-commerce (its JD.com origin), fintech, telecom, and AI/big-data platforms. Its graduation reflects a storage architecture proven at genuinely exabyte-adjacent scale before it was ever open-sourced, plus a design — separated metadata/data scaling, dual hot/cold storage engines, and true multi-protocol access — that answers problems Ceph-based storage doesn't optimize for as directly: huge flat namespaces and mixed big-data/AI access patterns over the same dataset.
