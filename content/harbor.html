Harbor

containerd pulls images from a registry over the OCI distribution API — but the spec only defines how bytes move, not who is allowed to push them, whether they're safe to run, or what happens when the same image needs to exist in ten datacenters. Harbor is that missing layer: an open-source enterprise container registry that wraps a plain OCI-conformant registry with project-based access control, automated vulnerability scanning, artifact signing, and replication — turning "a place images live" into "a place images are governed."

Where this fits Harbor is not a registry implementation written from scratch — under the hood it runs the same open-source Distribution registry that Docker Hub and most other registries are built on, for the actual blob storage and the push/pull wire protocol. Harbor's job is everything *around* that: a control-plane API and UI, a Postgres database of projects/users/policies/scan-results, a job queue for async work (scanning, replication, garbage collection), and a pluggable scanner (Trivy by default). It graduated CNCF on June 15, 2020, the 11th project to do so, after originating at VMware in 2016 to solve exactly this gap for enterprises running Kubernetes on-prem or across clouds who couldn't just point every cluster at a public registry.

The problem: a registry that only stores bytes isn't enough

Docker Hub and the plain Distribution registry solve a narrow problem well: given an image name and tag, store its layers content-addressably and serve them back fast. That's sufficient for a single team pushing to a single namespace, but it breaks down the moment an organization needs answers to questions the distribution spec was never designed to answer: Which teams can push to which repositories? Does this image contain a critical CVE, and should that block deployment? Is this really the image our CI pipeline built, or did someone tamper with it in transit? How do we keep a copy of these images in three regions without every cluster hammering one central registry on every pull? Each answer requires state and policy that has nothing to do with storing blobs — which is exactly what Harbor adds as a layer on top.

The moving parts

  • Core — the central API server (Go). Every request from the Portal, the Docker/OCI CLI, or a CI pipeline's docker push/pull hits Core first, which checks auth and RBAC against Postgres before proxying blob traffic to the Registry component.
  • Registry — an embedded instance of the CNCF Distribution project. This is the piece that actually receives and stores OCI blobs and manifests on disk or object storage (S3, Azure Blob, GCS, etc.); Harbor doesn't reimplement the distribution protocol, it governs access to it.
  • Portal — the Angular web UI: browsing projects and repositories, viewing scan results, configuring policies, managing users and robot accounts.
  • Job Service — an async worker pool (backed by Redis queues) that runs everything that shouldn't block a request: triggering vulnerability scans, executing replication rules, garbage-collecting unreferenced blobs, firing webhooks.
  • Trivy (scanner adapter) — Harbor talks to scanners through a generic Scanner Adapter API, not a hardcoded integration. Trivy ships as the default, but Clair or a commercial scanner can be plugged in the same way — Job Service invokes whichever adapter is configured whenever a scan is triggered.
  • PostgreSQL & Redis — Postgres holds all metadata (projects, members, policies, scan results, replication rules); Redis backs the Job Service queues and short-lived caching.

All of this ships as one Helm chart (or docker compose for small setups) — from a cluster's point of view, Harbor is just another Deployment plus a Postgres and Redis it depends on, fronted by an Ingress that terminates TLS and load-balances across Core/Portal.

Projects: the unit of multi-tenancy

Every repository in Harbor lives inside a project — the boundary for access control, quotas, and policy. A project can be public (anyone can pull) or private, and members are assigned one of several roles: Project Admin (full control including policy and membership), Maintainer and Developer (push/pull with varying config rights), Guest and Limited Guest (read-only, with Limited Guest also hiding vulnerability details). For non-human callers — CI/CD pipelines, mainly — Harbor issues robot accounts: credentials scoped to specific actions on specific projects (e.g. "push to library/* only"), with an expiration date, so a leaked CI secret doesn't hand out a permanent admin credential.

Security pipeline: scan, sign, and gate

Two independent policies turn Harbor from passive storage into an active gate:

  • Vulnerability scanning — every push (or a scheduled re-scan, since new CVEs are discovered against old images constantly) can trigger Trivy against the image's OS packages and language dependencies. Results are stored per-digest and surfaced in the Portal with a severity breakdown.
  • "Prevent vulnerable images from running" — a per-project policy that blocks pull (not just deployment — Harbor has no idea what happens to an image after it leaves the registry, so the pull itself is the enforcement point) whenever the latest scan reports a CVE at or above a configured severity threshold, with an optional CVE allowlist for exceptions the security team has explicitly accepted.
  • Content trust / signing — Harbor originally used Notary (TUF-based signing, the same lineage as TUF), but deprecated that integration starting in v2.6 and dropped it entirely in v2.9. The current path is Cosign (from the Sigstore project) or the OCI-native Notation, both of which store a signature as an ordinary OCI artifact attached to the image's digest rather than in a separate trust server. A project can require "only signed images may be pulled" the same way it requires "no critical CVEs."

What to notice Signing always succeeds and scanning always completes — the CVEs are just reported. The only step that can actually block anything is the policy gate, evaluated at pull time against the latest scan result. Toggle the policy off with the vulnerable image selected: the scan still reports a critical CVE, but the pull now goes through anyway, because nothing enforces the finding. Scanning without a policy is just a dashboard; the gate is what makes it a control.

Replication

Harbor can replicate repositories to or from another Harbor instance, or to/from most major registries (Docker Hub, ECR, GCR/Artifact Registry, ACR, Quay, and others) via replication rules filtered by project, repository name, or tag, and triggered manually, on a schedule, or automatically on every push. This is how a multi-region deployment keeps a local copy of its images near each cluster instead of every region pulling across a WAN link to one origin registry — the same problem, at a different layer, that Dragonfly (next up) solves with peer-to-peer distribution once images are already local to a region and thousands of nodes need to pull them at once.

Where you'd reach for it

  • A private, policy-enforced registry — you need to run your own registry (compliance, data residency, air-gapped environments) but still want RBAC, scanning, and signing rather than bare Distribution.
  • Supply-chain gates before deployment — CI pushes to Harbor, and a project policy blocks any image with unpatched critical CVEs or without a valid signature from ever being pullable, independent of whatever is doing the deploying (Argo CD, Flux, plain kubectl).
  • Multi-region or multi-cluster image distribution — replication rules keep a local mirror near each cluster instead of every pull crossing a long network path back to one registry.
Often confused with Harbor vs. a plain registry (Distribution/Docker Hub): Harbor embeds a Distribution registry for storage — it doesn't replace it — and adds the project/RBAC/scan/sign/replication layer on top; a bare registry has none of that. Harbor vs. Quay: Red Hat's Quay covers similar ground (scanning, RBAC, replication) but isn't a CNCF project; teams choose between them mostly on ecosystem fit (Quay ties closely to OpenShift) rather than a fundamental architectural difference. Harbor vs. Dragonfly: Harbor decides whether an image may be pulled and stores the canonical copy; Dragonfly accelerates how a large fan-out of nodes actually pulls it, and commonly sits in front of or alongside a registry like Harbor rather than replacing it.

Why it graduated

Harbor started at VMware in 2016 as an internal project to run a compliant private registry across VMware's own Kubernetes platforms, joined CNCF at the Sandbox level in 2018, moved to Incubating later that same year, and graduated on June 15, 2020 — the 11th CNCF project to reach Graduated status. The graduation case rested on broad production adoption across many organizations (not just VMware), an open governance model with a multi-vendor maintainer base, and demonstrated integration with the rest of the cloud-native security stack — pluggable scanners, Kubernetes-native deployment via Helm, and (at the time) Notary, later replaced by Sigstore/Cosign as that ecosystem matured.
