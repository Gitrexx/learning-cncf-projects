KEDA

Kubernetes ships a built-in autoscaler for Pods — the Horizontal Pod Autoscaler (HPA) — but it was designed around one shape of signal: CPU and memory utilization pulled from metrics.k8s.io, sampled from Pods that are already running. That's a bad fit for a huge class of real workloads: a consumer that should scale on how many messages are sitting in a Kafka topic or a SQS queue, not on how busy the Pod happens to be right now — and it can't help at all with the case where the right number of replicas is zero, because HPA can never scale a Deployment below 1. KEDA (Kubernetes Event-Driven Autoscaling) fills both gaps: it lets the HPA scale on external, event-source-specific metrics instead of just CPU/memory, and it adds the 0↔1 transition HPA structurally can't do — real scale-to-zero for anything, not just Knative-style HTTP services.

Where this fits KEDA doesn't replace the HPA — it feeds it. KEDA is a thin, pluggable layer that watches an event source (a queue, a stream, a cron schedule, a Prometheus query, 60+ others), turns that into a metric the HPA can understand, and additionally takes over the one job the HPA can't do: deciding when a workload should exist at all. It sits squarely inside "autoscaling," the same landscape slot as the HPA and the Cluster Autoscaler, but one layer higher: it decides how many Pods, not how many nodes.

The gap KEDA closes: custom metrics were always possible, never uniform

Kubernetes' HPA has supported "external metrics" since early on via the custom.metrics.k8s.io and external.metrics.k8s.io APIs — but someone had to run a metrics adapter that implemented that API for their specific event source, and every team building one solved the same problem slightly differently: how to poll the source, how to authenticate, how to convert "37 messages in the queue" into a Kubernetes metric value, how to handle the source being briefly unreachable. KEDA standardizes all of that behind one CRD-driven contract and a growing catalog of maintained scalers — small Go modules that each know how to talk to one event source (RabbitMQ, Kafka, Redis, PostgreSQL, Azure Service Bus, AWS SQS, GCP Pub/Sub, Prometheus, cron schedules, and dozens more) — so "scale my Deployment on Kafka consumer lag" becomes a twenty-line YAML resource instead of a bespoke adapter someone has to build and operate.

Three components, one job split in two phases

A KEDA install runs three pieces, and the split matters because it maps directly onto how scaling decisions get made:

ComponentRole
keda-operatorWatches ScaledObject/ScaledJob resources, polls each scaler on its pollingInterval, and owns the activation decision — scaling 0↔1 directly by patching the Deployment, bypassing the HPA entirely.
keda-operator-metrics-apiserverImplements the external.metrics.k8s.io API, translating each scaler's raw reading (queue depth, lag, whatever) into a metric value the standard Kubernetes HPA controller can query.
keda-admission-webhooksValidates ScaledObject/ScaledJob specs on create/update — e.g. rejects two ScaledObjects targeting the same Deployment, which would fight over the same HPA.

That gives KEDA a genuinely two-phase architecture. For the 0↔1 transition — the part the HPA cannot do, since it only ever adjusts an existing replica count — the KEDA operator itself decides and patches the Deployment straight to 1 (or straight to 0) the moment a scaler's IsActive check flips. For 1↔N scaling once at least one replica is running, KEDA gets out of the way: it creates and owns a standard Kubernetes HorizontalPodAutoscaler object on your behalf, wired to query KEDA's own metrics server as an external metric source, and the native HPA control loop — the same one that's always driven CPU-based scaling — takes it from there, complete with its usual stabilization windows and scale-velocity policies.

ScaledObject: the core resource

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-worker
spec:
  scaleTargetRef:
    name: order-worker           # the Deployment being scaled
  pollingInterval: 30            # seconds between scaler checks (default)
  cooldownPeriod: 300            # seconds of inactivity before scaling to zero (default)
  minReplicaCount: 0             # KEDA-only: HPA alone could never go this low
  maxReplicaCount: 10
  triggers:
    - type: rabbitmq
      metadata:
        queueName: orders
        queueLength: "5"          # target: ~5 messages per replica
      authenticationRef:
        name: rabbitmq-trigger-auth

scaleTargetRef points at any Deployment, StatefulSet, or arbitrary scalable custom resource. Each entry under triggers selects a scaler by type and configures it — a ScaledObject can list several triggers, and KEDA scales up if any of them says it should. authenticationRef points at a separate TriggerAuthentication (or cluster-scoped ClusterTriggerAuthentication) resource, which keeps credentials — a connection string, an IAM role, a Vault path — out of the ScaledObject itself and lets platform teams manage secrets once, referenced by many workloads.

ScaledJob: the other target shape Not every event-driven workload is a long-running Deployment that should have more or fewer replicas — sometimes each unit of work should be its own Kubernetes Job, run to completion and discarded. ScaledJob covers that case: instead of adjusting a Deployment's replica count, KEDA creates one Job per unit of pending work (up to maxReplicaCount concurrently), which fits batch-style, one-shot processing better than a pool of long-lived worker Pods.

What to notice The jump from 0 to 1 replica happens the instant the queue goes above zero and the operator's poll lands — that's KEDA's own activation decision, no HPA involved. Every replica count above 1 only ever changes on an HPA-labeled tick, because from there it's the standard Kubernetes HPA loop reading KEDA's external metric. And dropping the queue to zero doesn't scale down immediately: the badge turns amber and counts down the cooldownPeriod (modeled here as 10 ticks — the real default 300s ÷ 30s pollingInterval) before KEDA scales the last replica to zero, so a brief lull in traffic doesn't thrash your workload.

Extensibility: scalers as a plugin surface

The scaler catalog covers most common event sources out of the box, but KEDA doesn't require every integration to live in its own repo. An external scaler is a small gRPC service you write and run yourself, implementing KEDA's scaler interface (IsActive, GetMetricsAndActivity); a ScaledObject trigger of type external or external-push points at it. That's the escape hatch for an internal system or a niche event source KEDA doesn't ship a scaler for — you get the same activation/HPA-handoff machinery for free, you just supply the "how do I read this source" logic.

Often confused with The HPA is what KEDA drives, not what it replaces — KEDA still creates and relies on a real HPA object for 1→N scaling; it only adds the external-metric feed and the 0↔1 capability the HPA lacks on its own. The Vertical Pod Autoscaler (VPA) is solving a different axis entirely (resizing a Pod's CPU/memory requests, not replica count) and is generally not run alongside KEDA/HPA on the same metric without care, since both would be adjusting the same Pods. The Cluster Autoscaler operates one layer down — nodes, not Pods — and typically reacts to KEDA's scaling decisions (more Pods triggering more node capacity), rather than competing with it. And KEDA HTTP Add-on is a separate, not-yet-graduated KEDA sub-project purpose-built for scaling on live HTTP request volume (including true zero-downtime scale-from-zero for web traffic) — a scenario the queue/ stream-oriented core scalers don't cover well on their own.

Why it graduated, and where you'll meet it

KEDA graduated CNCF in August 2023 on the strength of a simple, sharply-scoped idea executed well: keep the HPA as the trusted scaling control loop, and just widen what can feed it — plus add the one capability, scale-to-zero, that no amount of custom metrics could ever unlock on their own. You'll meet KEDA anywhere workloads are driven by bursty, queue-shaped, or scheduled demand rather than steady CPU load: message-queue consumers, stream processors, cron-triggered batch jobs, and — increasingly — as the autoscaling backbone under serverless-on-Kubernetes platforms (including parts of Knative and Azure Container Apps) that need real scale-to-zero without reinventing the HPA underneath it.
