Kubeflow

A data scientist has a notebook that trains a good model on a laptop. Getting from there to production means a lot of plumbing: rerunning the same steps on fresh data every week, training on 16 GPUs across 4 nodes instead of one, trying 200 hyperparameter settings without babysitting them, recording which dataset and code produced which model, and handing the result to something that serves it. Kubeflow is the open-source answer to that plumbing, built as Kubernetes controllers and CRDs. It isn't one tool. It's a family of projects, one for each stage of the model lifecycle, which you can install together as a platform or pick from one at a time.

Where this fits Kubeflow started at Google in 2017 as "a simpler way to run TensorFlow jobs on Kubernetes" (the name is Kube + Tensorflow). It quickly became framework-agnostic. It joined the CNCF as an incubating project in 2023. The TOC voted it to graduated on 24 July 2026, and CNCF announced it on 17 August 2026. It's the first ML platform to reach the top tier. CNCF's graduation announcement counts more than 6,600 contributors from over 1,000 organizations and about 260 million Python package downloads. Named users include Bloomberg, NVIDIA, Red Hat (it's the upstream of OpenShift AI), LinkedIn, Spotify, and Capital One. Relative to Kubernetes, every part of Kubeflow is an operator: you describe a training run, a tuning experiment, or a notebook server as a custom resource, and a controller turns it into Pods, Jobs, and Services.

The problem: ML isn't one job, it's a lifecycle

A web service has a fairly simple shape: build an image, roll it out, scale it. An ML system has several stages, and each one needs something different from the cluster:

StageWhat it needs from the clusterKubeflow project
ExploreLong-lived interactive environments with GPUs and persistent volumesNotebooks
Prepare dataLarge distributed batch jobsSpark Operator
TrainGang-scheduled, multi-node GPU jobs that know about torchrun, MPI, or JAXTrainer
TuneMany parallel trials, each scored on a metric, with a search algorithm choosing the next oneKatib
OrchestrateA repeatable, versioned DAG of all the above, with caching and lineagePipelines
TrackA record of which model version came from which run, data, and parametersModel Registry
ServeAutoscaled inference endpointsKServe (born in Kubeflow, now its own CNCF project)

Before Kubeflow, teams either glued this together themselves (cron plus bash plus a shared NFS mount plus a spreadsheet of model versions) or bought a managed platform such as SageMaker, Vertex AI, or Azure ML. Kubeflow's pitch is to get that managed-platform experience on any Kubernetes cluster, including on-prem GPU fleets, with the same RBAC, quotas, and GitOps you already use.

The architecture: a set of operators plus a shared shell

There are two ways to consume it, and the difference matters when you read blog posts:

  • Standalone components. Install only Kubeflow Pipelines, or only Trainer, with its own manifests or Helm chart. Many production users do this. For example, they run KFP for orchestration and nothing else, or use Trainer under their own scheduler.
  • The Kubeflow AI Reference Platform. A tested, versioned bundle of all the components, plus the Central Dashboard, Istio, an auth stack (Dex and oauth2-proxy), and cert-manager, installed from the kubeflow/manifests repo. It was renamed from "Kubeflow Platform" around release 1.11 (late 2025) and has since moved to calendar versions such as 26.03. Vendor distributions such as Red Hat OpenShift AI, Charmed Kubeflow, and the cloud packagings build on it.

Multi-tenancy: Profiles

A Profile is a cluster-scoped CRD that represents one user or team. The profile controller turns each Profile into a namespace, plus RoleBindings for the owner and contributors, an Istio AuthorizationPolicy that admits only requests carrying those users' identity headers, and optional ResourceQuotas. Everything a user creates (notebooks, pipeline runs, TrainJobs) lives in their profile namespace. If you know Kubernetes, this is just "namespace-per-tenant" automated, with the mesh enforcing it at the HTTP layer for the web apps.

Kubeflow Pipelines (KFP): ML workflows as containerized DAGs

Pipelines is the project most people mean when they say "we use Kubeflow." You write Python. Each step is a component, and the pipeline is a function that wires components together by their inputs and outputs: 

from kfp import dsl, compiler

@dsl.component(base_image="python:3.12", packages_to_install=["pandas"])
def preprocess(raw: dsl.Input[dsl.Dataset], clean: dsl.Output[dsl.Dataset]):
    import pandas as pd
    pd.read_csv(raw.path).dropna().to_csv(clean.path, index=False)

@dsl.component(base_image="pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime")
def train(data: dsl.Input[dsl.Dataset], lr: float, model: dsl.Output[dsl.Model]):
    ...  # write weights to model.path

@dsl.pipeline(name="churn")
def churn(lr: float = 3e-4):
    ing = dsl.importer(artifact_uri="s3://data/churn.csv", artifact_class=dsl.Dataset)
    prep = preprocess(raw=ing.output)
    train(data=prep.outputs["clean"], lr=lr).set_accelerator_type("nvidia.com/gpu").set_accelerator_limit(1)

compiler.Compiler().compile(churn, "churn.yaml")   # → platform-neutral IR

The compiler doesn't produce Kubernetes YAML directly. It produces an IR (PipelineSpec). That portability is a big deal: the same compiled file runs on open-source KFP and on Google's managed Vertex AI Pipelines. When you submit a run, this is what happens:

  1. The KFP API server stores the pipeline version and run in MySQL, then compiles the IR into an Argo Workflows Workflow. Argo is the default and main execution engine (see the Argo deep-dive). There was a Tekton backend, but it's no longer the main path.
  2. For each task, Argo first runs a driver. The driver resolves the task's inputs from upstream outputs, computes a cache key (a hash of the component spec and its input values and artifacts), and checks whether an identical execution has already succeeded. If it has, the task is marked cached and its outputs are reused without starting a Pod.
  3. Otherwise the user's container runs, wrapped by a small Go launcher injected as its entrypoint. The launcher downloads input artifacts from object storage (S3, GCS, or the in-cluster store), runs your code, uploads output artifacts, and records the execution and its artifacts for lineage.
  4. A persistence agent watches Workflow status and syncs it back to the API server. The ScheduledWorkflow controller handles recurring runs ("retrain every Monday").

    What to notice
    The first run executes every step. Run again with nothing changed: every task's cache key matches a previous
    success, so the whole thing completes almost immediately and no Pods start. Tick change train lr:
    ingest and preprocess stay cached, but train has a new input, so it
    reruns, and everything downstream reruns because its input artifact (the model) is new. Tick new raw
    data and the change propagates from the first step. Caching only works because components are
    pure functions of their inputs. If a step reads "today's date" or a mutable table without
    taking it as an input, the cache gives you stale results. In that case you turn caching off per task with
    .set_caching_options(False).
  


  
Kubeflow Trainer: distributed training as one CRD

  

    Distributed training is awkward for plain Kubernetes. A 4-node PyTorch job needs 4 Pods that all start
    together (gang scheduling).
    Each Pod needs to know its rank, the world size, and the address of rank 0 (MASTER_ADDR). If one
    Pod fails, the whole group usually has to restart. A Deployment or a single Job can't express any of that.
  

  

    The old Training Operator (v1) solved it with one CRD per framework: TFJob,
    PyTorchJob, MPIJob, XGBoostJob, and so on, each with its own controller
    logic. Kubeflow Trainer v2 (released 2025, the current line) replaces them with a split that
    platform teams will recognize:
  

  
    
    
  • TrainingRuntime / ClusterTrainingRuntime, written by the
      platform engineer. A reusable blueprint: a JobSet template, an mlPolicy (torch with
      numProcPerNode, or MPI with SSH setup), and optional dataset and model
      initializers that pre-download from Hugging Face or S3 into a shared volume. Kubeflow ships
      built-ins such as torch-distributed, DeepSpeed, MLX, JAX, XGBoost, and LLM fine-tuning
      runtimes.
    • 
    
  • TrainJob, written by the data scientist. A short object that says
      "this image, this command, this many nodes, using that runtime."
    • 
  


apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: churn-ddp
  namespace: team-ml            # a Profile namespace
spec:
  runtimeRef:
    kind: ClusterTrainingRuntime
    name: torch-distributed
  trainer:
    image: registry.example.com/churn-train:1.4
    command: ["python", "train.py", "--lr", "3e-4"]
    numNodes: 4
    resourcesPerNode:
      limits: { nvidia.com/gpu: 2 }

  

    The Trainer controller merges the TrainJob into the runtime and creates a JobSet (a
    Kubernetes SIG project for groups of Jobs with a headless Service for Pod discovery). It injects the torchrun
    environment (PET_NNODES, PET_NPROC_PER_NODE, PET_MASTER_ADDR,
    and so on), and hands gang admission and quota to Kueue or another gang scheduler (Volcano,
    the coscheduling plugin). Most users never write the YAML. They call
    TrainerClient().train(...) from the Python Kubeflow SDK in a notebook, which
    creates the TrainJob for them.
  

  

    Reading old blog posts
    If a tutorial says kind: PyTorchJob with apiVersion: kubeflow.org/v1, that's the
    Training Operator v1 API. It's still widely deployed, but new work targets TrainJob. The Kubeflow
    docs have a migration guide.
  


  
Katib: hyperparameter tuning as a control loop

  

    Training has knobs (learning rate, batch size, dropout, number of layers) that the model doesn't learn by
    itself. Finding good values means training many times and comparing a metric. Katib (Arabic
    for "secretary") automates that with three CRDs:
  

  
    
    
  • Experiment: the search space, the objective (for example, minimize
      val_loss, with an optional goal that ends the experiment early), the algorithm, and the budget
      (maxTrialCount, parallelTrialCount, maxFailedTrialCount), plus a
      trial template: any Kubernetes resource (a Job, a TrainJob, an Argo Workflow) with
      placeholders for the parameters.
    • 
    
  • Suggestion: the experiment controller asks the suggestion service, a gRPC
      service running the chosen algorithm, for the next N parameter sets. It sends along every completed trial's
      result.
    • 
    
  • Trial: one parameter set. The trial controller fills in the template, runs
      it, and a metrics collector (a sidecar that parses val_loss=0.231 lines from
      stdout, reads TensorFlow event files, or receives pushed metrics) reports the objective to Katib's DB.
    • 
  


apiVersion: kubeflow.org/v1beta1
kind: Experiment
spec:
  objective: { type: minimize, objectiveMetricName: val_loss, goal: 0.05 }
  algorithm: { algorithmName: bayesianoptimization }   # random, grid, tpe, cmaes, hyperband, pbt…
  maxTrialCount: 30
  parallelTrialCount: 3
  earlyStopping: { algorithmName: medianstop }       # kill trials doing worse than the median
  parameters:
    - name: lr
      parameterType: double
      feasibleSpace: { min: "1e-5", max: "1e-1", distribution: logUniform }
    - name: dropout
      parameterType: double
      feasibleSpace: { min: "0.0", max: "0.6" }
  trialTemplate: { ... }   # e.g. a TrainJob with ${trialParameters.lr}

  

    The algorithm choice matters most when trials are expensive. Random search samples
    independently. It's simple, parallelizes perfectly, and works surprisingly well, but it never learns from
    earlier trials. Bayesian optimization fits a cheap
    surrogate model
    to the trials so far and chooses the next point by maximizing an
    acquisition function,
    so each new trial goes where it's most likely to beat the current best. Try both below.

    What to notice
    Over several seeds, Bayesian optimization usually reaches a lower loss in fewer trials. After the initial
    random points it packs its trials into the promising region and refines there. Random search scatters its
    trials evenly and sometimes finds the narrow basin by luck. Bayesian optimization isn't always better, though.
    With a noisy metric, or when Katib runs many trials in parallel (each batch has to be chosen before the
    previous one reports back), its advantage shrinks. Random search stays a strong, cheap baseline. That's why
    Katib offers both, plus Hyperband (stops weak trials early with a small budget), TPE, CMA-ES, and
    population-based training.
  


  
The rest of the family

  
    
    
  • Notebooks. A Notebook CR (created from the dashboard's form) becomes a
      StatefulSet with a PVC for the home directory, a Service, and an Istio VirtualService so it's reachable at
      /notebook/<ns>/<name>/. Images exist for JupyterLab, VS Code (code-server), and
      RStudio. A culling controller can stop idle notebooks to free their GPUs.
    • 
    
  • Spark Operator. SparkApplication CRDs for running Apache Spark on
      Kubernetes. It was donated to Kubeflow in 2024 and covers the "prepare a lot of data" stage. Recent releases
      add Spark 4 and Spark Connect.
    • 
    
  • Model Registry. A metadata service with a REST API. It records registered models,
      their versions, and the artifact URIs, linked back to the pipeline run that produced them. It's the
      handoff point to serving: "deploy version 7 of churn." The project is broadening into a
      catalog of models and other AI assets, so you may see it under new names in recent releases.
    • 
    
  • Kubeflow SDK. A newer, unified Python package (pip install kubeflow) that
      wraps Trainer, Katib, Model Registry, and Spark behind one client API, so a data scientist never has to
      touch kubectl.
    • 
    
  • KServe is not part of Kubeflow any more. It started as KFServing inside
      Kubeflow and became an independent CNCF project for inference (InferenceService, autoscaling
      including scale-to-zero via Knative, LLM runtimes). The platform bundle still
      installs it, and the Model Registry points at it.
    • 
  


  
Where you'd reach for it

  
    
    
  • You already run Kubernetes (often an on-prem or multi-cloud GPU fleet) and want ML to
      share its scheduling, quotas, identity, and GitOps, rather than running a separate ML silo.
    • 
    
  • You need repeatable, versioned training pipelines with caching and lineage: weekly
      retrains, regulated industries that must show "which data produced this model."
    • 
    
  • You run multi-node training or LLM fine-tuning and want platform engineers to own the
      runtime blueprints while researchers just submit jobs.
    • 
    
  • You want to avoid lock-in. KFP's IR runs on Vertex AI as well as on your own cluster.
    • 
  

  

    The trade-off is operational weight. The full platform is a lot of moving parts: Istio, an auth stack,
    MySQL, object storage, Argo, and half a dozen controllers. A three-person data team on a single cloud may get
    more done with SageMaker or Vertex AI. That's why so many teams install just KFP or just Trainer, or buy a
    distribution.
  


  

    Often confused with
    Argo Workflows: KFP runs on Argo. Argo is a generic DAG engine, and KFP adds typed
    ML artifacts, caching, lineage, and a Python SDK on top. MLflow: mainly experiment tracking
    and a model registry. It overlaps with Model Registry and Katib's results UI, but it doesn't orchestrate
    Kubernetes workloads, and many teams use both. Ray / KubeRay: a distributed compute framework
    you program against. Kubeflow schedules jobs; Ray is the job's runtime, and the two are often
    combined. Kueue / Volcano: batch quota and gang schedulers that Trainer and Katib
    use. They don't replace them. KServe: serving, now a separate project.
  


  
Why it graduated

  

    Graduation recognizes maturity, not novelty. Kubeflow had years of production use at large organizations, a
    vendor-diverse maintainer base (Google, Red Hat, NVIDIA, Apple, Bloomberg, IBM, Canonical, and others), a
    third-party security audit, and a formal steering committee for governance. It has become the reference
    answer to "how do you run the ML lifecycle on Kubernetes." That matters more now that AI training and
    inference are among the biggest workloads in the CNCF landscape. CNCF's own framing was that graduation is a
    vote for Kubernetes as the AI control plane.
