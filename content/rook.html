Rook

Every project so far has assumed persistent storage just shows up when a Pod asks for it — a PersistentVolumeClaim gets bound, a volume appears, done. On a managed cloud that's because the cloud provider's block-storage service is doing the actual work behind a CSI driver. On bare metal, or when you need block, file, and object storage from the same pool of disks without three separate systems, someone still has to run that storage layer — and historically that meant standing up Ceph, a powerful but famously operationally heavy distributed storage system, entirely by hand outside Kubernetes. Rook's job is to make Ceph a Kubernetes-native, self-managing thing: not a new storage engine, but an operator that runs, heals, and scales an existing one.

Where this fits Rook is a Kubernetes operator for storage orchestration — by far its dominant use is running Ceph (Rook started with several backends; Ceph is the actively maintained one today). You declare a CephCluster custom resource describing which nodes and disks to use; the Rook operator turns that into a running Ceph cluster of Pods, and Ceph itself — via the Ceph-CSI driver — hands your other Pods block volumes, a shared filesystem, or an S3-compatible object store, all from the same underlying pool of storage. Rook manages the cluster's lifecycle; it does not sit in the data path once a volume is mounted.

The problem: Kubernetes has no opinion about where bytes live

Kubernetes standardized how a Pod asks for storage (PVCs) and how a driver provisions it (the CSI interface), but it deliberately has no opinion on what's underneath a CSI driver. On EKS, GKE, or AKS that's fine — the cloud's block-storage service is already elastic, replicated, and someone else's 3am pager. On bare metal, in a homelab, or in an air-gapped environment, there usually isn't one. You need something that turns a pile of raw disks across a set of nodes into resilient, expandable storage — and that "something" has traditionally been Ceph: a distributed storage system, created by Sage Weil in 2004, that provides block, file, and object storage from a single self-healing cluster with no single point of failure. The catch was always operational: standing up and running Ceph well — sizing monitors correctly, building CRUSH maps, handling disk failures, planning capacity — is a specialty in its own right, usually done with dedicated tooling (ceph-deploy, cephadm) completely outside any Kubernetes workflow.

Rook's founding idea, entering CNCF Sandbox in January 2018, is that this operational knowledge belongs in a Kubernetes controller instead of a runbook. You describe the desired storage cluster as a custom resource; a controller drives the cluster toward that state and keeps fighting entropy — disk failures, node loss, capacity growth — the same way every other controller in this landscape does.

The operator and its CRDs

The rook-ceph-operator is an ordinary Kubernetes Deployment that watches a family of custom resources and reconciles Ceph daemons to match. The main ones:

  • CephCluster — the cluster itself: which nodes and raw devices to use, how many monitors, network mode, and cluster-wide settings. Creating one is what actually stands the Ceph cluster up.
  • CephBlockPool — a replicated or erasure-coded pool backing RBD (block) volumes, with a failure domain (host, rack, ...) and replica count.
  • CephFilesystem — provisions the metadata and data pools plus MDS daemons for a shared, POSIX CephFS filesystem multiple Pods can mount ReadWriteMany.
  • CephObjectStore — stands up RGW (RADOS Gateway) daemons exposing an S3-compatible bucket API over the same underlying cluster.

Apply a CephCluster and the operator creates the daemon Pods; apply a CephBlockPool and it creates the pool and a matching StorageClass your app's PVCs can target. Nothing about Ceph's internals — placement groups, CRUSH rules, monitor quorum — has to be hand-tuned for common cases; the operator picks sane defaults and exposes the knobs that actually matter as CRD fields.

The daemons underneath: MON, MGR, OSD, MDS, RGW

A running Rook-Ceph cluster is a handful of daemon types, each its own set of Pods, all watched and healed by the operator:

  • MON (Monitor) — maintains the authoritative cluster map (which OSDs exist, the CRUSH map, pool config) via Paxos consensus among an odd-sized quorum (typically 3 or 5). Every client and daemon consults the monitors to learn the cluster's current shape.
  • MGR (Manager) — tracks runtime metrics, exposes the Ceph dashboard and Prometheus metrics, and hosts management modules; runs active/standby.
  • OSD (Object Storage Daemon) — one per disk (or partition): the actual data-serving workhorse. This is where objects live, where replication or erasure coding happens, and what recovers when a disk or node is lost.
  • MDS (Metadata Server) — tracks the directory tree and file metadata for CephFS only; block (RBD) and object (RGW) storage don't need it.
  • RGW (RADOS Gateway) — a stateless HTTP daemon translating S3/Swift API calls into operations on the underlying object store.

Underneath all of it is RADOS (Reliable Autonomic Distributed Object Store) — Ceph's core storage layer. Block, file, and object storage are three different client-facing APIs built on the same RADOS object store; that's why one Rook-Ceph cluster can serve all three from the same disks instead of needing three separate storage systems.

CRUSH: placement without a lookup table

The mechanism that makes Ceph scale is CRUSH (Controlled Replication Under Scalable Hashing). A naive distributed store needs a central metadata service mapping every object to its physical location — a bottleneck and a single point of failure at scale. Ceph instead spreads objects across placement groups (PGs) — logical shards of a pool, typically far fewer than the object count — and CRUSH is a deterministic algorithm any client or daemon can run locally to compute which OSDs host a given PG, from the cluster map plus a pseudo-random hash. No lookup, no round trip to a metadata server: everyone computes the same answer independently.

CRUSH is also failure-domain aware. A pool's replication rule can say "keep each PG's replicas on different hosts" (or racks, or zones) — so CRUSH will never place two replicas of the same PG on the same node, which is exactly what makes losing an entire node survivable rather than just losing a disk. When an OSD (or a whole node) goes down, CRUSH recomputes placement for the PGs that lost a replica and the affected OSDs re-replicate data onto the new target automatically — Ceph's self-healing, with no external orchestrator involved.

What Rook actually exposes to your Pods

Provisioning and mounting is handled by the separate Ceph-CSI driver, which Rook deploys and wires up automatically — this is also the precise sense in which "Rook is not in the data path": once a volume is mounted, your application's I/O goes straight from the Ceph-CSI driver (and ultimately the client library) to the OSDs via CRUSH-computed placement, not through the Rook operator.

Where you'd reach for it

  • Bare-metal and on-prem Kubernetes — the primary case: no cloud block-storage API exists, and Rook turns a set of nodes' local disks into elastic, replicated storage.
  • Needing block, file, and object from one system — instead of running three separate storage stacks (e.g. an NFS server, a block CSI driver, and a MinIO cluster), one Rook-Ceph cluster serves all three from the same pool of disks.
  • Edge or air-gapped clusters — anywhere a managed cloud storage service simply isn't available and self-hosted, self-healing storage is the only option.
Often confused with Rook vs. Ceph: Ceph is the storage system; Rook is the Kubernetes operator that deploys, heals, and upgrades it — you can run Ceph without Rook (the traditional way), but you can't run Rook without Ceph. Rook vs. Longhorn / OpenEBS: those are simpler, Kubernetes-native block storage systems built from scratch for the container era with a smaller operational footprint; Rook brings the far more mature but heavier Ceph, and is the only one of the three offering block, file, and object from one cluster. Rook vs. a cloud CSI driver (EBS, PD): those provision storage the cloud already runs for you; Rook runs the storage cluster itself, inside your Kubernetes cluster, which is the point when there's no cloud storage service to call.

Why it graduated

Rook entered CNCF Sandbox in January 2018 and reached Graduated status in October 2020 — the first (and for a long time only) project in CNCF's storage category to do so. Its graduation reflected a mature operator managing a genuinely production-proven storage engine (Ceph long predates Kubernetes and powers storage at large scale independently of it), plus the project narrowing its focus over time to the backend that mattered most in practice: Ceph. You'll meet Rook wherever a team runs Kubernetes without a cloud provider's storage API underneath it — bare metal, edge, and on-prem platform teams are its home turf.
