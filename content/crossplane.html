Crossplane

Every project so far in this section has stretched a Kubernetes-shaped API over something that isn't a container: Dapr's building blocks, Knative's request-driven scaling, KubeEdge's offline nodes, CloudEvents' event envelope. Crossplane takes the boldest version of that idea and points it at infrastructure itself — a managed Postgres instance, a VPC, an IAM role, a Helm release, a DNS zone — and manages all of it the same way the kubelet manages a Pod: as an object someone declares, that a controller continuously reconciles toward. It graduated CNCF in November 2025, and the pitch is blunt: stop treating "provision the cloud" and "run the workload" as two different tools with two different mental models.

Where this fits Crossplane turns a Kubernetes cluster into a universal control plane. You install Providers (packages that add CRDs + controllers for a target system — AWS, GCP, Azure, but also Helm, Vault, GitHub, or plain Kubernetes), which give you Managed Resources — one Kubernetes object per external thing, reconciled the same way a Deployment is reconciled. On top of that, Composite Resource Definitions (XRDs) let a platform team define its own custom API (say, XDatabase), and a Composition says what combination of Managed Resources one instance of that API expands into. It's the control-plane-building half of this landscape's runtime section, the way Crossplane's own docs put it: a cloud-native alternative to Terraform that never stops reconciling.

The problem: infrastructure and workloads speak different languages

A typical cloud-native app needs a Deployment, a Service, and an Ingress — all declared as Kubernetes objects, all continuously reconciled by controllers so drift gets corrected automatically. But that same app also needs a managed database, an object storage bucket, a message queue, maybe a DNS record — and those usually get provisioned by a completely different tool: Terraform, a cloud console, a bespoke script, run from a CI pipeline as a one-shot apply. Two different APIs, two different failure modes, two different places to look when something drifts, and no way for the Kubernetes-native half of your stack (RBAC, GitOps, admission policy) to reach the infrastructure half at all.

Crossplane's founding bet, incubated at Upbound starting in 2018, is that the second half doesn't need a separate tool — it needs the same tool, because Kubernetes' reconciliation model (declare desired state, let a controller loop drive reality toward it) is a better fit for infrastructure than one-shot, run-when-you-remember apply tools ever were. So Crossplane extends the Kubernetes API itself with new resource types for infrastructure, and lets the same controllers, the same kubectl, and the same RBAC that already govern your workloads govern your cloud resources too.

Providers and Managed Resources: one Kubernetes object per external thing

A Provider is an installable package (distributed as an OCI artifact, installed with a Provider object much like a Helm chart) that adds a set of CRDs and a controller targeting one system. provider-aws-rds adds an RDSInstance kind; provider-helm adds a Release kind for installing charts; provider-kubernetes even lets Crossplane manage objects on a different Kubernetes cluster. The ecosystem now spans official and community providers for every major hyperscaler plus dozens of other systems — anything with an API is fair game, not just "cloud infra" in the AWS/GCP/Azure sense.

Each CRD a Provider installs is a Managed Resource (MR) — the Crossplane representation of one external resource, in a strict 1:1 relationship: one RDSInstance object, one actual RDS instance. Its controller runs the same reconcile loop as any Kubernetes controller: observe the external resource's current state via the provider's API, diff it against spec, and call create/update/delete as needed — every few minutes, forever, not just at creation time. That loop is what makes Crossplane fundamentally different from a plan-and-apply tool: if someone hand-edits the RDS instance in the AWS console, the next reconcile notices and reverts it, the same way a Deployment controller would restore a Pod someone deleted by hand.

Managed Resources alone are already useful You can stop right here and get value: install a provider, write MRs directly, and get Kubernetes-native, continuously-reconciled infrastructure with RBAC and GitOps for free. Most real platforms go one layer further, though, because raw MRs are as low-level as raw cloud API calls — a platform team wants to hand developers something higher-level, like "give me a database," not "here are the eleven AWS objects a database needs."

Composite Resources: building your own API

That higher layer is a Composite Resource Definition (XRD) — it defines a brand-new custom API, the way a CRD defines any Kubernetes type, except the objects it produces (Composite Resources, or XRs) don't map to one external thing; they map to a combination of Managed Resources that a Composition assembles. An XRD for XDatabase might expose just engine, size, and region to the person requesting one, while the Composition behind it fans that single request out into an RDSInstance, a DBSubnetGroup, and a SecurityGroup — full of organization-specific defaults (encryption on, a specific VPC, tagging conventions) the requester never has to know about.

A Composition doesn't hard-code that fan-out with static templates anymore — as of Crossplane v2, the standard mechanism is a pipeline of Composition Functions: small, independently packaged and versioned programs that Crossplane calls in sequence with a request/response protocol. Each function in the pipeline receives the XR plus whatever resources previous functions in the pipeline have proposed so far, and returns the resources it wants to add or change — the last function's output is what Crossplane actually creates. This replaced the older, purely declarative "patch-and-transform" mode with something that can run real logic (loops, conditionals, calls to external systems) to decide what infrastructure a request needs.

One more variable: scope. In Crossplane v2, an XRD's composite resources are namespaced by default — an XR lives in a namespace and composes resources in that same namespace, so ordinary Kubernetes RBAC and namespace isolation apply directly, no extra indirection needed. XRDs can instead be Cluster-scoped for resources that legitimately span namespaces, or (for backward compatibility) LegacyCluster-scoped — the original v1 model, where the XR itself is cluster-scoped and a namespaced Claim object acts as a proxy so a namespaced user can still request one. Claims still show up constantly in existing platforms built before v2; v2's namespaced XRs exist specifically to make that extra proxy object unnecessary going forward.

The reconciliation loop vs. plan-and-apply

This is the crux of "Crossplane vs. Terraform," and it's worth being precise about it rather than reaching for "Crossplane is Terraform on Kubernetes." Terraform computes a plan by diffing your configuration against a state file, then applies it once; nothing watches for drift until you run plan again by hand (or on a schedule). Crossplane's Managed Resource controllers behave like every other Kubernetes controller in this landscape (compare Argo CD's sync loop, or the kubelet reconciling a Pod spec): they watch continuously, and every observed drift is corrected on the next reconcile, typically within minutes, with no human or pipeline run required. The tradeoff is real too — a live control loop touching production cloud accounts is a different operational surface than a CLI you invoke deliberately, which is exactly why Crossplane leans hard on Kubernetes' existing safety rails (RBAC, admission webhooks, GitOps review) rather than inventing its own.

Where you'd reach for it

  • Platform engineering / internal developer platforms — the dominant real-world pattern: a platform team defines XRDs like Environment, Application, or DatabaseService, and application teams self-serve against that API without ever seeing the underlying cloud resources or needing cloud IAM permissions themselves.
  • Multi-cloud or multi-system abstraction — one Composition can target AWS RDS in one environment and Cloud SQL in another behind the identical XDatabase API, so application manifests don't change across environments.
  • Unifying infra and workload GitOps — because MRs and XRs are ordinary Kubernetes objects, tools already in this landscape (Argo CD, Flux, Kyverno, OPA) apply to infrastructure exactly as they apply to Deployments, with no separate pipeline needed.
Often confused with Crossplane vs. Terraform: both provision infrastructure declaratively, but Terraform is a one-shot CLI tool driven by a state file, while Crossplane is a live Kubernetes control plane that reconciles forever — see above. Crossplane vs. Cluster API: Cluster API uses the same provider/reconciler pattern specifically to provision Kubernetes clusters; Crossplane is general-purpose and can provision anything a provider exists for, including clusters themselves. Crossplane vs. a Helm chart: Helm templates and installs Kubernetes manifests once per release; a Crossplane Composition keeps reconciling its output continuously and can provision resources entirely outside Kubernetes (a managed database, a VPC) that Helm has no concept of.

Why it graduated

Crossplane entered CNCF as a Sandbox project in 2020, moved to Incubating in 2021, and reached Graduated status in November 2025 after completing third-party security audits and moving its release and artifact infrastructure onto CNCF-operated systems — the same governance and security bar every graduated project in this landscape has cleared. Its graduation reflected a large and still-growing ecosystem of providers and a genuine production pattern (platform teams building self-service infrastructure APIs) that CNCF judged mature and vendor-neutral enough to graduate. You'll meet it any time a platform-engineering conversation reaches for "how do we let developers request infrastructure without giving them cloud console access" — it's usually either Crossplane or a Crossplane-shaped in-house tool.
