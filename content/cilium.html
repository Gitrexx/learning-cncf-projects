Cilium

Envoy, Istio, and Linkerd all solve networking by putting a proxy in the request path — a process the packet has to reach, be parsed by, and be forwarded from. Cilium takes a different bet entirely: instead of adding a proxy, it moves networking, security, and observability into the Linux kernel itself, using a kernel technology called eBPF. No sidecar, no separate process to hop through — the kernel that was already going to handle the packet now also enforces policy and reports what happened, at the point the packet actually arrives.

Where this fits Cilium started in 2015 at a company called Isovalent, betting early on eBPF back when the technology was mostly known for kernel-level packet filtering (its literal ancestor, BPF, is what tcpdump is built on). Cilium joined the CNCF in October 2021 and reached Graduated status on October 11, 2023. By 2026 it's the default or a first-class CNI option on every major managed Kubernetes offering — GKE's Dataplane V2, EKS, and AKS's BYO-CNI path all surface Cilium-style eBPF networking directly. It's also the parent project of Hubble (observability) and Tetragon (runtime security via eBPF, in the same family as Falco but kernel-native).

The problem: iptables doesn't scale, and IPs are a bad security anchor

Before Cilium, the standard Kubernetes dataplane relied on iptables: kube-proxy watched Services and Endpoints and translated them into long chains of iptables rules for NAT and load-balancing, and CNI plugins used more iptables rules (or a userspace agent) for NetworkPolicy. Two problems compound here. First, iptables rule chains are evaluated roughly linearly — every packet walks the list until something matches — so as the number of Services and policies grows, per-packet latency grows with it; large clusters could see real, measurable kube-proxy overhead. Second, both kube-proxy and stock NetworkPolicy reason about IP addresses: rules say "allow traffic from 10.1.2.3." But Pod IPs are ephemeral — a Pod that restarts gets a new IP, and that IP can be immediately reassigned to a completely different, unrelated Pod. An IP-based rule set is only ever a snapshot of identity that's already stale by the time you read it.

eBPF: kernel programs without a kernel module

eBPF lets you attach small programs to kernel hooks — a network interface receiving a packet, a socket operation, a system call — and have the kernel run them in-line, with no context switch out to a userspace process. The kernel doesn't just trust these programs blindly: before loading one, an in-kernel verifier statically proves it terminates, never reads out-of-bounds memory, and can't crash the kernel, then a JIT compiler turns it into native machine code. Cilium's cilium-agent compiles and loads eBPF programs onto hooks at several points in the packet's journey: XDP (the earliest possible point, right at the network driver, before the kernel has even allocated a full packet buffer — ideal for dropping unwanted traffic as cheaply as possible), the tc (traffic control) layer for most policy and routing decisions, and socket-level hooks that let Cilium redirect a connection at the socket layer itself, skipping the rest of the network stack entirely for pod-to-pod traffic on the same node.

Architecture: agent, operator, and per-node eBPF maps

Cilium runs as a DaemonSet plus a small control component, not a per-Pod sidecar:

  • cilium-agent — one per node. It watches the Kubernetes API for Pods, Services, Endpoints, and Cilium's own CRDs, and translates that state into eBPF programs and maps (kernel-resident hash tables) loaded into that node's kernel. It also runs the CNI plugin invoked by the kubelet when a Pod is created, wiring up its virtual interface and attaching the eBPF programs to it.
  • cilium-operator — one (logical) instance cluster-wide, handling jobs that shouldn't run redundantly on every node: cluster-wide IP address management (allocating pod CIDR ranges per node), garbage-collecting stale identities, and talking to cloud-provider APIs for native-routing setups.
  • Envoy (optional, per node — not a sidecar) — when a CiliumNetworkPolicy needs L7 awareness (an HTTP method or path, a gRPC service), Cilium runs one shared Envoy instance per node and redirects just the matching traffic to it. This is the one place Cilium and the service-mesh world overlap: recent Cilium releases can run an entire sidecar-free "service mesh" mode this way, contrasted with Istio and Linkerd's per-Pod proxy model.

Identity-based security: policy that survives IP churn

This is Cilium's core idea. Every Pod's relevant Kubernetes labels are hashed into a security identity — a small numeric ID (a 16-bit space, so up to 65,536 distinct identities per cluster) — and by default that identity is represented cluster-wide as a CiliumIdentity custom resource. Every Pod with the same relevant labels shares the same identity, regardless of which node it's on or what IP it was handed. The eBPF datapath enforces policy by looking up the identity attached to a packet's source, not its IP — so when a Pod restarts and gets a new IP, nothing about policy enforcement needs to change, because the identity derived from its labels is unchanged. This is also what makes Cilium's policy model reach further than the IP address it arrived on: a CiliumNetworkPolicy (a superset of the standard Kubernetes NetworkPolicy) can allow traffic by identity plus an HTTP method, or by DNS name for egress to the outside world (an FQDN-based rule like "allow egress to api.example.com on 443," which plain IP-based policy has no way to express since the IP behind a hostname can change at any time).

Replacing kube-proxy

Because the eBPF datapath already sees every packet, Cilium can take over kube-proxy's job entirely. Service-to-endpoint mappings are stored in eBPF hash maps rather than iptables chains, turning lookup from a linear scan into a near-constant-time hash lookup regardless of how many Services exist. For Pod-to-Pod traffic on the same node, Cilium can go further and rewrite the destination at the socket layer the moment a connection is opened — the packet never even needs a full trip through the IP stack to be NAT'd, it's redirected once, up front.

Hubble: observability for free

Because the eBPF programs already see every packet and already know its identity, they're a natural place to also emit an event. Hubble is Cilium's observability layer: it turns that same eBPF vantage point into flow logs (who talked to whom, with which identity labels, allowed or dropped and why), a live service dependency map, and per-flow metrics — all without an instrumentation library in the app or a sidecar collecting data. It's the same "the infrastructure already saw this, so surface it" idea Envoy sidecars give Istio and Linkerd for L7 traffic, except Cilium gets it for all traffic, L3 through L7, because it sits below the app entirely.

Cluster Mesh Cilium can also stitch multiple Kubernetes clusters into one flat network and one identity domain (Cluster Mesh): Services in one cluster become reachable from another, and a security identity computed from labels in cluster A is recognized and enforced the same way in cluster B. It's the multi-cluster analogue of the same "policy follows identity, not location" principle.

Why it graduated, and where you'll run into it

Cilium graduated on the strength of solving a problem every cluster has (the Service dataplane and NetworkPolicy enforcement) with a structurally better mechanism than the incumbent, at a moment when eBPF was maturing into a trusted, widely-adopted kernel technology. You'll meet it as the CNI itself — often invisibly, as the default networking layer under a managed cluster — and explicitly wherever a team cares about dense NetworkPolicy at scale, wants FQDN-aware egress control, needs Hubble's flow visibility for incident response, or is chasing kube-proxy overhead out of a very large cluster.

Often confused with Calico is the other major CNI and has grown its own eBPF dataplane option, but its default and most common mode is still iptables/IPVS with BGP for routing — Cilium was eBPF-native from the start and that's still its deepest investment. Flannel is a much simpler overlay-only CNI with no built-in NetworkPolicy enforcement at all — it solves basic Pod connectivity, not security or observability. And Cilium is not a service mesh replacement for Istio/Linkerd by default — its per-node, sidecar-free Envoy mode covers some of the same L7 ground, but Cilium's home turf is the CNI layer (L3/L4, identity, kube-proxy replacement) that a mesh normally assumes already exists underneath it.
